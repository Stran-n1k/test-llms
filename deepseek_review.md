**Проверяемый объект:** `/home/petr/review/project`, коммит `997879a` («Review baseline»).
**Окружение проверки:** Linux amd64, Go 1.27.3 (в `go.mod` объявлен 1.24), Docker 29.9.2, Docker Compose 5.7.0, PostgreSQL 16-alpine в отдельном контейнере; два независимых процесса приложения на портах 18080/18081 с одной базой.

## 1. Краткое заключение

Решение соответствует обязательным свойствам `TASK.md`, которые удалось проверить на практике:

- данные переживают перезапуск приложения, перезапуск PostgreSQL и цикл `docker compose down` / `up`;
- при конкурентных бронированиях места не перепродаются;
- повтор запроса создания брони с тем же ключом идемпотентности не создаёт дубликат, в том числе при одновременных запросах и после перезапуска;
- отмена возвращает места ровно один раз, включая повторные и одновременные отмены;
- гарантии сохраняются для двух независимых экземпляров сервиса с общей PostgreSQL;
- некорректные запросы получают понятные 4xx и не меняют данные;
- схема воспроизводимо создаётся на пустой базе, повторный и параллельный запуск нескольких экземпляров безопасны;
- `Dockerfile` и `compose.yaml` собираются и запускаются, README соответствует фактическому поведению.

**Подтверждённых функциональных дефектов уровня P0–P2 не найдено.** Ниже приведены два P3-замечания (гигиена зависимостей и молчаливый пропуск интеграционных тестов без `TEST_DATABASE_URL`) и отдельно — неподтверждённые риски и необязательные рекомендации. Отсутствие найденных проблем не означает доказанной безопасности.

Ограничения проверки: один хост, PostgreSQL 16, без сетевых разделений, без `kill -9` в середине коммита, без multi-host-сценариев и без сканирования CVE образа/ОС. Полный список — в разделе 7.

## 2. Подтверждённые дефекты

### P0 / P1 / P2

Не найдено. Нарушений обязательных свойств `TASK.md` в проверенных сценариях не выявлено.

### P3-1. Зафиксированные версии зависимостей имеют известные уязвимости по данным `govulncheck`

**Файл и строки:** `go.mod:7` (`github.com/jackc/pgx/v5 v5.7.6`), `go.mod:16` (`golang.org/x/text v0.24.0`), `go.mod:14` (`golang.org/x/crypto v0.37.0`); версии зафиксированы в `go.sum`.

**Условие проявления.** Уязвимости становятся практически значимыми только при определённой конфигурации или будущих изменениях кода; в текущей конфигурации через HTTP API они не эксплуатируются (обоснование ниже). Это не подтверждённая удалённая уязвимость сервиса, а дефект гигиены зависимостей.

**Последствия.** В поставке присутствуют версии с известными CVE. Для pgx это SQL-инъекция через путаницу плейсхолдеров с dollar-quoted строками; для x/text — паника и бесконечный цикл на специально сформированном вводе. Если в будущем появится simple protocol с динамическим SQL или недоверенный источник пароля БД, риск станет реальным.

Инструмент также сообщил о 2 уязвимостях package-level в pgx (`GO-2026-4771`, `GO-2026-4772`) и 20 module-level (в основном `golang.org/x/crypto`), которые, по его же выводу, не вызываются из кода.

**Применимость к текущему коду.**

- `GO-2026-5004` (pgx). В pgx v5.7.6 интерполяция параметров выполняется в `Conn.sanitizeForSimpleQuery` (`conn.go:1243`), а simple protocol выбирается для запросов без аргументов (`conn.go:500-502`) или при явной настройке. Все запросы в `internal/booking/store.go`, принимающие пользовательские значения, передают аргументы `$1...$n` и по умолчанию идут через extended protocol (`DefaultQueryExecMode = QueryExecModeCacheStatement`, `conn.go:190`). Константные DDL-запросы миграции и `Ping` могут идти simple protocol, но не содержат пользовательских данных и dollar-quoted литералов. Приложение нигде не включает simple protocol. Поэтому SQL-инъекция через HTTP в текущем коде не эксплуатируется.
- `GO-2026-6629` / `GO-2026-5970` (x/text). Путь достигается при SASLprep-нормализации пароля в pgx на этапе подключения к PostgreSQL. Вход — пароль из `DATABASE_URL`, то есть доверенная конфигурация оператора, а не HTTP-ввод. Испорченный пароль может уронить или подвесить запуск, но не даёт удалённого воздействия через API.
- Перечисленные module-level срабатывания `x/crypto` относятся к пакетам SSH/openpgp, которые проект не импортирует.

**Краткое направление исправления.** Обновить `github.com/jackc/pgx/v5` до `>= 5.9.2` и `golang.org/x/text` до `>= 0.41.0` (и `golang.org/x/crypto` до исправленной версии, которую подберёт `go mod tidy`), затем повторить `go test` и `govulncheck`. В рамках ревью зависимости не изменялись.

## 3. Неподтверждённые риски и необязательные рекомендации

### 3.1. Неподтверждённые риски

1. **Исчерпание ресурсов и отсутствие ограничителей.** В `main.go:44` жёстко задано `MaxConns = 20` на экземпляр; нет `statement_timeout`/`lock_timeout`, rate limiting и квот. `/healthz` использует тот же пул (`handler.go:42`). Предпосылки: устойчивая нагрузка на одно событие или зависшая транзакция/advisory lock; последствия: рост задержек, занятые соединения, 503 на healthz, перезапуск оркестратором. Кратковременный всплеск 1000 запросов прошёл за 4,1 с без 500, но устойчивый/состязательный сценарий не проверялся. Направление: таймауты, отдельный health-пул, rate limiting, метрики.
2. **Порт PostgreSQL опубликован наружу с демонстрационными учётными данными.** `compose.yaml:7-9` задаёт `booking/booking`, `compose.yaml:22` использует тот же пароль, порт `5432` публикуется на все интерфейсы. Предпосылки: хост доступен из недоверенной сети; последствия: прямой доступ к БД в обход приложения и его инвариантов. Для локальной демонстрации это допустимо; для эксплуатации — условие развёртывания.
3. **Нет аутентификации и TLS.** Прямо разрешено `TASK.md`. Предпосылки: публичная сеть; последствия: любой клиент может создавать события и брони, а при знании UUID — отменять чужую бронь; трафик и учётные данные БД передаются в открытом виде. UUID v4 трудно угадать, но они могут утекать через логи/ссылки. Условие развёртывания, не дефект задания.
4. **Денормализованный счётчик `booked_seats`.** Инвариант «сумма активных мест = `booked_seats`» поддерживается только кодом `Store`; `CHECK` в `migrate.go:13-14` ограничивает лишь диапазон. Предпосылки: будущие прямые записи в БД, ручной ремонт или новый путь записи; последствия: расхождение счётчика и фактических броней. В текущих стресс-проверках расхождений не было (0 drift). Направление: сохранять запись только через `Store`; при необходимости — триггер или периодическая сверка.
5. **Миграции не версионированы.** `CREATE TABLE IF NOT EXISTS` (`migrate.go:9-32`) не добавит новую колонку в уже существующую таблицу; изменение схемы потребует ручного `ALTER TABLE` или отдельной системы миграций. Это честно указано в README:202-204. Предпосылки: будущее изменение схемы; последствия: старые базы не получат изменение, возможны ошибки на старте. Направление: версионированные миграции при первом изменении схемы.
6. **Глобальные и бессрочные ключи идемпотентности.** Один и тот же ключ нельзя использовать для разных событий; ключи и брони хранятся бессрочно (README:97-101, 200-201). Предпосылки: повторное использование ключа или долгая эксплуатация; последствия: 409 при другом `event_id` и неограниченный рост таблиц. Направление: при необходимости — область видимости по событию, TTL/архивация.
7. **Наблюдаемость.** `internalError` (`handler.go:250-252`) не логирует исходную ошибку; нет access-логов, request-id, метрик и трассировки. Предпосылки: инцидент с 500/задержками; последствия: сложнее диагностировать. Направление: логировать внутренние ошибки с идентификатором запроса, добавить базовые метрики.
8. **Кэширование динамических GET.** Ответы `/events/{id}` и `/events/{id}/availability` не содержат `Cache-Control`; промежуточный кэш теоретически может показать устаревшую доступность. Бронирование всё равно атомарно проверит места. Направление: `Cache-Control: no-store` для динамических ответов.
9. **Мелкие особенности HTTP-семантики.** `HEAD` на ресурсы возвращает 405; тело > 1 МиБ даёт 400 `invalid_json`, а не 413; отсутствие `Content-Type` даёт 415 (разумно и соответствует README). Сообщение `invalid JSON: %v` раскрывает детали Go-декодера, но не секреты. Это не нарушения `TASK.md`, а необязательная полировка.

### 3.2. Необязательные рекомендации

- Ввести узкий интерфейс для зависимости `Handler` от хранилища, чтобы проверять валидацию и маршрутизацию без PostgreSQL; текущая привязка к конкретному `*Store` (`handler.go:20-30`) заставляет даже простые HTTP-тесты поднимать БД.
- Добавить unit-тесты для `pathParts`, валидации и маппинга ошибок.
- Добавить `statement_timeout`/`lock_timeout` и контекстный таймаут на запросы к БД; отделить liveness от readiness.
- Добавить rate limiting и квоты на создание событий/броней.
- Добавить access-логи с request-id, метрики и аудит отмен.
- Зафиксировать base-образы по digest, добавить `read_only`, `cap_drop`, лимиты ресурсов; не публиковать порт БД на host в production.
- Обновить зависимости по P3-1 и включить `govulncheck` в CI.
- Включить интеграционные тесты в CI с сервисом PostgreSQL (P3-2).
- Добавить fuzz-тесты для JSON/HTTP-слоя.
- Вернуть более общее сообщение для `invalid_json`, не раскрывающее имена Go-полей.
- Добавить `Cache-Control: no-store` для динамических ответов.

## 4. Архитектура

**Соразмерность.** Решение небольшое и соразмерное задаче: `cmd/booking/main.go` плюс четыре файла в `internal/booking` — `types.go`, `store.go`, `migrate.go`, `handler.go` (~690 строк кода и ~390 строк тестов). Нет лишних слоёв, интерфейсов «на будущее», DI-контейнера или внешней ORM. Для задачи такого размера это плюс: меньше кода для сопровождения и меньше мест, где можно ошибиться с транзакциями.

**Разделение ответственности.** `main.go` отвечает за конфигурацию, пул, миграцию, жизненный цикл HTTP-сервера и graceful shutdown (`main.go:25-83`). `handler.go` — за HTTP-маршруты, разбор запроса, валидацию и преобразование ошибок в статусы; бизнес-логики в нём нет, кроме проверок входных полей. `store.go` — за SQL и транзакции. `migrate.go` — за DDL. `types.go` — модели, лимиты и sentinel-ошибки. Направление зависимостей чистое: `main -> booking -> pgx`, без циклов. Единственное смешение — миграция живёт в `Store` (`migrate.go:37`), хотя это инфраструктурная/стартовая ответственность, а не доступ к данным. Для текущего размера это приемлемо; выделение отдельного `Migrator` не окупается.

**Бизнес-инварианты и транзакции.** Ключевое достоинство: инварианты размещены там, где их можно проверить атомарно. Проверка вместимости, инкремент `booked_seats` и вставка брони находятся в одной транзакции, строка события блокируется `SELECT ... FOR UPDATE` (`store.go:151-179`). Отмена делает условный `UPDATE ... WHERE status='active' RETURNING` и уменьшает счётчик в той же транзакции (`store.go:198-220`); ровно один конкурентный отменяющий проходит дальше. Идемпотентность опирается на advisory lock по хешу ключа и уникальное ограничение в БД (`store.go:133-137`, `migrate.go:21-22`). Это правильное место для инвариантов, которые должны соблюдаться между двумя экземплярами: приложение не пытается координировать их в памяти.

Компромисс — денормализованный `booked_seats`. Он даёт дешёвое чтение доступности и простую атомарную блокировку, но инвариант «счётчик = сумма активных мест» не выражен в схеме. Пока все записи идут через `Store`, это корректно; при появлении второго пути записи понадобится триггер, вычисление на лету или регулярная сверка. Это осознанный trade-off, а не ошибка.

**Тестируемость.** Тесты сильные для заявленного объёма: настоящая PostgreSQL, отдельная случайная схема на тест (`integration_test.go:29-78`), два независимых пула, `-race`, повторная миграция, конкурентное бронирование, идемпотентность, конкурентная отмена и HTTP-сценарии. Это позволяет проверять именно те свойства, которые важны по `TASK.md`. Ограничение: все тесты завязаны на БД и молча пропускаются без переменной (P3-2); handler привязан к конкретному `*Store`, поэтому валидацию нельзя проверить без PostgreSQL. Для задачи это приемлемая цена, но при росте числа HTTP-сценариев лучше ввести интерфейс и выделить чистые функции валидации.

**Понятность и стоимость изменений.** Код читается легко: имена говорящие, комментарии объясняют порядок блокировок и смысл идемпотентности (`store.go:116-118, 131-133, 189-190`), README подробно описывает гарантии и ограничения. `CreateBooking` — самый длинный метод (~70 строк), в нём совмещены поиск по ключу, проверка вместимости и запись; его можно разбить на небольшие helper-функции, но транзакционная граница должна остаться единой, поэтому выигрыш невелик. Основная будущая стоимость — отсутствие версионированных миграций: добавление колонки не применится к существующей базе, и это придётся решать отдельно. Это указано в README как известное ограничение, поэтому для текущего задания допустимо.

**Итог по архитектуре.** Решение не переусложнено и не имеет архитектурных дефектов, блокирующих сопровождение. Слабые места — эволюция схемы, наблюдаемость и тестируемость HTTP-слоя без БД; они относятся к будущему развитию, а не к выполнению текущих требований.

## 5. Безопасность

### 5.1. Модель угроз и границы доверия

Предполагаемая модель: HTTP-клиент недоверенный; сеть до PostgreSQL и переменные окружения (`DATABASE_URL`, `HTTP_ADDR`) — доверенные; содержимое БД — доверенное, поскольку писать в неё может только сервис. Атакующий контролирует метод, путь, заголовки и JSON-тело, а также UUID, которые он знает или подбирает. Аутентификация и TLS отсутствуют по условию `TASK.md`; это не дефект выполнения, но обязательное условие публичной эксплуатации.

### 5.2. SQL-инъекции

Все значения передаются параметрами `$1...$n`; динамической подстановки пользовательских строк в SQL нет. Идентификаторы схемы в тестах экранируются через `pgx.Identifier` (`integration_test.go:46`), в прикладном коде таких мест нет. Проверка полезной нагрузкой `x'; DROP TABLE bookings;--` в `title` и `k'); DROP TABLE events;--` в `idempotency_key` показала, что значения сохраняются буквально, таблицы остаются доступны, ответы корректны.

`govulncheck` формально указывает на CVE SQL-инъекции в pgx v5.7.6 (P3-1), но в текущей конфигурации путь `SanitizeSQL` не используется для пользовательских запросов: они идут через extended protocol с аргументами, а simple protocol применяется только к константным DDL/`Ping` без dollar-quoted литералов. Это обоснование применимости, а не доказательство, что зависимость безопасна в любой будущей конфигурации.

### 5.3. Недоверенный JSON и ограничения входа

`decodeRequest` (`handler.go:211-230`) проверяет `Content-Type`, ограничивает тело 1 МиБ через `http.MaxBytesReader`, включает `DisallowUnknownFields` и требует ровно одно JSON-значение. Дополнительно `encoding/json` имеет собственный предел вложенности. Проверены: пустое тело, пробелы, массив, `null`, два объекта, неизвестные поля, тело 2 МиБ, NUL в `title` и ключе, числа вне диапазона, дробные числа, огромные числа. Во всех случаях получен 4xx; ответов 5xx и паник не было, данные не изменились. Длина `title` считается в рунах и согласована с `char_length` в БД; ключ ограничен 200 байтами и проверяется на NUL, что предотвращает ошибки PostgreSQL на NUL-байтах.

### 5.4. Таймауты и исчерпание ресурсов

У HTTP-сервера заданы `ReadHeaderTimeout 5s`, `ReadTimeout 15s`, `WriteTimeout 30s`, `IdleTimeout 60s` (`main.go:58-65`). Это защищает от медленных заголовков и части slowloris-сценариев. Ограничение тела — 1 МиБ. При этом нет rate limiting, квот, `statement_timeout`/`lock_timeout`; пул ограничен 20 соединениями на экземпляр (`main.go:44`), а `/healthz` использует тот же пул. При устойчивой нагрузке или зависшей транзакции возможны очередь запросов и 503 на healthz; в кратком тесте 1000 параллельных запросов (4,1 с, 800 успешных броней, 200 корректных 409, 0 ошибок 5xx) проблема не проявилась. Это неподтверждённый риск, а не выявленный отказ.

### 5.5. Утечки ошибок, секретов и логирование

Клиенту возвращается общее `{"error":{"code":"internal_error","message":"internal server error"}}` (`handler.go:250-252`); исходная ошибка БД не раскрывается. Ошибки разбора JSON содержат только текст декодера и не содержат секретов. Логи структурированы (`slog`), пишутся в stdout; пользовательский ввод в логи не попадает. Проверены несколько некорректных `DATABASE_URL`: pgx редактирует пароль в URL и keyword/value DSN (`postgres://user:xxxxx@...`, `password=xxxxx`), а ошибки подключения не содержат пароля. Оговорка: строка, не являющаяся валидным DSN, может быть выведена целиком; если оператор ошибочно поместит секрет в произвольную строку без схемы, он может попасть в лог. Это не подтверждённая утечка при штатной конфигурации.

Отдельно: `internalError` не логирует исходную ошибку, поэтому 500-е сложно диагностировать; access-логов и аудита отмен нет. Это влияет на наблюдаемость, а не на конфиденциальность.

### 5.6. Контейнеры и открытые порты

Приложение в образе работает не от root: `Dockerfile:10-12` создаёт пользователя `app`, `USER app`; проверено `docker exec project-app-1 id` → `uid=100(app)`. Сборка multi-stage, в runtime нет компилятора и исходников. `Dockerfile` не задаёт `read_only`, `cap_drop` и лимиты ресурсов — это необязательное усиление. `compose.yaml:8-9` публикует PostgreSQL на все интерфейсы, `compose.yaml:24-25` — приложение на все интерфейсы; для демо это удобно, для production требует сетевой политики и смены пароля. Порт БД с паролем `booking` — риск эксплуатации, а не дефект выполнения задания.

### 5.7. Аутентификация, TLS и условия развёртывания

Аутентификации и TLS нет; это прямо разрешено `TASK.md`. Для публичной эксплуатации необходимы: аутентификация и авторизация (особенно для отмены броней), TLS на входе, TLS или защищённая сеть до PostgreSQL, менеджер секретов вместо пароля в compose, ограничение сетевого доступа к БД, rate limiting и аудит. Без авторизации любой, кто знает UUID брони, может её отменить; UUID v4 делает перебор непрактичным, но не заменяет авторизацию.

7. **Другие версии PostgreSQL, ОС и архитектуры.** Проверялась только PostgreSQL 16 на Linux amd64; совместимость с другими версиями и платформами не проверялась.

## 8. Сильные стороны

- **Конкурентность спроектирована правильно.** Блокировка строки события `FOR UPDATE`, условный `UPDATE ... RETURNING` при отмене и проверка вместимости в одной транзакции — это именно те механизмы, которые дают гарантии при двух экземплярах. Подтверждено стрессом: 1000 броней, 2400 отмен, 600 смешанных операций, 0 расхождений.
- **Идемпотентность простая и надёжная.** Уникальное ограничение БД плюс advisory lock по хешу ключа; повтор возвращает исходную бронь, в том числе после отмены и перезапуска; конфликт параметров даёт понятный 409. Проверено 60 одновременными запросами и двумя процессами.
- **Отмена ровно один раз.** Условное обновление статуса не даёт вернуть места дважды; конкурентные и повторные отмены возвращают 200 и не меняют `cancelled_at`.
- **Сохранность данных и миграция.** PostgreSQL-том, повторная миграция, перезапуск приложения/БД/контейнеров и параллельный старт на пустой базе — всё проверено.
- **Валидация.** Продуманные ограничения тела, запрет неизвестных полей, NUL-байтов, несколько JSON-значений; понятные коды ошибок; некорректные запросы не портят данные.
- **Документация.** README точно описывает API, гарантии, механизм хранения, команды и известные ограничения; расхождений с фактическим поведением не найдено.
- **Качество кода и тестов.** Небольшой понятный код, `gofmt`/`go vet`/`staticcheck`/`gosec` чисто, `go.sum` проверен; тесты используют настоящую PostgreSQL, отдельные схемы, два пула и `-race`, стабильны при `-count=3`.
- **Эксплуатационные мелочи.** Graceful shutdown, тайм-ауты HTTP-сервера, healthcheck с проверкой БД, non-root контейнер, многоступенчатая сборка, отсутствие SQL-инъекций и утечек секретов в проверенных путях.

## Приложение A. Воспроизводящий скрипт (временный, вне проекта)

```bash
#!/usr/bin/env bash
set -euo pipefail

B=http://127.0.0.1:18081
json_id() { python3 -c 'import sys,json; print(json.load(sys.stdin)["id"])'; }

# 4. Инвариант в БД.
docker exec dsk-review-pg psql -U booking -d bookingapp -P pager=off -c "
SELECT count(*) AS drift FROM (
  SELECT e.id FROM events e LEFT JOIN bookings b ON b.event_id = e.id
  GROUP BY e.id, e.booked_seats, e.capacity
  HAVING e.booked_seats <> COALESCE(SUM(b.seats) FILTER (WHERE b.status='active'), 0)
     OR e.booked_seats > e.capacity OR e.booked_seats < 0
) t;"
```

Ожидаемые результаты (фактически получены): `50 201 / 150 409` и `booked_seats=50`; `1` ответ 201, `59` ответов 200, `distinct booking ids: 1`, `booked_seats=7`; `50 200` и `booked_seats=0`; `drift=0`.
