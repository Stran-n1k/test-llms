Приложение не включает `QueryExecModeSimpleProtocol` и использует обычный extended protocol; все SQL-запросы — константы с параметрами (`internal/store/store.go:99-100,121,125,129,140-142,166,184,196`), dollar-quoted литералов и пользовательских вставок в текст SQL нет. ### 3.2. Отсутствие аутентификации и авторизации

`TASK.md` прямо разрешает не делать авторизацию, поэтому это не дефект. Для публичной эксплуатации это условие развёртывания: любой, кто знает `id` события или бронирования, может прочитать бронирование и отменить его (`internal/api/api.go:233-262`). `id` — UUID v4, поэтому перебор практически неосуществим, но идентификаторы могут утечь через логи, referrer, клиентские приложения или переписку. Компенсация на периметре: аутентификация, авторизация по владельцу, TLS, rate limiting, аудит.

### 3.3. Отсутствие TLS и шифрования соединения с БД

`compose.yaml:19` использует `sslmode=disable`, приложение не терминирует TLS. Для локального запуска это нормально и описано в README; для публичной эксплуатации нужен TLS-прокси перед приложением и, при необходимости, `sslmode` для PostgreSQL. Без этого трафик и учётные данные БД могут быть перехвачены в недоверенной сети. Это условие развёртывания, а не дефект выполнения TASK.md.

### 3.4. Ограничение ресурсов, rate limiting и неограниченный рост данных

Аутентификации нет, поэтому любой клиент может создавать события и бронирования без ограничения частоты. События, бронирования и ключи идемпотентности хранятся бессрочно (`internal/store/schema.sql:1-21`; ограничение описано в README). Возможны исчерпание диска/БД, рост индексов и деградация популярного события, у которого все записи сериализуются на одной строке `events`. Автоматических квот, TTL и фоновой очистки нет; README это признаёт. Для эксплуатации нужны rate limiting/квоты на периметре, мониторинг размера БД и политика хранения. Тяжёлых нагрузочных проверок в рамках ревью не проводилось, поэтому конкретные пределы не измерены.

### 3.5. Контейнеры и цепочка поставок

Положительно: приложение работает не от root (`Dockerfile:10-12`, проверено `uid=10001(app)`), порт приложения опубликован только на loopback, PostgreSQL в `compose.yaml` наружу не опубликована (проверено `docker inspect`). Не подтверждены как дефекты, но остаются рисками: нет `read_only` rootfs, `cap_drop`, `no-new-privileges` и лимитов CPU/памяти; образы `golang:1.25-alpine`, `alpine:3.22`, `postgres:17-alpine` закреплены тегами, а не digest. Сканирование базовых образов/OS-пакетов (Trivy, Docker Scout и т.п.) не выполнялось, поэтому об отсутствии уязвимостей в них ничего не утверждается. README честно фиксирует незакреплённые digest.

### 3.6. Денормализованное поле `available`

Инвариант `available + SUM(quantity активных бронирований) = capacity` поддерживается кодом (`internal/store/store.go:121,166,196`), а не ограничением БД между таблицами. Текущие два пути записи корректны, и тесты проверяют инвариант. Риск: будущий код записи, ручные правки БД или восстановление части данных могут нарушить соответствие; README прямо предупреждает о прямых записях вне сервиса. Это осознанный компромисс в пользу простого и быстрого чтения; триггер или вычисляемое поле усложнили бы решение.

### 3.7. Интеграционные тесты по умолчанию пропускаются

`go test ./...` без `TEST_DATABASE_URL` завершается успешно, но интеграционные тесты пропускаются (`internal/api/integration_test.go:40-46`); README это явно описывает и предлагает `REQUIRE_INTEGRATION=1`. Риск — «зелёный» CI без проверки PostgreSQL и конкурентности. Это не нарушение TASK.md (тесты есть и запускаются скриптом), но для CI рекомендуется отдельный обязательный job с `REQUIRE_INTEGRATION=1`.

### 3.8. Семантика идемпотентности

Ключ глобален для БД и хранится бессрочно. Повтор после отмены возвращает исходное отменённое бронирование и не создаёт новое — это явно описано в README и не противоречит TASK.md, но клиент обязан смотреть на `status`. Ключи длиной от 1 символа технически допустимы (`internal/api/api.go:22`), поэтому при слабом клиентском ключе возможны коллизии между клиентами и раскрытие чужого бронирования по угаданному ключу; для нормального клиента README предписывает случайный UUID. Сервер не оценивает энтропию ключа — это разумно оставить клиенту, но стоит помнить при интеграции.

### 3.9. Краевые случаи Unicode/JSON

- `encoding/json` заменяет непарный суррогат (`"\ud800"`) на `U+FFFD`; такой JSON проходит проверку `utf8.Valid` и принимается как имя из одного символа замены. Это не нарушает TASK.md (байты валидны, данные не портятся), но если нужна строгая проверка Unicode, непарные суррогаты следует отклонять отдельно. Проверено отдельным вызовом `encoding/json`.
- Дублирующиеся поля JSON обрабатываются стандартно: побеждает последнее значение. Строгая проверка дубликатов не требуется TASK.md.
- Глубина/размер JSON ограничены 16 KiB (`internal/api/api.go:20,112`), поэтому дорогие разборы ограничены.

### 3.10. Паника, откат и недоступность БД

Явного `recover` в HTTP-слое нет; при панике `net/http` закроет соединение и запишет стек в стандартный лог, а не вернёт JSON `500`. В прочитанном коде не найдено пути, приводящего к панике на пользовательском вводе; это потенциальная устойчивость, а не подтверждённый дефект. `defer tx.Rollback(context.Background())` — распространённый приём, гарантирующий откат при отменённом контексте; при «чёрной дыре» в сети теоретически возможен выход за таймаут запроса. Подтвердить это в рамках ревью не удалось; для строгой эксплуатации можно ограничить контекст отката.

### 3.11. Привязка и наблюдаемость

`HTTP_ADDR` по умолчанию `:8080` (`cmd/server/main.go:31-34`), то есть при запуске вне Compose сервис слушает все интерфейсы. В Compose порт ограничен `127.0.0.1` (`compose.yaml:21-22`), но при самостоятельном запуске это стоит учитывать. Также нет access-логов, request-id и метрик; для небольшого сервиса это допустимо, но затрудняет разбор инцидентов. Тела запросов приложение не логирует; явного логирования ключей идемпотентности нет (в проверенных путях они в логи не попадали) — это скорее плюс для приватности.

### 3.12. Отказ PostgreSQL, резервное копирование, HA

Гарантии сохраняются на уровне PostgreSQL; README описывает отсутствие резервного копирования и высокой доступности. В ревью проверен штатный перезапуск контейнера PostgreSQL через Compose (приложение восстановило health, данные сохранились). Не проверялись `kill -9` PostgreSQL, заполнение диска, потеря сети и failover — это инфраструктурные риски, а не дефекты приложения.

## 5. Архитектура

### 5.1. Соразмерность и состав

Решение небольшое и соразмерное задаче: три производственных файла Go (`cmd/server/main.go`, `internal/api/api.go`, `internal/store/store.go`, вместе с `schema.sql` — около 560 строк) и около 560 строк тестов. Единственная прямая зависимость — `pgx`; фреймворков, ORM, Redis и лишних слоёв нет. Это не переусложнено: для заявленных свойств достаточно HTTP-слоя и транзакционного слоя доступа к PostgreSQL.

### 5.2. Разделение ответственности и направление зависимостей

- `cmd/server` отвечает за конфигурацию из `DATABASE_URL`/`HTTP_ADDR`, старт, миграцию, HTTP-сервер и graceful shutdown (`cmd/server/main.go:26-67`).
- `internal/api` отвечает за маршрутизацию, разбор и валидацию HTTP/JSON, коды ответов и единый формат ошибок (`internal/api/api.go:33-59,90-160,199-262`).
- `internal/store` отвечает за SQL, транзакции, идемпотентность, отмену и миграцию (`internal/store/store.go:57-200`).

Направление зависимостей однонаправленное: `main → api → store`; `store` не импортирует `api`. Это хорошее разделение для данного размера. Компромисс: `store.Event`/`store.Booking` одновременно являются DTO API (JSON-теги в `internal/store/store.go:28-43`), а `api` обращается к `store.Pool` для `/healthz` (`internal/api/api.go:263-266`). В результате транспорт и хранение связаны типами и пулом. Для маленького сервиса это экономит код; при независимом развитии API/БД потребуется отдельный маппинг или интерфейс.

### 5.3. Бизнес-инварианты и границы транзакций

Ключевые инварианты размещены там, где их можно проверить атомарно, — в транзакциях store:

- создание бронирования: вставка с уникальным ключом и уменьшение `available` в одной транзакции (`internal/store/store.go:132-174`);
- повтор: `INSERT ... ON CONFLICT DO NOTHING` + чтение существующей строки в `READ COMMITTED` (`internal/store/store.go:140-157`);
- отмена: условное обновление `status='active'` и возврат мест в одной транзакции (`internal/store/store.go:176-200`);
- миграция: DDL и запись версии в одной транзакции под advisory lock (`internal/store/store.go:57-87`).

Это правильное размещение: вынесение этих проверок в отдельный «сервисный» слой над SQL потребовало бы распределённых транзакций или повторных проверок и увеличило риск гонок. Валидация продублирована в API и в CHECK-ограничениях (`internal/store/schema.sql:3-18`) — это эшелонированная защита, а не лишнее дублирование, потому что БД защищает и от обхода API.

### 5.4. Тестируемость

Сильная сторона: интеграционные тесты поднимают настоящую PostgreSQL, создают отдельную схему на тест, два независимых пула и два HTTP-сервера (`internal/api/integration_test.go:38-130`), проверяют конкурентность, повтор, отмену, смешанную гонку, ограничения БД и перезапуск. Это тестирует именно те свойства, которые заявлены в TASK.md. Негативные HTTP-тесты вынесены в быстрый unit-тест (`internal/api/api_test.go:11-92`).

Ограничение тестируемости: `api.New` принимает конкретный `*store.Store`, а unit-тесты используют `nil` (`internal/api/api_test.go:12`); поэтому валидный запрос в таком тесте упадёт на nil. Для проверки только отклоняемых запросов это безопасно, но небольшой интерфейс к store позволил бы тестировать обработчики без БД. Это не ошибка, а запас на будущее.

### 5.5. Понятность и стоимость изменений

Код читается хорошо: короткие функции, именованные sentinel-ошибки, константы колонок, комментарии к неочевидным местам (`internal/store/store.go:132-133,176-177`). Понятны и транзакционные границы, и причина `READ COMMITTED`.

Стоимость изменений умеренная:

- добавить маршрут — нужно обновить и `mux`, и `allowedMethods` (`internal/api/api.go:36-41,61-76`), иначе можно получить неверный `404` вместо `405`;
- добавить поле бронирования — нужно обновить схему, структуры, валидацию и сравнение в идемпотентности (`internal/store/store.go:149`);
- добавить миграцию — расширить `switch` (`internal/store/store.go:74-85`);
- любой новый путь записи обязан обновлять `available`, иначе нарушится инвариант (см. 3.6).

Это не дефекты, а цена простоты. Альтернативы (таблица маршрутов, интерфейс store, список миграций) уменьшили бы стоимость изменений, но для текущего объёма не обязательны.

### 5.6. Компромиссы

- **Одна строка `events` на событие** сериализует все бронирования события; для маленького сервиса это просто и корректно, для высокой нагрузки — узкое место. README это признаёт.
- **Денормализованный `available`** ускоряет чтение, но требует дисциплины записи.
- **Глобальный ключ идемпотентности без TTL** упрощает гарантии, но требует политики хранения.
- **Отсутствие отдельного сервисного слоя** оправдано: бизнес-правила тесно связаны с SQL-транзакциями.

## 6. Безопасность

### 6.1. Модель угроз и границы доверия

Предполагаемая модель: HTTP-клиенты недоверенные; PostgreSQL, `DATABASE_URL`, `HTTP_ADDR` и Docker-хост контролируются оператором; аутентификация и TLS по TASK.md не требуются. Активы: места на событиях, записи бронирований, доступность БД и процесса. Проверялись SQL-инъекции, обработка недоверенного JSON, ограничения размера и времени, утечки ошибок/секретов, логирование, контейнер и порты. Активные проверки выполнялись только против собственных тестовых сервисов; внешние цели и тяжёлые атаки не использовались.

### 6.2. Что проверено и подтверждено

- **SQL-инъекции.** Весь SQL — константы с параметрами; пользовательские строки не вставляются в текст запроса (`internal/store/store.go:99-100,121,125,129,140-142,166,184,196`). Проверены имя события со строкой `'; DROP TABLE events; --`, SQL-строка в `event_id`, в `Idempotency-Key` и в пути: имя сохранилось как данные (`201`), запросы с SQL в `event_id`/ключе/пути получили `400`, таблицы остались на месте. Это подтверждает отсутствие инъекции в проверенных путях, но не доказывает безопасность всех будущих изменений.
- **Недоверенный JSON.** Ограничение тела 16 KiB (`internal/api/api.go:20,112`), запрет неизвестных полей, ровно один документ, проверка UTF-8, типов и диапазонов (`internal/api/api.go:106-139,162-232`). Проверены `null`, массивы, мусор после объекта, неверные типы, переполнение, NUL, невалидный UTF-8, граница 16384/16385 байт.
- **Таймауты и заголовки.** `ReadHeaderTimeout` 5 с, `ReadTimeout`/`WriteTimeout` 15 с, `IdleTimeout` 60 с, `MaxHeaderBytes` 16 KiB (`cmd/server/main.go:49`); контекст API 10 с (`internal/api/api.go:44`). Это ограничивает медленные запросы и размер заголовков.
- **Ошибки клиенту.** SQL-текст и внутренние детали не возвращаются: `a.fail` отдаёт общие коды, а подробности пишет в лог (`internal/api/api.go:90-104`). `Location` строится из сгенерированного UUID, не из пользовательской строки.
- **Секреты в стартовых ошибках.** Проверены некорректные DSN с паролем: `pgx` редактирует пароль (`user:xxxxxx@...`), в лог не попадает открытый пароль. Это свойство используемой версии `pgx`, а не кода приложения, но проверено на практике.
- **Логирование.** Логи — JSON в stdout; приложение не логирует тела запросов и явно не логирует ключи идемпотентности. Внутренние ошибки БД логируются; в проверенных путях значения ключей в них не попадали, но гарантировать отсутствие любых значений в `DETAIL` ошибок нельзя — это серверный лог, не ответ клиенту.
- **Контейнер и сеть.** Приложение работает от `uid=10001(app)`, не privileged; порт приложения опубликован только на `127.0.0.1`; у PostgreSQL в `compose.yaml` нет опубликованных портов. Проверено `docker inspect`.
- **Ограничение доступа к БД.** В `compose.yaml` БД доступна только внутри сети Compose; наружу опубликован только HTTP-порт на loopback.

### 6.3. Подтверждённые уязвимости

В рамках проверенных сценариев подтверждённых эксплуатируемых уязвимостей не найдено. Известные CVE в зависимостях (раздел 3.1) — подтверждённый результат сканера, но применимость к текущим путям не подтверждена. Это не означает, что уязвимостей нет вообще: полный аудит, fuzzing, DAST и сканирование базовых образов не проводились.

### 6.4. Условия публичной эксплуатации

Для выхода за пределы локального запуска нужны как минимум: TLS, аутентификация и авторизация по владельцу бронирования, rate limiting/квоты, защищённое хранение секретов, `sslmode` для БД, резервное копирование и мониторинг, закрепление образов по digest и их сканирование. Отсутствие этих средств не является дефектом выполнения TASK.md: авторизация, TLS и инфраструктурные средства явно не требовались.

## 9. Сильные стороны

- **Гарантии опираются на PostgreSQL, а не на процесс.** Условный `UPDATE ... WHERE available >= quantity` и условная отмена `status='active'` сериализуются на строке БД и работают для нескольких экземпляров; локальных mutex нет.
- **Корректный механизм идемпотентности.** Уникальный ключ, `INSERT ... ON CONFLICT DO NOTHING`, ожидание конкурентной вставки и последующее чтение в `READ COMMITTED`; ключ не занимается при неуспехе, что проверено.
- **Отмена идемпотентна.** Места возвращает только транзакция, изменившая `active` на `cancelled`; повторные и одновременные отмены не удваивают доступность.
- **Атомарность при сбоях.** Вставка брони и списание мест — одна транзакция; падение процесса в середине операции не оставляет ни брони, ни занятого ключа.
- **Хорошая валидация.** Строгий JSON-разбор, ограничение 16 KiB, запрет неизвестных полей, проверка UTF-8, UUID, диапазонов, ключа и пустого тела отмены; ошибки в едином формате.
- **Безопасные значения по умолчанию для контейнера.** Non-root, loopback-публикация приложения, БД без внешнего порта.
- **Качественная миграция.** DDL и версия в одной транзакции, advisory lock для одновременного старта, fail-fast на неизвестной версии, повторный запуск без потери данных.
- **Сильные тесты.** Настоящая PostgreSQL, отдельная схема на тест, два пула/сервера, `-race`, конкурентные сценарии, перезапуск, ограничения БД и негативные HTTP-проверки; изолированный Compose-проект с cleanup.
- **Честная и подробная документация.** README объясняет механизм идемпотентности, границы транзакций, миграцию, команды запуска/тестов и известные ограничения; расхождений с кодом не обнаружено.
- **Простота и читаемость.** Нет лишних слоёв и зависимостей; ключевые инварианты находятся рядом с атомарными SQL-операциями.

## Приложение A. Воспроизводящая проверка конкурентности

Ниже — очищенная версия использованного скрипта; логика проверок та же, что в основном прогоне. Скрипт требует два экземпляра сервиса на портах 18080 и 18081 с общей БД.

```python
#!/usr/bin/env python3
# Независимая проверка конкурентности/идемпотентности.
# Запуск: python3 probe_clean.py
import json, sys, threading, urllib.request, urllib.error, uuid, collections

A = "http://127.0.0.1:18080"
B = "http://127.0.0.1:18081"

def req(base, method, path, key=None, body=None):
    data = None
    if body is not None:
        data = body if isinstance(body, bytes) else json.dumps(body).encode()
    r = urllib.request.Request(base + path, data=data, method=method)
    if body is not None:
        r.add_header("Content-Type", "application/json")
    if key is not None:
        r.add_header("Idempotency-Key", key)
    try:
        with urllib.request.urlopen(r, timeout=30) as resp:
            return resp.status, resp.read()
    except urllib.error.HTTPError as e:
        return e.code, e.read()

def event(cap):
    s, b = req(A, "POST", "/events", body={"name": "probe", "capacity": cap})
    assert s == 201, (s, b)
    return json.loads(b)

def booking(eid, qty, key, base=None):
    return req(base or A, "POST", "/bookings", key=key,
               body={"event_id": eid, "quantity": qty})

def cancel(bid, base=None):
    return req(base or A, "POST", f"/bookings/{bid}/cancel", body=b"")

def avail(eid):
    s, b = req(A, "GET", f"/events/{eid}")
    assert s == 200, (s, b)
    return json.loads(b)["available"]

def parallel(n, fn):
    out = [None] * n
    barrier = threading.Barrier(n)
    def run(i):
        barrier.wait()
        try:
            out[i] = fn(i)
        except Exception as ex:
            out[i] = ("EXC", repr(ex))
    ts = [threading.Thread(target=run, args=(i,)) for i in range(n)]
    for t in ts: t.start()
    for t in ts: t.join()
    return out

fails = []

# 1. 40 запросов по 1 месту на событие вместимостью 7.
e = event(7)
res = parallel(40, lambda i: booking(e["id"], 1, f"cap-{uuid.uuid4().hex}",
                                     B if i % 2 else A))
codes = collections.Counter(r[0] for r in res)
print("1 capacity:", dict(codes), "available=", avail(e["id"]))
if codes.get(201) != 7 or codes.get(409) != 33 or avail(e["id"]) != 0:
    fails.append("capacity")

# 2. Один ключ, 50 одновременных запросов через два экземпляра.
e2 = event(20)
key = "same-" + uuid.uuid4().hex
res = parallel(50, lambda i: booking(e2["id"], 2, key, B if i % 2 else A))
codes = collections.Counter(r[0] for r in res)
ids = {json.loads(r[1])["id"] for r in res}
print("2 idempotency:", dict(codes), "ids=", len(ids), "available=", avail(e2["id"]))
if codes.get(201) != 1 or codes.get(200) != 49 or len(ids) != 1 or avail(e2["id"]) != 18:
    fails.append("idempotency")

# 3. 50 одновременных отмен одного бронирования.
bid = ids.pop()
res = parallel(50, lambda i: cancel(bid, B if i % 2 else A))
codes = collections.Counter(r[0] for r in res)
ts = {json.loads(r[1])["cancelled_at"] for r in res}
print("3 cancel:", dict(codes), "timestamps=", len(ts), "available=", avail(e2["id"]))
if codes.get(200) != 50 or len(ts) != 1 or avail(e2["id"]) != 20:
    fails.append("cancel")

# 4. Повтор создания после отмены не создаёт новое и не возвращает места второй раз.
s, b = booking(e2["id"], 2, key)
print("4 replay-after-cancel:", s, json.loads(b)["status"], "available=", avail(e2["id"]))
if s != 200 or json.loads(b)["status"] != "cancelled" or avail(e2["id"]) != 20:
    fails.append("replay-after-cancel")

# 5. Смешанная гонка: отмена исходного, его повтор и новые бронирования.
e3 = event(20)
okey = "mix-" + uuid.uuid4().hex
s, b = booking(e3["id"], 12, okey)
assert s == 201, (s, b)
```

## Приложение B. Проверка отката при падении процесса

Сценарий: транзакция уже вставила бронирование, но ждёт строку события; процесс получает `SIGKILL`. После отката не должно остаться ни брони, ни занятого ключа.

```sh
# EID — id события вместимостью 2, PG — временный контейнер PostgreSQL.
docker exec -d "$PG" psql -U booking -d booking -c \
  "begin; update events set available=available where id='$EID'; select pg_sleep(8); commit;"
sleep 1
curl -s -m 20 -X POST http://127.0.0.1:18082/bookings \
  -H 'Content-Type: application/json' -H 'Idempotency-Key: crash-key-1' \
  -d "{\"event_id\":\"$EID\",\"quantity\":1}" &
sleep 2
kill -9 "$APP_PID"
sleep 9
docker exec "$PG" psql -U booking -d booking -tAc \
  "select count(*) from bookings where idempotency_key='crash-key-1'"   # 0
docker exec "$PG" psql -U booking -d booking -tAc \
  "select available from events where id='$EID'"                        # 2
# После повторного запуска приложения тот же ключ дал 201.
```

Результат: `count=0`, `available=2`; повтор с тем же `Idempotency-Key` после старта — `201`.
