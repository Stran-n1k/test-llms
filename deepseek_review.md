### D1. Инъекция перевода строки в лог (P3, подтверждено)

- **Где:** `internal/httpapi/server.go:294` — `log.Printf("%s %s %d %s", r.Method, r.URL.Path, ...)`.
- **Условие:** запрос с percent-encoded управляющими символами в пути, например `GET /events/%0Aforged-log-line`. `net/http` декодирует `%0A` в `r.URL.Path`; строка пишется в лог без экранирования.
- **Последствия:** неаутентифицированный клиент подделывает произвольные строки журнала, включая ложные записи об ошибках/доступах. Целостность журнала и алертинга нарушается; доступа к данным или выполнения кода нет. Если журнал используется как аудит или источник алертов, значимость повышается.
- **Доказательство:** запрос выше и `tail -2 defect.log | cat -A`:

  ```text
  ... GET /events/$
  forged-log-line 400 38M-BM-5s$
  ```

  То есть в файле две строки вместо одной, вторая полностью контролируется клиентом (`38M-BM-5s` — это `cat -A`-представление `38µs`).
- **Направление исправления:** логировать `%q` или `r.URL.EscapedPath()`, вычищать `\n`/`\r`/прочие управляющие символы, либо перейти на структурный логгер с экранированием полей.

### D2. Лимиты считаются в байтах, а документированы в символах (P3, подтверждено)

- **Где:** `internal/service/service.go:67` (`len(name) > maxNameLength`), `:94` (`len(clientToken) > maxTokenLength`); `README.md:61` («`name` 1–200 символов»), `README.md:91` («1–128 символов»).
- **Условие:** не-ASCII имя или ключ. `len` в Go — число байт; кириллица занимает 2 байта на символ.
- **Последствия:** имя из 150 кириллических символов (300 байт) отклоняется с сообщением «at most 200 characters», хотя символов 150; ключ из 100 кириллических символов отклоняется при лимите «128 символов». Контракт API и сообщения об ошибках вводят клиента в заблуждение.
- **Доказательство:**

  ```text
  150 Cyrillic chars (300 bytes) -> 400 name must be at most 200 characters
  100 Cyrillic chars (200 bytes) -> 400 idempotency key must be at most 128 characters
  ```

- **Направление исправления:** решить, что является единицей (байты или руны), и привести код и README к одному; для «символов» — `utf8.RuneCountInString`. Если остаются байты, явно написать «байт» и учесть это в тексте ошибки.

### D3. Идемпотентный повтор с местами вне диапазона возвращает 400, а не исходную бронь (P3, подтверждено)

- **Где:** `internal/store/postgres.go:179-183` — проверка `seat < 1 || seat > capacity` выполняется до поиска существующей брони (`:188-208`). `README.md:94-95`: «Повтор с другими местами возвращает исходное бронирование без изменений».
- **Условие:** для пары `(event_id, idempotency_key)` уже есть бронь, повтор приходит с местом вне `1..capacity`.
- **Последствия:** вместо документированного `200` с исходной бронью клиент получает `400 seat_out_of_range`. Если клиент повторяет запрос с испорченным/изменённым телом, он не может получить результат уже созданной брони. Данные не портятся.
- **Доказательство:**

  ```text
  first create -> 201
  replay with seat 9 -> 400 {"error":{"code":"seat_out_of_range","message":"seat 9 is out of range 1..3"}}
  ```

- **Направление исправления:** сначала искать существующую бронь по `(event_id, token)` и возвращать её; проверку диапазона выполнять только для новой брони. Либо явно описать это исключение в README. Важно не потерять гарантию, что неудачная попытка не создаёт строку: поиск существующей брони не должен вставлять новую.

### D4. `409 seat_taken` при проигранной гонке не перечисляет места (P3, подтверждено)

- **Где:** `internal/store/postgres.go:220-225` — при `23505` возвращается `&domain.SeatTakenError{}` без списка; предварительная проверка `:210-218` обычно даёт точный список, но не является арбитром. `README.md:104-105` обещает, что сообщение перечисляет занятые места.
- **Условие:** два запроса одновременно прошли предварительную проверку и один проиграл на частичном уникальном индексе.
- **Последствия:** клиент получает общее «one or more requested seats are already booked» без конкретных номеров; README вводит в заблуждение. Целостность данных не страдает.
- **Доказательство:** в 100 гонках двух одновременных запросов на одно место 99 ответов `409` содержали общее сообщение; в отдельном прогоне — 300 из 300. Пример:

  ```text
  generic 409 messages: 99 of 100 races
  ```

- **Направление исправления:** после `23505` выполнить отдельное чтение занятых мест (вне откатившейся транзакции) и вернуть их в `SeatTakenError`; либо скорректировать README, указав, что список может отсутствовать при гонке.

### D5. `available_seat_numbers` пропадает при нуле свободных мест (P3, подтверждено)

- **Где:** `internal/httpapi/server.go:54` — тег `json:"available_seat_numbers,omitempty"`.
- **Условие:** событие полностью занято (например, capacity 1 и место 1 забронировано).
- **Последствия:** поле не приходит вовсе вместо `[]`; форма ответа зависит от состояния. Клиенты, ожидающие массив по README (`README.md:72,75`), не получают поле (в JSON его просто нет; не `[]`). Для строгих JSON-схем это ломающее изменение.
- **Доказательство:**

  ```json
  {"id":103,"name":"full","capacity":1,"created_at":"...","booked_seats":1,"available_seats":0}
  ```

- **Направление исправления:** убрать `omitempty` и инициализировать пустой срез (`[]`), либо документировать отсутствие поля. Для списков в API обычно предпочтительнее стабильный `[]`.

### D6. `404`/`405` от стандартного mux — не JSON (P3, подтверждено)

- **Где:** `internal/httpapi/server.go:19-38` — маршруты зарегистрированы в `http.NewServeMux`, но обработчики для неизвестного пути и неверного метода не заданы; `README.md:46` утверждает «Все ответы — JSON».
- **Условие:** `GET /nope` или `GET /bookings` (метод не тот).
- **Последствия:** ответы `404 page not found` и `Method Not Allowed` в `text/plain`; клиент, единообразно разбирающий конверт `{"error":{...}}`, ломается. Это не влияет на данные, но противоречит заявленному контракту.
- **Доказательство:**

  ```text
  GET /nope -> 404 text/plain; charset=utf-8 b'404 page not found\n'
  GET /bookings -> 405 text/plain; charset=utf-8 b'Method Not Allowed\n'
  ```

- **Направление исправления:** зарегистрировать fallback-обработчик и обёртку для метода, возвращающие тот же JSON-конверт с кодами `not_found`/`method_not_allowed`; либо явно описать исключение в README.

### D7. `t.Fatalf` вызывается из рабочих горутин (P3, подтверждено по коду)

- **Где:** `integration/integration_test.go:99-129` (`stack.do`), `:131-138` (`decode`) вызывают `t.Fatalf`; эти helpers используются внутри горутин, запущенных `runConcurrently` (`:210-220`), например в `:454`, `:489`, `:533`, `:577`, `:620`, `:682`.
- **Условие:** любая ошибка HTTP/декодирования в конкурентном тесте.
- **Последствия:** нарушается контракт `testing`: `FailNow`/`Fatalf` должен вызываться из горутины теста. Вспомогательная горутина завершается через `runtime.Goexit`; тест помечается failed, но исходная ошибка может быть замаскирована вторичными несовпадениями счётчиков, а часть проверок не выполнится. Ложного «зелёного» прогона в наблюдавшихся сценариях нет, но диагностика ухудшается.
- **Доказательство:** чтение кода; при прогонах ошибок не было, поэтому проявился только риск, а не отказ.
- **Направление исправления:** helpers должны возвращать `error` (или результат), а `Fatalf` — вызываться только в главной горутине; в рабочих горутинах — `t.Errorf` с последующей агрегацией. Подойдёт `errgroup` с возвратом ошибок.

### D8. Тесты перезапуска и конкурентных миграций проверяют не то, что заявлено; есть непокрытые пути (P3)

- **Где:** `integration/integration_test.go:719-749` (`TestPersistenceAcrossRestart`), `:751-793` (`TestMigrationsIdempotentAndConcurrent`), `:42-61` (`setup` вызывает `Migrate`); `README.md:176`.
- **Условие/суть:**
  1. Тест «перезапуска» закрывает и снова открывает пул соединений в том же процессе; процесс, контейнер и приложение не перезапускаются. README говорит «проверено тестом `TestPersistenceAcrossRestart`», что сильнее фактической проверки (фактическая сохранность подтверждена мной вручную через compose restart/down-up и SIGTERM).
  2. Тест конкурентных миграций запускается после `setup()`, который уже применил миграции, поэтому все версии пропускаются (`version <= current`) и параллельное применение DDL на пустой БД не проверяется; проверяется только захват advisory lock и no-op. Я отдельно проверил 6 одновременных стартов на пустой БД — работает, но тестом это не покрыто.
  3. Путь `Idempotency-Key` из заголовка (`server.go:166-169`) не покрыт: helper всегда кладёт ключ в тело. Проверено вручную.
  4. Не покрыт сценарий «отменить старую бронь после перебронирования тех же мест» — важная проверка, что отмена не освобождает чужие места. Проверено вручную.
- **Последствия:** регрессии в перезапуске процесса, конкурентной миграции, приоритете заголовка и повторной отмене могут пройти незамеченными; README даёт завышенные гарантии.
- **Доказательство:** чтение тестов и их прогон; отдельные ручные проверки описаны в разделе 6.
- **Направление исправления:** тест с реальным перезапуском процесса/контейнера; отдельная пустая БД/схема для теста миграций (или создание БД в тесте); тесты заголовка и старой отмены; скорректировать README.

### D9. Интеграционные тесты делят одну БД без изоляции (P3)

- **Где:** `integration/integration_test.go:42-61` — общий `BOOKING_TEST_DATABASE_URL`, без уникальной схемы, `TRUNCATE` или транзакционной изоляции; все тесты пишут в одни таблицы.
- **Условие:** повторные прогоны, параллельный запуск, отладка.
- **Последствия:** БД растёт от прогона к прогону (в моём прогоне — сотни событий/броней), тесты нельзя пометить `t.Parallel`, состояние может влиять на диагностику; скрытые зависимости от порядка/накопленных данных. Прогон `-count=2` прошёл, поэтому фактического отказа не наблюдалось.
- **Доказательство:** код `setup()` и накопление данных; прогоны `-count=1` и `-count=2` успешны.
- **Направление исправления:** отдельная схема/БД на тест, либо очистка таблиц в `t.Cleanup`, либо уникальные префиксы и параллельно-безопасные проверки.

## 3. Неподтверждённые риски и необязательные рекомендации

### 3.1. Неподтверждённые риски (не выдаются за дефекты)

1. **Публичная эксплуатация без аутентификации/авторизации.** TASK.md прямо разрешает отсутствие авторизации; это не дефект. Однако при публикации любой клиент может создать событие, прочитать любое бронирование и отменить его по последовательному `id`, а также перебрать идентификаторы. Условия развёртывания: обратный прокси с аутентификацией/авторизацией, TLS, сетевые ACL, rate limiting, аудит. То же относится к отсутствию TLS и к `sslmode=disable` в compose.
2. **Исчерпание ресурсов.** `GET /events` не имеет пагинации, а `GET /events/{id}` при capacity 100000 возвращает весь список мест: в замере — 589 053 байта и ~0,03 с на запрос (2 vCPU). Без rate limiting это усилитель нагрузки и трафика; лимиты задокументированы в README, поэтому это риск публичной эксплуатации, а не нарушение TASK.md. Также нет retention для отменённых строк и нет квот на создание событий/броней.
3. **Нет `statement_timeout`/таймаута на SQL-запрос.** Запросы используют контекст HTTP-запроса; при обрыве клиента запрос отменяется (проверено: транзакция откатилась, повтор вернул 201). Но если клиент ждёт, а БД заблокирована, запрос может долго удерживать соединение из пула (25 соединений). Воспроизвести исчерпание пула не удалось; рекомендую `statement_timeout` и отдельные таймауты на запросы.
4. **Advisory lock миграций может блокировать старт неограниченно долго,** если процесс, держащий блокировку, завис. Не воспроизводилось; рекомендуется `pg_try_advisory_lock` с таймаутом/повторами или `lock_timeout`.
5. **Денормализация `booking_seats.event_id`.** Значение приходит из запроса и не связано композитным FK с `bookings(event_id)`. Текущий код всегда передаёт согласованные значения (SQL-проверка `booking_event_mismatch = 0`), но прямой доступ к БД или будущая ошибка кода может нарушить инвариант. Рекомендуется композитный FK или CHECK.
6. **Нет DB-ограничения `seat_no <= capacity`;** проверка только в приложении (`postgres.go:179-183`). Для защиты от прямых записей и будущих изменений можно добавить CHECK/триггер, но при текущем API нарушение невозможно.
7. **Ответ `201` читается после коммита** (`postgres.go:229-236`): в экзотической гонке другой клиент, угадавший новый `id`, может отменить бронь до чтения, и `201` вернёт `cancelled`. Данные при этом консистентны; воспроизвести не удалось. Можно читать бронь внутри транзакции или собирать ответ из уже известных данных.
8. **Ошибки `context.Canceled` логируются как `internal error`** (наблюдалось `check seats: context canceled` при обрыве клиента). Это шум в логах и потенциальные ложные алерты; рекомендуется отличать отмену клиента от внутренней ошибки.
9. **Образы закреплены тегами, не digest;** `postgres:16-alpine` и `alpine:3.21` могут обновиться. Сканирование CVE образов не выполнялось; `govulncheck` проверяет только Go-модули.
10. **Повтор с тем же ключом и другим телом возвращает исходную бронь** — задокументированное поведение (`README.md:94-97`), не дефект. Риск: клиент, ошибочно переиспользовавший ключ для другой операции, получит чужие места без признака конфликта. Рекомендация: хранить хеш тела и возвращать `409`/`422` при несовпадении.

### 3.2. Необязательные рекомендации (не требования TASK.md)

- Свести валидацию места в одно место: сейчас положительность/дубликаты проверяет service (`service.go:107-120`), диапазон — store (`postgres.go:179-183`), а ошибки разные (`invalid_request` и `seat_out_of_range`). Это не ошибка, но снижает связность.
- Сортировать места защитно внутри store, а не полагаться на контракт «service уже отсортировал» (`postgres.go:350-352`). Иначе новый вызывающий `Store.CreateBooking` может нарушить предположение об отсутствии deadlock.
- Убрать `DB() *sql.DB` из продакшн-API store (`postgres.go:75`) или вынести тестовый доступ в отдельный helper.
- Не включать `Migrate`/`Ping` в бизнес-интерфейс `Store` (`service.go:25-40`): миграции — инфраструктурная обязанность; сейчас `service.Migrate` (`service.go:60`) и вызов в `main.go:47` немного размывают слои.
- Переименовать `EventAvailability.AvailableSeats []int` (`domain.go:29`) — поле звучит как количество, но хранит номера мест; в ответе при этом `available_seats` — число, а `available_seat_numbers` — список. Это затрудняет чтение.
- Добавить структурные логи с request id, метрики и таймауты БД; для публичного API — rate limiting. README уже фиксирует отсутствие метрик/трейсинга.
- Для контейнеров: `read_only`, `no-new-privileges`, лимиты CPU/памяти, секреты вместо пароля в compose, TLS до БД, публикация только через прокси.
- Для ответа `400` на превышение тела можно использовать `413` (`http.MaxBytesReader`, `server.go:237`), но это вопрос вкуса; главное — поведение стабильно и не приводит к 500.

## 4. Архитектура

### 4.1. Соразмерность и структура

Решение соразмерно небольшой задаче: пять production-пакетов, стандартный `net/http` (Go ≥ 1.22), одна прямая внешняя зависимость `pgx/v5` (`go.mod:5`, плюс косвенные), собственная миграционная обвязка на ~50 строк (`internal/store/migrations.go`). Нет лишних фреймворков, брокеров, кешей и слоёв «на вырост». Это сильная сторона: код читается за один проход, запуск воспроизводим, зависимостей мало.

Структура:
- `cmd/server/main.go` — конфигурация, открытие пула, миграции, HTTP-сервер, graceful shutdown.
- `internal/domain` — типы и ошибки.
- `internal/service` — валидация и фасад над хранилищем.
- `internal/store` — SQL, транзакции, миграции.
- `internal/httpapi` — маршруты, DTO, маппинг ошибок, middleware.

### 4.2. Направление зависимостей и связанность

Направление корректное: `httpapi → service → domain`, `store → domain`; `service` определяет потребительский интерфейс `Store` (`service.go:25-40`), `store` его реализует, `main` связывает. Циклов нет. Это даёт тестируемость service через подделку (`service_test.go:12-48`) и позволяет заменить хранилище.

Связанность умеренная, но есть два «протекающих» места:
- `PostgresStore.DB()` (`postgres.go:75`) отдаёт `*sql.DB` любому импортёру; это тестовый хук в продакшн-типе. Лучше держать его в `_test.go`-хелпере или отдельном пакете.
- Интерфейс `Store` включает `Ping` и `Migrate` (`service.go:25-27`), то есть инфраструктурные операции проходят через бизнес-сервис (`service.go:58-60`, `main.go:47`). Для задачи это безвредно, но семантически `Migrate` — не бизнес-операция.

### 4.3. Где живут бизнес-инварианты и границы транзакций

Ключевое архитектурное решение: гарантии конкурентности вынесены в PostgreSQL, а не в память процесса. Это правильно для требования «два экземпляра с общей базой»:
- запрет перепродажи — частичный уникальный индекс `UNIQUE (event_id, seat_no) WHERE active` (`migrations.go:46-47`);
- идемпотентность — `UNIQUE (event_id, client_token)` (`migrations.go:32`) и `INSERT ... ON CONFLICT DO NOTHING` (`postgres.go:188-208`);
- однократная отмена — `UPDATE ... WHERE status='confirmed'` + `UPDATE booking_seats ... WHERE active` в одной транзакции (`postgres.go:243-276`).

Границы транзакций расставлены аккуратно: в `CreateBooking` в одной транзакции находятся чтение capacity, вставка брони, предпроверка мест и вставка мест (`postgres.go:165-231`); в `CancelBooking` — смена статуса и освобождение мест (`:243-276`). Это соответствует инвариантам. Чтение ответа после коммита (`:232`, `:275`) на данные не влияет; нюанс описан в 3.1.7.

Цена решения: бизнес-правила выражены в SQL и индексах, а не в доменных типах. `domain` — в основном DTO/ошибки (`domain.go`), `service` — тонкий валидатор. Понять правила можно только по `postgres.go` и миграциям. Для небольшой задачи это разумный компромисс: альтернатива (локальные мьютексы/счётчики) не дала бы гарантий для двух экземпляров, а явная блокировка строк event усложнила бы схему. Но при росте правил (категории мест, лимиты на клиента, частичные брони) стоимость изменений вырастет: придётся менять и SQL, и API, и тесты.

### 4.4. Тестируемость

- Service тестируется без БД через `fakeStore` (`service_test.go`), что покрывает валидацию и сортировку.
- HTTP-слой не имеет unit-тестов; он проверяется интеграционно через `httptest` и настоящую PostgreSQL (`integration_test.go`). Это даёт реалистичность, но замедляет обратную связь и оставляет без быстрых тестов `decode`, маппинг ошибок, 404/405, лимит тела.
- Store тестируется только интеграционно — это неизбежное следствие вынесения инвариантов в SQL. Тесты конкурентности содержательные (одинаковый ключ, одно место, массовые брони, отмена, две «инстанции»), но качество реализации тестов имеет замечания D7–D9.

### 4.5. Понятность и стоимость изменений

Код читаемый, имена в целом точные, комментарии объясняют неочевидные решения (порядок вставки мест, зачем partial index). Ошибки типизированы (`domain.go:45-76`), маппинг в HTTP собран в одном месте (`server.go:258-275`) — добавить новый класс ошибок относительно дешево, хотя требует правки и домена, и `writeError`.

Что затруднит поддержку:
- расхождение README и поведения (D2–D6) — новый разработчик будет доверять документации;
- неявный контракт «места уже отсортированы» (`postgres.go:350-352`);
- дублирование проверки мест между service и store;
- отсутствие unit-тестов HTTP-слоя;
- отсутствие структурных логов/метрик (задокументировано, но повышает стоимость эксплуатации).

Избыточной сложности не видно. Упрощения, которые можно было бы назвать чрезмерными (собственные миграции вместо golang-migrate, `statusWriter`, recovery-middleware), малы и оправданы: они уменьшают число зависимостей и кода. Требовать конкретного числа слоёв или библиотек нет оснований.

## 5. Безопасность

### 5.1. Модель угроз и границы доверия

Предполагаемая модель: неаутентифицированный HTTP-клиент в сети может вызывать любой метод API; PostgreSQL считается доверенной; TLS между клиентом и приложением и между приложением и БД в compose отсутствует. Граница доверия — порт 8080 приложения. Внутренние порты БД в compose не публикуются, что снижает поверхность. Отсутствие аутентификации/авторизации разрешено TASK.md и не считается дефектом; это условие публичной эксплуатации (см. 3.1.1).

### 5.2. Подтверждённые недостатки

- **D1 — инъекция в лог** (P3): подтверждена, подробности и воспроизведение в разделе 2. Это единственная подтверждённая уязвимость; она не даёт доступа к данным, но ломает целостность журнала.
- Иных подтверждённых уязвимостей (SQLi, RCE, обход авторизации, утечка секретов) не найдено. Это не доказывает их отсутствие (см. 5.5).

### 5.3. Проверенные классы

- **SQL-инъекции.** Все пользовательские значения передаются параметрами (`$1`, `$2`, …); динамически собираются только списки плейсхолдеров в `takenSeats`/`insertSeats` (`postgres.go:318-348,353-367`), идентификаторы таблиц/колонок не приходят от клиента, `id` в пути парсится как `int64` (`server.go:228-234`). Проверка: имя `x'); DROP TABLE events;--` сохранено как строка, таблица `events` на месте; `event_id` строкой отклонён с 400. Инъекций не обнаружено.
- **Недоверенный JSON.** `DisallowUnknownFields`, ровно один объект, лимит тела 1 МиБ (`server.go:236-248`). Пустое/битое тело, неизвестные поля, строки вместо чисел, тело >1 МиБ дают 400 без 500/паники. Глубина вложенности ограничена `encoding/json`; отдельных проверок на deeply nested JSON не делал.
- **Таймауты и ресурсы.** На сервере заданы `ReadHeaderTimeout` 5 с, `ReadTimeout` 10 с, `WriteTimeout` 15 с, `IdleTimeout` 60 с (`main.go:55-58`); пул БД — 25 соединений (`postgres.go:41-43`). При обрыве клиента запрос к БД отменяется: в тесте с `ACCESS EXCLUSIVE` на `booking_seats` клиент отвалился по `--max-time 2`, транзакция откатилась (0 строк), повтор с тем же ключом вернул 201. Риски исчерпания пула и отсутствие `statement_timeout` — в 3.1.2–3.1.3.
- **Утечка внутренних ошибок и секретов.** Клиенту отдаётся общий `internal server error`; детали пишутся в лог (`server.go:271-273`). В логах нет тел запросов, заголовков и ключей идемпотентности. При старте с недоступной БД сообщение содержит DSN-параметры `user/database` и адрес, но не пароль (проверено с `secretpw`). `healthz` раскрывает только доступность БД.
- **Логирование.** Путь логируется без экранирования (D1); в остальном формат минимальный (метод, путь, статус, длительность). Нет request id и структурных полей — эксплуатационное замечание.
- **Контейнеры и порты.** Приложение запускается от непривилегированного `app` (uid 10001, `Dockerfile:13-14`), образ на alpine, бинарник статический. БД в compose не имеет `ports` — наружу не опубликована. Приложение публикует `0.0.0.0:8080` (`compose.yaml:21-22`), TLS нет. Пароль БД задан в compose открытым текстом (`compose.yaml:19`), `sslmode=disable`; для dev это нормально, для продакшна — условия развёртывания. Нет `read_only`, `no-new-privileges`, лимитов ресурсов и закрепления образов по digest.
- **Зависимости.** `govulncheck` v1.9.0 (Go 1.27.3) по `./...`: `No vulnerabilities found.` Это проверка известных уязвимостей Go-модулей (pgx v5.12.0 и косвенные), а не аудит образов/ОС и не доказательство отсутствия уязвимостей.

### 5.4. Условия безопасной публичной эксплуатации

Аутентификация и авторизация (включая право отменять только свои брони), TLS на периметре, rate limiting и квоты, ограничение размера ответов/пагинация, сетевые ACL, секреты вне compose, TLS до БД, структурированный аудит с защитой от инъекций в лог, сканирование образов/SBOM, лимиты ресурсов контейнеров. Без этого сервис остаётся корректным по TASK.md, но не готовым к открытому интернету.

### 5.5. Оговорка

Проверки были ограничены сценариями раздела 6, одним экземпляром PostgreSQL 16.15 на одном хосте и короткими нагрузочными всплесками. Не проводились фаззинг, аудит зависимостей на уровне C/ОС, тесты с TLS/аутентификацией, отказоустойчивость и длительная нагрузка. Отсутствие найденных проблем не означает доказанную безопасность.

## 7. Не выполненные проверки и причины

- **Длительная нагрузка и замеры latency/throughput.** Выполнены только короткие всплески до 400 одновременных HTTP-клиентов на 2 vCPU; целей по производительности в TASK.md нет. Результаты не позволяют судить о поведении под устойчивой нагрузкой.
- **Фаззинг HTTP-входа** (`go test -fuzz`) не запускался: не был обязателен, а ручная матрица покрывает основные классы; это не доказательство устойчивости к произвольному JSON.
- **TLS, аутентификация, авторизация, CSRF/CORS** не проверялись: в решении они не реализованы (TASK.md разрешает), поэтому проверять нечего; это условия развёртывания.
- **Сканирование уязвимостей образов/SBOM** (trivy/grype и т.п.) не выполнялось; `govulncheck` покрывает только Go-модули. Утверждать отсутствие CVE в `alpine`/`postgres` нельзя.
- **Отказоустойчивость и failure injection:** SIGKILL в середине миграции, падение БД в середине транзакции, переполнение диска, потеря сети, failover PostgreSQL — не воспроизводились; нет безопасного способа сделать это в рамках ревью без риска для чужих ресурсов.
- **Два экземпляра на разных хостах** не проверялись: оба процесса запускались на одном хосте с общей БД; это не меняет гарантии БД, но сетевые задержки/разделение сети не проверены.
- **Другие версии PostgreSQL/ARM/Windows** не проверялись: использован `postgres:16-alpine` (16.15), linux/amd64.
- **Исчерпание пула соединений** при многих зависших запросах не воспроизводилось; проверен только один заблокированный запрос и отмена по контексту.
- **Очень большие события (capacity 100000) под конкурентной нагрузкой** не проверялись; замерен одиночный `GET` (589 КБ, ~0,03 с).
- **Браузерное поведение, CORS, content sniffing** не проверялись.
- **Аудит внутренностей pgx и Go runtime** не проводился; выводы о зависимостях ограничены `govulncheck`.

Ошибки окружения (например, недоступность БД при старте) не трактовались как дефекты приложения: поведение проверялось отдельно и соответствует задуманному (30-секундное ожидание, затем ошибка).

## 8. Сильные стороны решения

- **Гарантии конкурентности на уровне БД.** Частичный уникальный индекс, уникальность `(event_id, token)` и транзакционная отмена — правильная основа для двух экземпляров; это подтверждено не только тестами, но и независимыми процессами и SQL-проверками.
- **Идемпотентность доведена до практических сценариев:** повтор после 409, повтор после отмены, одновременные одинаковые запросы, приоритет заголовка над телом.
- **Отмена действительно однократная:** повторная отмена не меняет `cancelled_at`, не освобождает места повторно и не затрагивает новую бронь на те же места.
- **Атомарность многоместной брони:** при конфликте не остаётся ни брони, ни части мест; это проверено SQL-инвариантами.
- **Миграции:** идемпотентные DDL, `schema_migrations`, advisory lock; 6 одновременных стартов на пустой БД и повторный запуск на заполненной — без ошибок и потерь.
- **Эксплуатационные мелочи:** таймауты сервера, graceful shutdown, recovery-middleware, общий 500 без утечки деталей, лимит тела, строгий JSON, непривилегированный пользователь контейнера, БД не опубликована наружу.
- **Тесты содержательные:** покрыты конкурентное бронирование, одинаковый ключ, массовые запросы, отмена, две «инстанции», миграции; есть отдельный скрипт с настоящей PostgreSQL и race detector.
- **Документация:** README подробный, с командами, примерами, принятыми решениями и ограничениями; большинство утверждений проверяемы (обнаруженные расхождения перечислены в D2–D6).
- **Малый объём зависимостей и понятный код:** `go vet`/`gofmt` чисто, `govulncheck` без известных уязвимостей Go-модулей.

### Приложение B. `probe.py` — конкурентные и функциональные проверки на двух экземплярах

Запускался после `start_servers.sh` (два процесса на портах 18081/18082, общая БД `booking_proc`). Команда: `python3 probe.py`. Результат: `failures: 0`.

```python
#!/usr/bin/env python3
"""Independent black-box checks against the running booking service.

Usage: probe.py
Both instances (18081, 18082) must share the booking_proc database.
"""
import json
import random
import sys
import threading
import time
import urllib.error
import urllib.request

BASES = ["http://127.0.0.1:18081", "http://127.0.0.1:18082"]
FAILS = []
NOTES = []


def req(base, method, path, body=None, headers=None, raw=None, timeout=20):
    data = raw
    hdrs = dict(headers or {})
    if body is not None:
        data = json.dumps(body).encode()
        hdrs["Content-Type"] = "application/json"
    r = urllib.request.Request(base + path, data=data, headers=hdrs, method=method)
    try:
        with urllib.request.urlopen(r, timeout=timeout) as resp:
            return resp.status, resp.read()
    except urllib.error.HTTPError as e:
        return e.code, e.read()


def call(method, path, body=None, headers=None, raw=None, timeout=20):
    # round robin across the two instances
    base = BASES[random.randrange(len(BASES))]
    return req(base, method, path, body, headers, raw, timeout)


def j(body):
    try:
        return json.loads(body)
    except Exception:
        return None


def check(cond, msg, detail=""):
    if cond:
        print("ok   " + msg)
    else:
        print("FAIL " + msg + (" :: " + str(detail) if detail else ""))
        FAILS.append(msg + (" :: " + str(detail) if detail else ""))


def create_event(name, capacity):
    st, raw = call("POST", "/events", {"name": name, "capacity": capacity})
    assert st == 201, (st, raw)
    return j(raw)


def parallel(fn, n):
    out = [None] * n
    barrier = threading.Barrier(n)

    def worker(i):
        barrier.wait()
        try:
            out[i] = fn(i)
        except Exception as e:  # noqa
            out[i] = ("EXC", repr(e))

    ts = [threading.Thread(target=worker, args=(i,)) for i in range(n)]
    for t in ts:
        t.start()
    for t in ts:
        t.join()
    return out


def check_no_5xx(label, results):
    bad = [r for r in results if not (isinstance(r, tuple) and isinstance(r[0], int) and r[0] < 500)]
    check(not bad, label + ": no 5xx/exception", bad[:3])


def main():
    # ---------- 1. validation ----------
    print("\n=== validation ===")
    st, raw = call("POST", "/events", {"name": "v", "capacity": 1})
    ev1 = j(raw)
    st, raw = call("POST", "/events", {"name": "", "capacity": 5})
    check(st == 400 and j(raw)["error"]["code"] == "invalid_request", "empty event name -> 400")
    st, raw = call("POST", "/events", {"name": "x", "capacity": 0})
    check(st == 400, "capacity 0 -> 400", (st, raw))
    st, raw = call("POST", "/events", {"name": "x" * 201, "capacity": 1})
    check(st == 400, "name 201 chars -> 400", (st, raw))
    st, raw = call("POST", "/events", {"name": "x", "capacity": 100001})
    check(st == 400, "capacity 100001 -> 400", (st, raw))
    st, raw = call("POST", "/events", {"name": "x", "capacity": 5, "unknown": True})
    check(st == 400, "unknown field -> 400", (st, raw))
    st, raw = call("POST", "/events", raw=b"{broken")
    check(st == 400 and j(raw) is not None, "malformed JSON -> 400 JSON error", (st, raw[:120]))
    st, raw = call("POST", "/events", raw=b"")
    check(st == 400, "empty body -> 400", (st, raw))
    st, raw = call("POST", "/bookings", {"event_id": ev1["id"], "seats": [1]})
    check(st == 400 and j(raw)["error"]["code"] == "invalid_request", "missing idempotency key -> 400")
    st, raw = call("POST", "/bookings", {"event_id": ev1["id"], "seats": [1], "idempotency_key": "k" * 129})
    check(st == 400, "token 129 chars -> 400", (st, raw[:100]))
    st, raw = call("POST", "/bookings", {"event_id": ev1["id"], "seats": list(range(1, 102)), "idempotency_key": "k101"})
    check(st == 400, "101 seats -> 400", (st, raw[:100]))
    st, raw = call("POST", "/bookings", {"event_id": ev1["id"], "seats": [1, 1], "idempotency_key": "dup"})
    check(st == 400, "duplicate seats -> 400", (st, raw[:100]))
    st, raw = call("POST", "/bookings", {"event_id": ev1["id"], "seats": [0], "idempotency_key": "zero"})
    check(st == 400, "seat 0 -> 400", (st, raw[:100]))
    st, raw = call("POST", "/bookings", {"event_id": ev1["id"], "seats": [2], "idempotency_key": "oor"})
    check(st == 400 and j(raw)["error"]["code"] == "seat_out_of_range", "seat > capacity -> 400 seat_out_of_range", (st, raw[:120]))
    st, raw = call("POST", "/bookings", {"event_id": 99999999, "seats": [1], "idempotency_key": "noev"})
    check(st == 404, "unknown event -> 404", (st, raw[:120]))
    st, raw = call("GET", "/events/0")
    check(st == 400, "id 0 -> 400", (st, raw[:120]))
    st, raw = call("GET", "/events/-1")
    check(st == 400, "id -1 -> 400", (st, raw[:120]))
    st, raw = call("GET", "/bookings/abc")
    check(st == 400, "non-numeric booking id -> 400", (st, raw[:120]))

    # body > 1 MiB
    big = b'{"name": "' + b"x" * (2 * 1024 * 1024) + b'", "capacity": 1}'
    st, raw = call("POST", "/events", raw=big, timeout=30)
    check(st == 400 and j(raw) is not None, "body > 1MiB -> 400 JSON (not 500/panic)", (st, raw[:120]))

    # wrong method (mux default; may be text/plain)
    st, raw = call("GET", "/bookings")
    NOTES.append(f"GET /bookings (method not allowed) -> {st}, content-type body: {raw[:60]!r}")

    # ---------- 2. idempotency ----------
    print("\n=== idempotency ===")
    ev = create_event("idem", 20)
    st, raw = call("POST", "/bookings", {"event_id": ev["id"], "seats": [1, 2], "idempotency_key": "K-body"})
    check(st == 201, "create K-body -> 201", (st, raw))
    b1 = j(raw)
    st, raw = call("POST", "/bookings", {"event_id": ev["id"], "seats": [1, 2], "idempotency_key": "K-body"})
    check(st == 200 and j(raw)["id"] == b1["id"], "repeat K-body -> 200 same id", (st, raw))
    # header wins over body
    st, raw = call("POST", "/bookings", {"event_id": ev["id"], "seats": [3], "idempotency_key": "ignored-body"},
                   headers={"Idempotency-Key": "K-header"})
    check(st == 201, "create with header key -> 201", (st, raw))
    bh = j(raw)
    st, raw = call("POST", "/bookings", {"event_id": ev["id"], "seats": [4], "idempotency_key": "other"},
                   headers={"Idempotency-Key": "K-header"})
    check(st == 200 and j(raw)["id"] == bh["id"] and j(raw)["seats"] == [3],
          "header key replay with other seats -> original booking", (st, raw))

    # same token, many concurrent requests, same seats
    ev2 = create_event("idem-race", 30)
    results = parallel(lambda i: call("POST", "/bookings",
                                      {"event_id": ev2["id"], "seats": [5, 6, 7],
                                       "idempotency_key": "race-token"}), 40)
    check_no_5xx("idem-race", results)
    statuses = [r[0] for r in results if isinstance(r, tuple)]
    ids = {j(r[1])["id"] for r in results if isinstance(r, tuple) and j(r[1])}
    check(sorted(set(statuses)) in ([200, 201], [200], [201]) and len(ids) == 1,
          "40 concurrent same-key requests -> one booking, only 200/201", (sorted(set(statuses)), ids))

    # same token but different seats concurrently
    ev3 = create_event("idem-diff", 30)
    def diff(i):
        return call("POST", "/bookings", {"event_id": ev3["id"], "seats": [i + 1],
                                          "idempotency_key": "diff-token"})
    results = parallel(diff, 20)
    check_no_5xx("idem-diff", results)
    ids = {j(r[1])["id"] for r in results if isinstance(r, tuple) and j(r[1])}
    check(len(ids) == 1, "20 concurrent same-key different-seats -> one booking id", ids)

    # retry after 409 must work (key not poisoned)
    ev4 = create_event("retry-after-409", 5)
    st, raw = call("POST", "/bookings", {"event_id": ev4["id"], "seats": [1], "idempotency_key": "holder"})
    holder = j(raw)
    st, raw = call("POST", "/bookings", {"event_id": ev4["id"], "seats": [1, 2], "idempotency_key": "retry-me"})
    check(st == 409, "first attempt with occupied seat -> 409", (st, raw[:150]))
    st, raw = call("POST", f"/bookings/{holder['id']}/cancel")
    check(st == 200, "cancel holder", (st, raw))
    st, raw = call("POST", "/bookings", {"event_id": ev4["id"], "seats": [1, 2], "idempotency_key": "retry-me"})
    check(st == 201, "retry same key after seat freed -> 201 (key not poisoned)", (st, raw[:200]))

    # ---------- 3. cancel ----------
    print("\n=== cancel ===")
    ev5 = create_event("cancel", 6)
    st, raw = call("POST", "/bookings", {"event_id": ev5["id"], "seats": [1, 2, 3], "idempotency_key": "c1"})
    bk = j(raw)
    results = parallel(lambda i: call("POST", f"/bookings/{bk['id']}/cancel"), 40)
    check_no_5xx("cancel-race", results)
    check(all(isinstance(r, tuple) and r[0] == 200 for r in results), "40 concurrent cancels -> all 200",
          [r[0] for r in results if isinstance(r, tuple)])
    stamps = {j(r[1]).get("cancelled_at") for r in results if isinstance(r, tuple)}
    check(len(stamps) == 1, "all cancels report one cancelled_at", stamps)
    st, raw = call("GET", f"/events/{ev5['id']}")
    check(j(raw)["available_seats"] == 6, "after concurrent cancels all 6 seats free", raw[:200])
    st, raw = call("POST", "/bookings", {"event_id": ev5["id"], "seats": [1, 2, 3], "idempotency_key": "c2"})
    check(st == 201, "seats rebookable exactly once after cancel", (st, raw[:200]))
    st, raw = call("POST", f"/bookings/{99999999}/cancel")
    check(st == 404, "cancel unknown -> 404", (st, raw[:100]))

    # cancel vs rebook race on two instances
    print("\n=== cancel vs rebook race ===")
    bad = []
    for i in range(40):
        ev = create_event(f"race{i}", 4)
        st, raw = call("POST", "/bookings", {"event_id": ev["id"], "seats": [1, 2, 3],
                                             "idempotency_key": f"r{i}"})
        b = j(raw)

        def cancel():
            return req(BASES[0], "POST", f"/bookings/{b['id']}/cancel")

        def rebook():
            return req(BASES[1], "POST", "/bookings", {"event_id": ev["id"], "seats": [2],
                                                       "idempotency_key": f"rn{i}"})

        res = parallel(lambda k: cancel() if k == 0 else rebook(), 2)
        for r in res:
            if not (isinstance(r, tuple) and r[0] in (200, 201, 409)):
                bad.append((i, r))
        st, raw = req(BASES[0], "GET", f"/events/{ev['id']}")
        detail = j(raw)
        if detail["booked_seats"] != detail["booked_seats"]:
            bad.append((i, "count"))
    check(not bad, "40 cancel/rebook races -> only 200/201/409, availability consistent", bad[:5])

    # ---------- 4. mass concurrent bookings ----------
    print("\n=== mass concurrent bookings (no oversell) ===")
    cap = 40
    ev6 = create_event("mass", cap)
    def mass(i):
        rng = random.Random(i * 7919 + 13)
        k = rng.randint(1, 4)
        seats = rng.sample(range(1, cap + 1), k)
        return call("POST", "/bookings", {"event_id": ev6["id"], "seats": seats,
                                          "idempotency_key": f"m{i}"})
    results = parallel(mass, 250)
    check_no_5xx("mass", results)
    check(all(isinstance(r, tuple) and r[0] in (201, 409) for r in results),
          "mass bookings: every response 201 or 409", [r[0] for r in results if isinstance(r, tuple)][:20])
    successes = [j(r[1]) for r in results if isinstance(r, tuple) and r[0] == 201]
    seats = []
    for b in successes:
        seats.extend(b["seats"])
    st, raw = call("GET", f"/events/{ev6['id']}")
    d = j(raw)
    check(len(seats) == len(set(seats)), "no seat appears in two successful responses",
          (len(seats), len(set(seats))))
    check(d["booked_seats"] == len(seats) <= cap, "DB booked count equals successful seat count and <= capacity",
          (d["booked_seats"], len(seats), cap))

    # ---------- 5. availability endpoint with large capacity ----------
    print("\n=== large capacity get ===")
    ev7 = create_event("big", 100000)
    t0 = time.time()
    st, raw = call("GET", f"/events/{ev7['id']}", timeout=30)
    dt = time.time() - t0
    check(st == 200 and len(j(raw)["available_seat_numbers"]) == 100000,
          f"GET event capacity 100000 returns 100000 seats in {dt:.2f}s, {len(raw)} bytes", (st, len(raw)))

    print("\n=== summary ===")
    print(f"failures: {len(FAILS)}")
    for f in FAILS:
        print(" - " + f)
    print("notes:")
    for n in NOTES:
        print(" - " + n)
    return 1 if FAILS else 0


if __name__ == "__main__":
    sys.exit(main())

```

### Приложение C. `deadlock_probe.py` и `start_servers.sh`

`deadlock_probe.py` — 400 параллельных запросов с пересекающимися наборами мест для поиска deadlock; результат: `{409: 397, 201: 3}`, неожиданных ответов нет, в PostgreSQL 0 deadlock. Команда: `python3 deadlock_probe.py`.

```python
#!/usr/bin/env python3
"""Overlap-heavy concurrency probe aimed at deadlocks between two instances."""
import json
import random
import sys
import threading
import urllib.error
import urllib.request

BASES = ["http://127.0.0.1:18081", "http://127.0.0.1:18082"]


def call(base, method, path, body=None):
    data = None
    hdrs = {}
    if body is not None:
        data = json.dumps(body).encode()
        hdrs["Content-Type"] = "application/json"
    r = urllib.request.Request(base + path, data=data, headers=hdrs, method=method)
    try:
        with urllib.request.urlopen(r, timeout=30) as resp:
            return resp.status, resp.read()
    except urllib.error.HTTPError as e:
        return e.code, e.read()


def main():
    base = BASES[0]
    st, raw = call(base, "POST", "/events", {"name": "deadlock", "capacity": 8})
    ev = json.loads(raw)
    sets = [[1, 2], [2, 3], [1, 3], [1, 2, 3], [3, 4], [4, 5], [2, 5], [1, 2, 3, 4],
            [5, 6, 7], [7, 8], [6, 8], [1], [8]]
    n = 400
    out = [None] * n
    barrier = threading.Barrier(n)

    def worker(i):
        barrier.wait()
        rng = random.Random(i)
        seats = sorted(rng.choice(sets))
        b = BASES[i % 2]
        out[i] = call(b, "POST", "/bookings", {"event_id": ev["id"], "seats": seats,
                                               "idempotency_key": f"d{i}"})

    ts = [threading.Thread(target=worker, args=(i,)) for i in range(n)]
    for t in ts:
        t.start()
    for t in ts:
        t.join()
    codes = {}
    for r in out:
        codes[r[0]] = codes.get(r[0], 0) + 1
    print("status counts:", codes)
    bad = [(i, r[0], r[1][:100]) for i, r in enumerate(out) if r[0] not in (201, 409)]
    print("unexpected:", bad[:10])
    st, raw = call(base, "GET", f"/events/{ev['id']}")
    d = json.loads(raw)
    print("booked/available:", d["booked_seats"], d["available_seats"])
    assert d["booked_seats"] <= 8
    return 0 if not bad else 1


if __name__ == "__main__":
    sys.exit(main())

```

`start_servers.sh` — запуск двух реальных процессов с общей БД (пример для окружения ревью).

#!/usr/bin/env bash
set -u
DSN='postgres://booking:booking@localhost:55433/booking_proc?sslmode=disable'
D=/tmp/opencode/booking-review
DATABASE_URL="$DSN" HTTP_ADDR=':18081' "$D/server" >"$D/a.log" 2>&1 &

DATABASE_URL="$DSN" HTTP_ADDR=':18082' "$D/server" >"$D/b.log" 2>&1 &
echo $! >"$D/b.pid"
for i in $(seq 1 100); do
  a=$(curl -s -o /dev/null -w '%{http_code}' localhost:18081/healthz || true)
  b=$(curl -s -o /dev/null -w '%{http_code}' localhost:18082/healthz || true)
  if [ "$a" = 200 ] && [ "$b" = 200 ]; then echo "both ready after ${i}00ms"; exit 0; fi
  sleep 0.1
done
echo "not ready: a=$a b=$b"; tail -5 "$D/a.log" "$D/b.log"; exit 1
