## 3. Дефекты

Приоритеты: P0 — потеря данных/перепродажа/критическая уязвимость; P1 — сломанное обязательное свойство; P2 — существенная ошибка контракта или эксплуатации при наличии обхода; P3 — малозначимое несоответствие/пограничный случай.

### P2-1. Сообщение 503 «повтор безопасен» неверно для неидемпотентного `POST /events`

**Файлы и строки**

- `internal/handler/rest/errors.go:71-74` — при истечении контекста запроса любой операции возвращается `503 service_unavailable` с текстом «the request took too long; it is safe to retry».
- `README.md:127` — таблица ошибок: `service_unavailable` 503, «База недоступна или запрос не уложился в 10 с; повтор безопасен».
- `README.md:159-161` — повтор с тем же ключом описан в контексте идемпотентности бронирования.
- `README.md:206-208` — прямо сказано: создание события неидемпотентно, повтор `POST /events` создаст второе событие.

**Условие проявления**

`POST /events` (или другой неидемпотентный запрос) превышает 10-секундный таймаут, либо клиент теряет ответ после того, как транзакция уже зафиксировалась. Сервер отвечает generic-сообщением «safe to retry», хотя для создания события безопасного повтора без дополнительного ключа нет. Для `POST /events/{id}/bookings` повтор безопасен только с тем же `Idempotency-Key`; с новым ключом это уже новое намерение.

**Последствия**

Клиент, следуя тексту ответа или таблице README, может повторить `POST /events` и создать второе событие. Это не портит вместимость и не приводит к перепродаже, но засоряет данные и может привести к неверной бизнес-трактовке. Для бронирования повтор с новым ключом аналогично создаст второе бронирование, если первое успело зафиксироваться.

**Доказательство**

На собственном стенде я удерживал таблицу событий под `ACCESS EXCLUSIVE` и отправил `POST /events`:

```bash
docker exec review-check-postgres-1 psql -U booking -d booking -c \
  "BEGIN; LOCK TABLE events IN ACCESS EXCLUSIVE MODE; SELECT pg_sleep(14); COMMIT;" &
sleep 1
curl -s -m 25 -w '\nstatus:%{http_code} time:%{time_total}\n' \
  -X POST localhost:8080/events \
  -H 'Content-Type: application/json' \
  -d '{"name":"timeout-event","starts_at":"2031-07-01T00:00:00Z","capacity":1}'
```

Фактический ответ после 9.998 с:

```json
{"error":{"code":"service_unavailable","message":"the request took too long; it is safe to retry"}}
```

После снятия блокировки повтор того же запроса дал `201` и создал событие. В этом прогоне первая вставка откатилась по таймауту, поэтому дубликата не было; но при гонке «commit успел, ответ потерян» клиент не может различить эти случаи, а сообщение прямо советует безопасный повтор. Противоречие с `README.md:207` подтверждается без гонки: один и тот же документ одновременно обещает безопасный повтор и признаёт создание события неидемпотентным.

**Направление исправления**

Сделать сообщение и документацию зависящими от операции: для `POST /events` — «создание события неидемпотентно, повтор может создать второе событие»; для `POST /events/{id}/bookings` — «повторяйте только с тем же `Idempotency-Key`». Альтернатива — добавить идемпотентность созданию событий, но это уже расширение контракта, а не обязательное требование `TASK.md`. В README строку 127 нужно согласовать со строкой 207.

### P2-2. Недоступная PostgreSQL даёт 500 `internal_error`, хотя README обещает 503 `service_unavailable`

**Файлы и строки**

- `internal/handler/rest/errors.go:75-77` — все ошибки, не распознанные как доменные/таймаутные, превращаются в `500 internal_error`.
- `README.md:127` — `service_unavailable` 503 заявлен в том числе для недоступной базы.

**Условие проявления**

PostgreSQL остановлен или недоступен по сети/имени, и `pgx` возвращает ошибку соединения (connection refused, DNS, сетевая ошибка), не являющуюся `context.DeadlineExceeded` контекста запроса. Воспроизведённый сценарий: событие создано заранее, затем PostgreSQL остановлен, затем отправлено бронирование с ключом:

```bash
EVENT_ID=<id-существующего-события>
KEY=<uuid>
docker compose -p review-check -f compose.yaml stop postgres
curl -s -o /dev/null -w 'health:%{http_code}\n' localhost:8080/healthz
# health:503
curl -s -w '\nstatus:%{http_code}\n' -X POST \
  localhost:8080/events/$EVENT_ID/bookings \
  -H 'Content-Type: application/json' -H "Idempotency-Key: $KEY" \
  -d '{"customer_name":"Retry","seats":2}'
# status:500, body: {"error":{"code":"internal_error","message":"internal server error"}}
docker compose -p review-check -f compose.yaml start postgres
sleep 3
# повтор того же запроса с тем же KEY -> 201, бронирование создано один раз
```

Фактический результат: `/healthz` вернул `503` с телом `{"error":{"code":"service_unavailable","message":"the database is unavailable"}}`, а операция — `500` с телом `{"error":{"code":"internal_error","message":"internal server error"}}`. После `docker compose start postgres` повтор с тем же `Idempotency-Key` успешно вернул `201`, `booked_seats` увеличился на 2; данные не пострадали.

**Последствия**

Клиенты и балансировщики получают разные классы ошибок для одной и той же причины: health-check говорит «сервис недоступен», API — «внутренняя ошибка». Это затрудняет retry/backoff-политики и мониторинг; 500 может восприниматься как баг приложения, а не как временная недоступность зависимости. Сохранность данных не нарушается: транзакция не начинается/откатывается, повтор безопасен при том же ключе.

**Доказательство**

Фактический вывод: `/healthz` — `503` и `{"error":{"code":"service_unavailable","message":"the database is unavailable"}}`; бронирование — `500` и `{"error":{"code":"internal_error","message":"internal server error"}}`. В логах при этом видна внутренняя причина (`failed to connect ...`), но клиенту она не раскрывается — это правильно с точки зрения безопасности, но не соответствует обещанному коду 503.

**Направление исправления**

Классифицировать ошибки соединения/пула (`*pgconn.ConnectError`, ошибки `net`, `pgconn.SafeToRetry`, класс SQLSTATE 08 и т.п.) как `503 service_unavailable`, сохранив generic-текст. Либо честно указать в README, что недоступность БД даёт 500, а 503 зарезервирован для таймаута. Второй вариант хуже для эксплуатации.

### P3-1. Нормализация пути возвращает 307 `text/html` вместо JSON-ошибки

**Файлы и строки**

- `internal/handler/rest/server.go:34-53` — `routeErrors` проверяет `mux.Handler(r)` и при непустом pattern делегирует `ServeMux`; для путей, которые `ServeMux` нормализует, он отдаёт свой redirect.
- `README.md:114` — «Все ошибки имеют вид `{"error":{"code","message","fields"?}}`».

**Условие проявления**

Запрос к пути с лишним слешем или dot-сегментом:

```bash
curl -i 'localhost:8080//events'
# 307 Temporary Redirect, text/html
curl -i -X POST 'localhost:8080//events'
# ServeMux использует 307 и для не-GET; Location: /events
```

Фактически:

```text
HTTP/1.1 307 Temporary Redirect
Content-Type: text/html; charset=utf-8
Location: /events

<a href="/events">Temporary Redirect</a>.
```

`/events/../events` и `/events/%2e%2e/events` нормализуются и обслуживаются как `/events` (200). `/events//bookings` даёт 307.

**Последствия**

Клиент, ожидающий JSON-ошибку, получает HTML-редирект. Для `POST` это 307 с сохранением метода и тела: клиент, следующий редиректу, выполнит операцию по нормализованному пути один раз; дубликата из-за редиректа нет. Это не нарушает обязательные свойства задачи, но противоречит широкому утверждению README и усложняет интеграцию. XSS/инъекций в redirect не обнаружено: `Location`/HTML формируются `net/http` с экранированием.

**Направление исправления**

Перехватывать 3xx от `ServeMux` в `routeErrors` и отдавать JSON-ошибку/явно документировать redirect, либо использовать роутер без автоматической нормализации. Если redirect оставлен намеренно, README должен исключать его из утверждения «все ошибки JSON».

### P3-2. Дубликаты ключей JSON принимаются; побеждает последнее значение

**Файлы и строки**

- `internal/handler/rest/decode.go:28-31` — используется стандартный `json.Decoder` с `DisallowUnknownFields`; дубликаты им не проверяются.
- `README.md:182-183` — заявлен «строгий разбор»: неизвестные поля и данные после значения отклоняются.

**Условие проявления**

```bash
curl -s -X POST localhost:8080/events \
  -H 'Content-Type: application/json' \
  -d '{"name":"first","name":"second","starts_at":"2031-01-01T00:00:00Z","capacity":2}'
```

Фактический ответ — `201`, в созданном событии `"name":"second"`. Аналогично дубликат `capacity`/`seats` даст последнее значение.

**Последствия**

Входные данные неоднозначны: разные парсеры/прокси могут выбрать разные значения. В текущем compose нет промежуточного парсера, поэтому подтверждённой уязвимости нет; это robustness/parser-differential риск. `TASK.md` не требует отклонять дубликаты, а README прямо перечисляет только неизвестные поля и trailing data, поэтому формально это не нарушение обязательного свойства; но заявление «строгий разбор» выглядит шире фактического поведения.

**Направление исправления**

Либо отклонять повторяющиеся имена (token-level обход или собственная проверка), либо явно указать в README, что дубликаты разрешены и обрабатываются по правилу «последнее значение».

### P3-3. `starts_at = 0001-01-01T00:00:00Z` отклоняется как «is required», хотя README разрешает год 1

**Файлы и строки**

- `internal/service/event/service.go:38-43` — проверка `cmd.StartsAt.IsZero()` стоит перед проверкой диапазона года.
- `README.md:196` — допущение: `starts_at` — RFC 3339 с годом от 1 до 9999 в UTC.

**Условие проявления**

`time.Time` для `0001-01-01T00:00:00Z` равен нулевому `time.Time`, поэтому `IsZero()` истинно:

```bash
curl -s -w '\nstatus:%{http_code}\n' -X POST localhost:8080/events \
  -H 'Content-Type: application/json' \
  -d '{"name":"year1","starts_at":"0001-01-01T00:00:00Z","capacity":1}'
# 400 validation_failed: starts_at is required

curl -s -w '\nstatus:%{http_code}\n' -X POST localhost:8080/events \
  -H 'Content-Type: application/json' \
  -d '{"name":"year1","starts_at":"0001-01-01T00:00:00.001Z","capacity":1}'
# 201
```

**Последствия**

Очень узкий, но документированный граничный случай отвергается с неверным сообщением. Сохранность данных не страдает; практическое влияние минимально. `TASK.md` не требует конкретного диапазона лет.

**Направление исправления**

Различать отсутствие поля и явное значение, например через `*time.Time` или отдельный флаг наличия в DTO, и не использовать нулевое значение как признак отсутствия. Либо явно исключить `0001-01-01T00:00:00Z` из README.

## 4. Архитектура

### Соразмерность и разделение ответственности

Решение соразмерно небольшой задаче. Собственный код — около 1,8 тыс. строк (без сгенерированных `server.gen.go` и моков); слои разделены предсказуемо:

- `internal/handler/rest` — HTTP-адаптер, разбор JSON, коды ошибок, middleware;
- `internal/service/event`, `internal/service/booking` — валидация, нормализация и бизнес-правила;
- `internal/repository/postgres` — SQL, транзакции, блокировки, миграции;
- `internal/model` — сущности, команды, запросы, ошибки, пагинация, валидация;
- `internal/app` — composition root: пул, миграции, сервисы, HTTP-сервер;
- `cmd/booking` — чтение окружения, сигналы, запуск.

Конкретные примеры:

- HTTP-слой не знает SQL: `handler.go` формирует `eventmodel.CreateServiceCommand`/`bookingmodel.CreateServiceCommand` и вызывает интерфейсы из `dependency.go`.
- Бизнес-инварианты вместимости находятся там, где их можно выполнить атомарно: проверка остатка и обновление `booked_seats` — в одной транзакции `internal/repository/postgres/booking.go:30-79`; дополнительная защита — `CHECK (booked_seats BETWEEN 0 AND capacity)` в `internal/repository/postgres/migrations/0001_init.sql:9-11`.
- Границы транзакций совпадают с границами бизнес-операций: создание бронирования — один `pgx.BeginFunc` (`booking.go:27-82`), отмена — один `pgx.BeginFunc` (`booking.go:164-186`), миграция — одна транзакция (`migrate.go:28-58`). Это правильный выбор для задачи: сервис не пытается координировать транзакции между репозиториями.
- Идемпотентность также размещена в БД, а не в памяти: `UNIQUE (idempotency_key)` (`0001_init.sql:26`), `replayBooking` (`booking.go:93-109`), разбор конфликта при `INSERT ... ON CONFLICT` (`booking.go:54-74`). В памяти общего состояния нет, поэтому два экземпляра работают корректно.
- Направление зависимостей: `handler -> service -> repository -> model`; интерфейсы объявлены на стороне потребителя (`internal/handler/rest/dependency.go`, `internal/service/*/dependency.go`), а конкретные типы собираются в `internal/app/app.go:61-67`. Циклов и скрытого глобального состояния нет.
- `internal/model/page` и `internal/model/validation` — небольшие общие модели без зависимости от транспорта/БД.

### Тестируемость и стоимость изменений

Тестируемость хорошая: сервисы зависят от узких интерфейсов, для них есть моки; репозиторий проверяется на настоящей PostgreSQL; e2e поднимает настоящий бинарник. Добавление нового эндпоинта потребует OpenAPI + `go generate` + handler/service/repository + тесты; это нормальная стоимость для контрактного API и она описана в README.

Небольшой дубль — ручной разбор JSON при наличии сгенерированных DTO; он оправдан требованием строгих ошибок (`decode.go:18-45`). Генерация кода (`internal/handler/rest/gen`) и отдельные `event`/`booking` сервисы добавляют boilerplate, но не выглядят избыточной архитектурой для тестируемого HTTP-сервиса с двумя сущностями.

### Компромиссы и места, которые стоит осознавать

- Денормализованный `events.booked_seats` и блокировка строки события сериализуют все бронирования одного события (`booking.go:30-32`). Это осознанный компромисс, описанный в README; для популярного события throughput ограничен. `CHECK` защищает от перепродажи/отрицательного остатка, но не доказывает равенство счётчика сумме подтверждённых броней; это обеспечивается кодом и тестами, а не триггером/реконсиляцией. Для небольшой задачи приемлемо, для эксплуатации стоит добавить периодическую проверку/метрику расхождения.
- Идемпотентный ключ хранится в самой строке бронирования, поэтому глобален и живёт столько же, сколько бронирование. Это просто и описано в README; цена — невозможность переиспользовать ключ после отмены и глобальные коллизии между клиентами.
- `routeErrors` (`server.go:34-53`) добавляет собственную обработку 404/405 ради JSON; она работает для обычных путей, но имеет описанный выше redirect-пробел. Это локальная сложность, а не архитектурный дефект.
- Классификация ошибок в `writeError` (`errors.go:48-78`) централизована и удобна, но неполна: ошибки недоступности БД попадают в `default` (P2-2), а generic-текст таймаута не учитывает идемпотентность операции (P2-1).
- Наблюдаемость ограничена структурными логами; метрик/трассировки нет, что README честно указывает. Для production это осознанное упрощение, а не ошибка выполнения задачи.

Архитектура не требует «правильного» числа слоёв или конкретной библиотеки; в текущем виде она понятна, тестируема и допускает локальные изменения. Блокирующих архитектурных замечаний нет.

## 5. Безопасность

### Модель угроз и границы доверия

Предполагаемая модель — публичный HTTP API без аутентификации (это прямо разрешено `TASK.md`), без браузерного UI и без cookies. Клиент может читать и отменять любое бронирование по UUID; `Idempotency-Key` глобален. PostgreSQL находится во внутренней Docker-сети; в `compose.yaml` у сервиса `postgres` нет `ports`, то есть наружу опубликован только HTTP-порт приложения. Это подтверждено `docker port`: у `review-check-postgres-1` публикаций нет, у приложений — 8080/8081.

Для публичной эксплуатации потребуются аутентификация/авторизация, TLS на HTTP и, желательно, на соединении с БД, rate limiting/квоты, управление секретами и резервное копирование. Это условия развёртывания, а не дефекты выполнения `TASK.md`, где авторизация явно не требуется.

### SQL-инъекции и недоверенный SQL

Все пользовательские значения передаются в pgx параметрами: `WHERE id = $1`, `INSERT ... VALUES ($1,$2,$3,$4)`, `LIMIT $2 OFFSET $3`, `UPDATE ... + $2`. Динамически собираются только статические списки колонок (`bookingColumns`, `eventColumns`) и статические `ORDER BY`; пользовательских фрагментов SQL нет. Миграции — встроенные статические файлы. Я отдельно отправил в `name`, `customer_name` и `Idempotency-Key` payload'ы вида `x'; DROP TABLE bookings;--`: они сохранились как обычные строки, таблицы и количество строк не изменились.

### Недоверенный JSON и ограничения входа

- Тело JSON ограничено 1 МиБ через `http.MaxBytesReader` (`decode.go:14,28`); запрос > 1 МиБ получил `413 payload_too_large`.
- Включён `DisallowUnknownFields`; лишние поля и данные после JSON-значения отклоняются (`decode.go:29-42`).
- Пустое тело, неверные типы, неверные timestamps, отрицательные/нулевые `seats`/`capacity`, слишком длинный `Idempotency-Key` (сервис, 255 байт) и неверные UUID дают 400/413/415 без записи данных.
- Строки `name`/`customer_name` ограничены 200 символами после trim и проверяются на управляющие символы (`validation.go:57-71`); NUL отклоняется.
- Пагинация ограничена: `limit` 1..200, `offset >= 0` (`page.go:12-17,41-57`).
- Дубликаты ключей JSON не отклоняются (P3-2); это не создаёт подтверждённой уязвимости в текущем окружении, но является parser-differential риском при появлении прокси/другого парсера.
- `HEAD`/`OPTIONS` обрабатываются стандартным `net/http`; `OPTIONS` даёт JSON 405 с `Allow`, лишние методы не исполняются.
- Пути с двойным слешем дают 307 HTML (P3-1), но не открывают файловую систему и не дают открытого редиректа: `Location` относительный, HTML экранируется.

### Таймауты, исчерпание ресурсов и отказоустойчивость

- На каждый запрос ставится контекст 10 с (`app.go:28`, `server.go:56-63`), он передаётся в pgx; при удержании блокировки запрос завершился `503` через 10.0 с, а не завис навсегда.
- `ReadHeaderTimeout=5s`, `ReadTimeout=15s`, `WriteTimeout=20s`, `IdleTimeout=60s` (`app.go:29-32`), что ограничивает slowloris и медленные тела.
- Пул pgx по умолчанию, параметр `pool_max_conns` можно задать через `DATABASE_URL`; README это описывает. При исчерпании пула запросы ждут и упираются в 10-секундный таймаут; для одного горячего события это документированный предел.
- Нет rate limiting, квот на число событий/бронирований и ограничения на общий объём БД. При публичной эксплуатации это риск DoS/исчерпания диска, но `TASK.md` таких требований не содержит; это condition of deployment.
- Нет отдельного `statement_timeout`/`lock_timeout` в PostgreSQL, но контекст запроса отменяет ожидание; соединение при неудачном rollback закрывается pgx, утечки транзакций не обнаружено. Дополнительный `RETRY` на сериализационные ошибки не нужен: используется Read Committed и блокировка строки.

### Утечки ошибок, секретов и логирование

- Ответ по умолчанию на внутреннюю ошибку — generic `{"error":{"code":"internal_error","message":"internal server error"}}`; детали пишутся только в лог (`errors.go:75-77`). Тест `TestServer_ServiceErrorsMapToResponses` проверяет отсутствие `secret` в теле.
- Логи содержат метод, route-pattern, статус и длительность, но не тело, не заголовки, не query и не `Idempotency-Key`; я проверил `docker logs` после запросов с ключами/именами — значений ключей и имён клиентов там нет.
- Ошибка соединения с БД в логе содержит `user=booking database=booking` и причину, но не пароль. При заведомо некорректном `DATABASE_URL` pgx замаскировал пароль (`user:xxxxx`), что я проверил отдельным запуском.
- Ошибки SQL/БД не возвращаются клиенту; constraint names и детали видны только в логах.
- Нет request-id/remote IP в логах; это ограничивает расследование инцидентов, но не является ошибкой безопасности.

### Контейнеры, секреты и порты

- `Dockerfile` собирает статический бинарник и запускает его от непривилегированного `uid=10001` (`Dockerfile:10-16`); проверено `docker exec ... id`.
- В runtime-образ копируется только бинарник, исходники и тесты не попадают; `.dockerignore` исключает `*`, оставляя только `go.mod`, `go.sum`, `cmd`, `internal`, и исключает `*_test.go`/`mocks`.
- PostgreSQL наружу не опубликован; приложение опубликовано на 0.0.0.0:8080/8081 — это нормально для локального compose, но для production нужен сетевой периметр.
- В `compose.yaml` учебный пароль `booking:booking` и `sslmode=disable`; README честно называет это ограничением. Это не production-секрет, но при развёртывании должно быть заменено.
- Нет `cap_drop`, `read_only`, `no-new-privileges` и лимитов ресурсов; это необязательные меры hardening, а не дефект задачи.
- Образы закреплены тегами (`postgres:18.1-alpine`, `golang:1.27.3-alpine`), но не digest; от проверки known vulnerabilities базовых образов я воздержусь, так как image scan не выполнялся.

### Идемпотентность как граница доверия

`Idempotency-Key` глобален и не привязан к клиенту. При отсутствии авторизации (разрешено) это означает: кто знает/угадал ключ и совпадающие параметры, получит чужое бронирование при повторе; ключ с другими параметрами даст 422 и может помешать легитимному повтору. README предупреждает об этом и советует UUID. Это осознанный компромисс, а не скрытая уязвимость; для production ключ стоит привязывать к аутентифицированному клиенту/тенанту.

### Итог по безопасности

Подтверждённых критических или высоких уязвимостей в проверенном объёме я не нашёл: SQL-инъекций нет, недоверенный JSON ограничен и не приводит к панике или записи в обход валидации, внутренние ошибки не утекают клиенту, секреты не логируются, приложение работает не от root, порт БД не опубликован. Это не доказательство отсутствия всех уязвимостей: не выполнялись image scan, TLS/auth-тесты, fuzzing и проверка production-настроек БД. Основные риски относятся к публичной эксплуатации без auth/TLS/rate limiting и к глобальным ключам идемпотентности.

`golang.org/x/vuln/cmd/govulncheck@latest` (v1.9.0) по `./...` сообщил `No vulnerabilities found.`; это проверка известных уязвимостей в достижимом Go-коде, а не гарантия для базовых образов и всех сценариев эксплуатации.

## 6. Неподтверждённые риски и необязательные рекомендации

Ниже — не подтверждённые дефекты, а риски/улучшения, которые я не смог или не считал нужным воспроизводить в рамках задачи.

1. **Нет аутентификации/авторизации.** Прямо разрешено `TASK.md`; для публичной эксплуатации нужны authn/authz, TLS, сетевые политики, rate limiting и квоты. Без них любой клиент может читать/отменять бронирования по UUID.
2. **Глобальный `Idempotency-Key`.** Возможны межклиентские коллизии/помехи и получение чужого бронирования при знании ключа. README это признаёт; для production — привязка к клиенту/тенанту и/или отдельная таблица идемпотентности с TTL.
3. **Слабые секреты и отсутствие TLS для БД.** `booking:booking` и `sslmode=disable` предназначены для локального compose; для production нужны секрет-менеджмент и TLS.
4. **Нет rate limiting/квот.** Возможны исчерпание соединений/диска, разрастание `bookings` и `events`; не проверялось нагрузочно. Это deployment-риск, а не нарушение `TASK.md`.
5. **Одно горячее событие сериализуется блокировкой строки.** README это описывает; при высокой нагрузке запросы упираются в 10-секундный таймаут и получают 503. Мои проверки были 100/160/600 конкурентных операций, не длительный soak/benchmark.
6. **Счётчик `booked_seats` не имеет DB-триггера/реконсиляции.** `CHECK` защищает только диапазон; равенство сумме подтверждённых броней обеспечивается кодом и тестами. При будущих изменениях или прямых правках БД возможен дрейф; стоит добавить периодическую проверку/метрику.
7. **`compose.yaml` не задаёт `stop_grace_period`.** Docker по умолчанию даёт 10 с, а `app.shutdownTimeout` — 15 с (`app.go:26`). При `docker compose down` под нагрузкой возможен SIGKILL до завершения graceful shutdown; транзакции БД атомарны, идемпотентный повтор спасает, но in-flight запросы могут быть потеряны. Рекомендую `stop_grace_period: 20s` или согласовать таймауты. Это не проверялось под нагрузкой и не является нарушением обязательных свойств.
8. **Наблюдаемость.** Нет метрик, трассировки, request-id, remote IP; логи содержат duration в наносекундах. README честно указывает отсутствие метрик/трассировки; для production стоит добавить.
9. **Pagination по offset.** Большие offset могут быть медленными, страницы могут сдвигаться при вставках; README это признаёт. Для больших объёмов — keyset pagination.
10. **Дубликаты ключей JSON и path-redirect.** Уже описаны как P3; это не подтверждённые уязвимости, а вопросы строгости/совместимости.
11. **Безопасность заголовков.** Нет `X-Content-Type-Options`, `Cache-Control`, security headers; для JSON API это необязательно, но полезно при появлении браузерных клиентов.
12. **Сканирование образов и supply chain.** Выполнен только `govulncheck` для Go-кода; Trivy/Grype/SBOM/подпись образов не выполнялись. Нельзя утверждать, что в базовых образах нет известных уязвимостей.
13. **Многоархитектурность/матрица версий.** Проверка выполнена на linux/amd64, Go 1.27.3, PostgreSQL 18.1; другие ОС/архитектуры/версии не проверялись.
14. **Отсутствие миграций назад и TTL ключей идемпотентности.** Осознанные ограничения README, не дефекты, но их нужно учитывать при эксплуатации.

### Точечные проверки ошибок/границ

- `POST /events` с `//events`/`/events//bookings` → 307 `text/html` (P3-1).

- Остановка PostgreSQL: `/healthz` → 503 `service_unavailable`, `POST /bookings` → 500 `internal_error`; после старта повтор с тем же ключом → 201, данные корректны (P2-2).
- Удержание `ACCESS EXCLUSIVE` на `events`: `POST /events` → 503 с сообщением «safe to retry» через 9.998 с; после снятия блокировки повтор → 201 (P2-1).

- Логи после запросов: нет `Idempotency-Key`, `customer_name`, пароля; ошибка соединения содержит только `user=booking database=booking`; некорректный DSN замаскирован (`user:xxxxx`).

## 8. Невыполненные проверки и ограничения

- Не выполнялся длительный soak/нагрузочный тест и бенчмарк; проверены 100–600 конкурентных операций, этого достаточно для проверки инвариантов, но не для оценки производительности на production-нагрузке.
- Не проверялись crash/power-loss самой PostgreSQL, репликация, failover и длительная недоступность БД. Штатная остановка и запуск контейнера PostgreSQL для проверки ошибок выполнялись; приложение перезапускалось, проект проверяет `SIGKILL` процесса.
- Не проверялись TLS, аутентификация, авторизация и rate limiting, потому что они отсутствуют по условию задачи. Это условия публичной эксплуатации, а не подтверждённые дефекты.
- Не выполнялся scan базовых Docker-образов (Trivy/Grype/SBOM/подпись); `govulncheck` проверяет только Go-код и его достижимые зависимости.
- Не проверялись другие ОС/архитектуры, Go-версии и версии PostgreSQL; стенд — linux/amd64, Go 1.27.3, PostgreSQL 18.1.
- Не выполнялось fuzzing/property-based тестирование JSON/HTTP и длительный chaos-тест; независимый стресс проверяет только выбранные инварианты.
- Не проверялись кастомные `APP_PORT`/`APP2_PORT`, огромные заголовки, HTTP/2, прокси/балансировщик, поведение за reverse proxy.
- Не проверялась миграция с намеренно сломанным/частично применённым файлом в отдельном эксперименте; проектный тест проверяет изменение checksum.
- `go test -race ./...` без Docker не запускался; ожидаемо integration/e2e завершатся ошибкой, как и написано в README. Short-набор без Docker проверен.
- Ошибки окружения не выдавались за ошибки приложения: все отказы выше были воспроизведены на управляемом стенде, либо помечены как condition of deployment/непроверенный риск.

## 9. Сильные стороны решения

1. **Корректная конкурентная модель.** Блокировка строки события, проверка остатка и изменение счётчика в одной транзакции; `CHECK` как последняя линия защиты. Подтверждено тестами и независимыми стрессами.
2. **Продуманная идемпотентность.** Глобальный `UNIQUE`-ключ, replay под блокировкой события, отдельный разбор конфликта ключа для разных событий, сохранение ключа только успешным бронированием, документированное поведение после отмены.
3. **Корректная отмена.** Условный `UPDATE` с `status='confirmed'`, возврат мест в той же транзакции; повторные/одновременные отмены не делают двойной возврат и сохраняют `cancelled_at`.
4. **Реальная проверка двух экземпляров.** Не только unit-моки: Testcontainers/PostgreSQL, настоящий бинарник, два процесса, конкурентные HTTP-запросы, перезапуск после `SIGKILL`.
5. **Аккуратная схема и миграции.** Транзакционные встроенные миграции, advisory lock, checksum, индексы, constraints; повторный запуск и конкурентный старт безопасны.
6. **Понятная слоистая структура.** Направление зависимостей, composition root, узкие интерфейсы, отдельные модели, читаемые ошибки; тестируемость заметно выше среднего для задачи такого размера.
7. **Хорошая защита входа.** Строгий JSON, лимит тела, проверки типов/строк/timestamps, понятные коды ошибок, отсутствие утечки внутренних ошибок и секретов в ответах/логах.
8. **Разумная эксплуатационная база.** Таймауты, graceful shutdown, health-check, non-root контейнер, отсутствие публикации PostgreSQL, воспроизводимая генерация и фиксация зависимостей.
9. **Честная документация.** README подробно описывает решения, компромиссы и ограничения; большая часть утверждений подтверждена кодом и проверками (исключения — P2/P3 выше).

## Приложение A. Временный воспроизводящий тест

В проект временные тесты не добавлялись. Скрипт ниже лежит вне проекта (`/tmp/opencode/review-check/repro.go`) и использовался против двух собственных экземпляров. Команда:

```bash
cd /tmp/opencode/review-check
go mod init reviewprobe          # один раз
go get github.com/google/uuid@v1.6.0
go run repro.go
```

Ожидаемый вывод при работающих экземплярах на 8080/8081 и общей БД:

```text
1 ok: 15 created, 85 conflict, booked=30
2 ok: one booking id, one 201
3 ok: seats returned once
```

```go
// Standalone review probe. Run against two instances of the service:
//   go run repro.go
// It expects http://127.0.0.1:8080 and :8081 to share one PostgreSQL.
package main

import (
	"bytes"
	"encoding/json"
	"fmt"
	"io"
	"net/http"
	"os"
	"sync"
	"time"

	"github.com/google/uuid"
)

var bases = []string{"http://127.0.0.1:8080", "http://127.0.0.1:8081"}
var client = &http.Client{Timeout: 30 * time.Second}

type event struct {
	ID          uuid.UUID `json:"id"`
	Capacity    int       `json:"capacity"`
	BookedSeats int       `json:"booked_seats"`
}
type booking struct {
	ID     uuid.UUID `json:"id"`
	Seats  int       `json:"seats"`
	Status string    `json:"status"`
}
type page struct {
	Items   []booking `json:"items"`
	HasMore bool      `json:"has_more"`
}

func fail(format string, args ...any) {
	fmt.Printf("FAIL: "+format+"\n", args...)
	os.Exit(1)
}

func call(method, url string, headers map[string]string, body []byte) (int, http.Header, []byte) {
	var reader io.Reader
	if body != nil {
		reader = bytes.NewReader(body)
	}
	req, err := http.NewRequest(method, url, reader)
	if err != nil {
		panic(err)
	}
	if body != nil {
		req.Header.Set("Content-Type", "application/json")
	}
	for k, v := range headers {
		req.Header.Set(k, v)
	}
	resp, err := client.Do(req)
	if err != nil {
		panic(err)
	}
	defer resp.Body.Close()
	data, err := io.ReadAll(resp.Body)
	if err != nil {
		panic(err)
	}
	return resp.StatusCode, resp.Header, data
}

func createEvent(capacity int) event {
	body, _ := json.Marshal(map[string]any{"name": "repro", "starts_at": "2031-01-01T00:00:00Z", "capacity": capacity})
	status, _, data := call("POST", bases[0]+"/events", nil, body)
	if status != 201 {
		fail("create event: %d %s", status, data)
	}
	var e event
	if err := json.Unmarshal(data, &e); err != nil {
		panic(err)
	}
	return e
}

func book(base string, eventID uuid.UUID, key string, seats int) (int, booking) {
	body, _ := json.Marshal(map[string]any{"customer_name": "Anna", "seats": seats})
	status, _, data := call("POST", base+"/events/"+eventID.String()+"/bookings",
		map[string]string{"Idempotency-Key": key}, body)
	var b booking
	if status == 200 || status == 201 {
		if err := json.Unmarshal(data, &b); err != nil {
			panic(err)
		}
	}
	return status, b
}

func list(eventID uuid.UUID) []booking {
	var all []booking
	for {
		status, _, data := call("GET", fmt.Sprintf("%s/events/%s/bookings?limit=200&offset=%d", bases[0], eventID, len(all)), nil, nil)
		if status != 200 {
			fail("list: %d %s", status, data)
		}
		var p page
		if err := json.Unmarshal(data, &p); err != nil {
			panic(err)
		}
		all = append(all, p.Items...)
		if !p.HasMore {
			return all
		}
	}
}

func fetch(eventID uuid.UUID) event {
	status, _, data := call("GET", bases[1]+"/events/"+eventID.String(), nil, nil)
	if status != 200 {
		fail("fetch: %d %s", status, data)
	}
	var e event
	if err := json.Unmarshal(data, &e); err != nil {
		panic(err)
	}
	return e
}

func invariant(eventID uuid.UUID) {
	current := fetch(eventID)
	sum := 0
	for _, b := range list(eventID) {
		if b.Status == "confirmed" {
			sum += b.Seats
		}
	}
	if current.BookedSeats != sum || current.BookedSeats > current.Capacity {
		fail("booked=%d sum(confirmed)=%d capacity=%d", current.BookedSeats, sum, current.Capacity)
	}
}

func main() {
	// 1. 100 concurrent requests for 2 seats against capacity 30.
	e := createEvent(30)
	statuses := make([]int, 100)
	var wg sync.WaitGroup
	start := make(chan struct{})
	for i := range statuses {
		wg.Add(1)
		go func(i int) {
			defer wg.Done()
			<-start
			statuses[i], _ = book(bases[i%2], e.ID, uuid.NewString(), 2)
		}(i)
	}
	close(start)
	wg.Wait()
	created, refused := 0, 0
	for _, status := range statuses {
		switch status {
		case 201:
			created++
		case 409:
			refused++
		default:
			fail("unexpected status %d", status)
		}
	}
	if created != 15 || refused != 85 {
		fail("created=%d refused=%d", created, refused)
	}
	invariant(e.ID)
	fmt.Println("1 ok: 15 created, 85 conflict, booked=30")

	// 2. 40 concurrent requests with one key and 4 seats.
	e = createEvent(10)
	key := uuid.NewString()
	answers := make([]booking, 40)
	statuses = make([]int, 40)
	start = make(chan struct{})
	for i := range statuses {
		wg.Add(1)
		go func(i int) {
			defer wg.Done()
			<-start
			statuses[i], answers[i] = book(bases[i%2], e.ID, key, 4)
		}(i)
	}
	close(start)
	wg.Wait()
	created = 0
	ids := map[uuid.UUID]bool{}
	for i, status := range statuses {
		if status == 201 {
			created++
		} else if status != 200 {
			fail("same-key status %d", status)
		}
		ids[answers[i].ID] = true
	}
	if created != 1 || len(ids) != 1 {
		fail("same-key created=%d ids=%d", created, len(ids))
	}
	invariant(e.ID)
	fmt.Println("2 ok: one booking id, one 201")

	// 3. 40 concurrent cancellations of one booking.
	e = createEvent(10)
	_, keep := book(bases[0], e.ID, uuid.NewString(), 4)
	_, victim := book(bases[0], e.ID, uuid.NewString(), 3)
	start = make(chan struct{})
	for i := range statuses {
		wg.Add(1)
		go func(i int) {
			defer wg.Done()
			<-start
			statuses[i], _, _ = call("POST", bases[i%2]+"/bookings/"+victim.ID.String()+"/cancel", nil, nil)
		}(i)
	}
	close(start)
	wg.Wait()
	for i, status := range statuses {
		if status != 200 {
			fail("cancel %d status %d", i, status)
		}
	}
	current := fetch(e.ID)
	if current.BookedSeats != keep.Seats {
		fail("cancel refunded wrong: booked=%d want %d", current.BookedSeats, keep.Seats)
	}
	invariant(e.ID)
	fmt.Println("3 ok: seats returned once")
}
```

Команды для P2-1/P2-2 и P3 приведены в соответствующих разделах выше; они используют только собственные контейнеры `review-check-*` и собственную тестовую БД.
