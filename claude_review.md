# Независимое техническое ревью: сервис бронирования мест

Проверен коммит `53aabc1`. Дата проверки: 2026-11-07. Исходники, тесты, зависимости, `TASK.md` и `README.md` не менялись; этот файл единственный добавленный.

## 1. Заключение

**Решение соответствует `TASK.md` частично.** Главные гарантии выдержаны: перепродажи нет, дубликатов нет, места при отмене возвращаются ровно один раз, данные сохраняются, два экземпляра работают согласованно. Это подтверждено на настоящей PostgreSQL, в том числе при `kill -9` приложения и базы под нагрузкой.

Есть **два нарушения требований приоритета P1**:

- **D1. Повтор на последних местах.** Одновременный повтор запроса с тем же ключом получает ложный отказ `409 not_enough_seats`, хотя бронирование создано. Механизм безопасного повтора в этом случае даёт неверный ответ.
- **D2. Граничный год в `starts_at`.** Один принятый запрос навсегда превращает `GET /events` в ответ `200` с пустым телом. Восстановление возможно только через SQL.

Дефектов P0 (перепродажа, потеря или порча подтверждённых данных) не найдено. Оба дефекта P1 исправляются локально, без смены архитектуры.

## 2. Подтверждённые дефекты

Шкала приоритетов:

- **P0:** нарушена гарантия сохранности или ёмкости.
- **P1:** нарушено требование `TASK.md` с серьёзным последствием.
- **P2:** реальный дефект с ограниченным последствием или обходным путём.

### D1 (P1). Одновременный повтор на заполненном событии получает ложный `not_enough_seats`

- **Где:** `internal/store/store.go:202-211` (поиск ключа до блокировки), `:217-245` (ветка «строка не обновлена» не проверяет ключ повторно). Противоречит `README.md:255-257`.
- **Условие:** два запроса с одним ключом и телом выполняются одновременно, и первый занимает столько мест, что второму их уже не хватает. Оба не находят ключ, второй ждёт блокировку строки события. После коммита первого условие `reserved_seats + $2 <= capacity` пересчитывается и не выполняется, а до `INSERT` и обработки `23505` дело не доходит.
- **Последствия:** клиент получает окончательный по смыслу отказ, хотя его бронирование подтверждено и места заняты. Если он поверит отказу и не повторит запрос, места останутся занятыми бессрочно. Дубликата и перепродажи нет. Именно для такой ситуации (таймаут и повтор на последних местах) и нужен механизм повтора.
- **Доказательство:**
  - Детерминированный тест `TestReview_ConcurrentRetryOnLastSeatsIsReplay` (приложение A) падал 5 из 5 раз: статусы `201` и `409` при одном бронировании в базе.
  - Два настоящих контейнера, ёмкость 2, 2 места, 8 параллельных запросов, 20 раундов (приложение C): `201=20, 200=74, 409=66`, ложный отказ в 18 раундах из 20, нарушений инвариантов 0.
  - Последовательный повтор на заполненном событии работает верно (`TestReview_SequentialReplayOnFullEvent`, 5 из 5).
- **Направление:** в ветке `pgx.ErrNoRows` до формирования `NotEnoughSeatsError` повторить поиск по ключу в той же транзакции. В READ COMMITTED новый оператор видит зафиксированную строку победителя. Вернуть повтор или `ErrIdempotencyConflict`. Добавить тест на эту гонку.

### D2 (P1). `starts_at` на границе года навсегда ломает `GET /events`

- **Где:** `internal/api/validation.go:67-71` (принимается значение, которое после приведения к UTC выходит за год 9999 или до года 0), `internal/api/errors.go:88-93` (заголовок отправлен до кодирования, ошибка `Encode` отброшена), `internal/api/handlers.go:52,61,75`.
- **Условие:** один запрос без авторизации, например `{"name":"x","capacity":1,"starts_at":"9999-12-31T23:59:59-23:59"}` или `"0000-01-01T00:00:00+00:01"`. `time.Time.MarshalJSON` отказывает для лет вне диапазона [0, 9999].
- **Последствия:**
  - Событие сохраняется, а `POST` отвечает `201` с `Content-Length: 0`, то есть клиент не получает тела.
  - `GET /events` отвечает `200` с пустым телом для всех клиентов, пока запись существует; рестарт не помогает.
  - API не умеет удалять события, поэтому восстановление возможно только через SQL.
  - В логах только `status:200, bytes:0`, строк уровня ERROR 0, то есть сбой незаметен для мониторинга.
  - `GET /events/{id}` для этого события тоже пуст. Остальные события и бронирование работают.
- **Доказательство:**

  ```bash
  curl -si -X POST localhost:8080/events -H 'Content-Type: application/json' \
    -d '{"name":"x","capacity":1,"starts_at":"9999-12-31T23:59:59-23:59"}' | head -6
  # HTTP/1.1 201 Created ... Content-Length: 0
  curl -s -o /dev/null -w '%{http_code} %{size_download}\n' localhost:8080/events
  # 200 0   (до запроса: 200 202)
  ```

  В базе: `10000-01-01 23:58:59+00`. Тест `TestReview_StartsAtOutsideJSONYearRange` падал 5 из 5 раз.
- **Направление:** ограничить диапазон при валидации с запасом на часовой пояс сервера, например разумным интервалом лет. Значения с сервера возвращаются в локальной зоне процесса. В `writeJSON` сначала кодировать в буфер, затем отправлять заголовок, а при ошибке логировать и отвечать 500. Отдельно решить, что делать с уже сохранёнными значениями.

### D3 (P2). NUL в строковых полях даёт 500 вместо ошибки валидации

- **Где:** `internal/api/validation.go:49,84` (нет проверки), затем `internal/api/errors.go:78-84`.
- **Условие:** корректный JSON с `\u0000` в `name` или `customer_name`.
- **Последствия:** клиент получает `500 internal_error` вместо понятной ошибки, что противоречит `TASK.md`. Ошибка клиента пишется в лог как ERROR и загрязняет сигнал мониторинга. Данные не меняются: транзакция откатывается, доступность прежняя.
- **Доказательство:** `TestReview_NULInStringsIsValidationError` падал 5 из 5 раз. Лог: `insert event: ERROR: invalid byte sequence for encoding "UTF8": 0x00 (SQLSTATE 22021)`. Для `customer_email` ответ правильный, 400.
- **Направление:** отклонять NUL при валидации с кодом 400 и указанием поля.

### D4 (P2). Отмена и дубль создания образуют дедлок, клиент получает 500

- **Где:** порядок блокировок: создание `events → bookings` (`internal/store/store.go:217-223`, затем `:258-262`), отмена `bookings → events` (`:309-310`, `:322-333`).
- **Условие:** отмена бронирования, пока в полёте ещё есть дубль запроса на его создание. Дубль держит строку события и в `INSERT` ждёт транзакцию отмены из-за проверки уникальности, а отмена ждёт строку события.
- **Последствия:** через `deadlock_timeout` (около 1 с) PostgreSQL прерывает одну из транзакций, клиент получает 500. **Гарантии не нарушаются:** транзакция откатывается, места возвращаются один раз, повтор после завершения гонки успешен. В журнале прерывались и `DELETE`, и `POST` (оба `UPDATE events` и `INSERT`).
- **Доказательство:**
  - `TestReview_CancelVsDuplicateCreateDeadlock`: 2 дубля — ответ не 200 в 2 раундах из 40; 8 дублей — в 32 и 29 раундах из 40 (два прогона). `reserved_seats` в конце каждого раунда равен 0.
  - Без специальной постановки дедлок возник 2 раза за две фазы смешанной нагрузки (2500 операций в каждой).
  - Журнал PostgreSQL: `deadlock detected ... UPDATE events SET reserved_seats = reserved_seats - $2`, лог приложения: `release seats: ERROR: deadlock detected (SQLSTATE 40P01)`.
- **Направление:** единый порядок блокировок в отмене: прочитать `event_id` без блокировки, заблокировать событие, затем бронирование. Либо повторять транзакцию на сервере при `40P01`.

### D5 (P2). Compose публикует суперпользователя PostgreSQL на всех интерфейсах

- **Где:** `compose.yaml:7-11`, `:25`.
- **Условие:** машина доступна из сети и порт не закрыт внешним фильтром. Правила Docker для опубликованных портов могут обходить локальный файрвол хоста.
- **Последствия:** любой, кто дошёл до порта, с паролем `booking` получает полный контроль над базой и выполнение команд в контейнере БД. README (`:380-381`) честно предупреждает о dev-пароле и публикации порта, но не говорит о правах суперпользователя и привязке ко всем интерфейсам.
- **Доказательство:** подключение через адрес хоста `10.0.2.15:5432` прошло; `rolsuper=true`; `COPY o FROM PROGRAM 'id'` вернул `uid=70(postgres)` (только в собственном контейнере).
- **Направление:** публиковать как `127.0.0.1:${POSTGRES_PORT:-5432}:5432`. Для приложения завести отдельную роль без прав суперпользователя.

### D6 (P3). Длинный путь запроса одной строкой попадает в лог

- **Где:** `internal/api/middleware.go:54`, `cmd/server/main.go:58` (`MaxHeaderBytes` 1 МиБ).
- **Условие:** запрос с очень длинным путём к любому адресу, без авторизации.
- **Последствия:** лог растёт примерно на столько же байт, сколько прислал клиент. Без лимитов частоты и ротации это ускоряет заполнение диска.
- **Доказательство:** запрос с путём 900 КБ дал ответ 404 и строку лога 900 143 байта.
- **Направление:** усекать путь в логе, уменьшить `MaxHeaderBytes`.

### D7 (P3). Внутренние детали попадают в ответы клиенту

- **Где:** `internal/api/errors.go:117`.
- **Условие:** неверный тип поля или зависшее тело запроса.
- **Последствия:** раскрываются имена Go-типов и внутренний адрес контейнера. Зависшее чтение тела к тому же описано как `invalid_json`, хотя JSON тут ни при чём. Прямого ущерба нет, но это помогает разведке.
- **Доказательство:**
  - `json: cannot unmarshal array into Go value of type api.createEventRequest`.
  - При зависшем теле через 15 с: `read tcp 172.18.0.4:8080->172.18.0.1:46980: i/o timeout`, статус 400.
- **Направление:** отображать ошибки декодера в собственные сообщения (поле и ожидаемый тип), сетевые ошибки чтения отдавать отдельным кодом.

### D8 (P3). `starts_at` принимает значения, не соответствующие RFC 3339

- **Где:** `internal/api/validation.go:67`, заявлено в `README.md:312-313`.
- **Условие:** `time.Parse(time.RFC3339, …)` снисходителен к формату.
- **Последствия:** приняты `2026-12-01T8:00:00Z`, `2026-12-01T18:00:00,5Z`, `2026-12-01T18:00:00+24:00`; последнее даёт сдвиг на сутки. Клиент узнаёт об ошибке формата только по дате в ответе.
- **Доказательство:** все три запроса вернули `201` (приложение D).
- **Направление:** строгий разбор, например через `time.Time.UnmarshalText`. Поведение стоит закрепить тестом.

### D9 (P3). README расходится с поведением

- **Где и условие:**
  - `README.md:169-170`: тот же ключ для другого события якобы даёт `409`. На деле — `201` и новое бронирование; ключ действует в пределах события, что и проверяется в `internal/integration/api_test.go:292-295`.
  - `README.md:378-379`: неверный метод якобы даёт текстовый `405`. На деле из-за обработчика `/` (`internal/api/api.go:69`) `PUT /events`, `PATCH /bookings/{id}`, `DELETE /events/{id}` отвечают JSON `404 not_found`.
- **Последствия:** клиент опирается на неверный контракт. Отсутствие `405` само по себе не нарушает `TASK.md`.
- **Доказательство:** приложение D.
- **Направление:** исправить README либо привести поведение к описанному.

### D10 (P3). Превышение лимита в хвосте тела даёт 400 вместо 413

- **Где:** `internal/api/errors.go:121-124`.
- **Условие:** верный объект, за которым следует более 1 МиБ пробелов.
- **Последствия:** клиент получает `400 invalid_json` «exactly one JSON object» вместо документированного `413`. Лимит при этом работает, данные не меняются.
- **Доказательство:** приложение D, случай «2 MiB trailing whitespace».
- **Направление:** проверять `MaxBytesError` и при втором вызове `Decode`.

### D11 (P3). Длина ключа считается в байтах, а описана в символах

- **Где:** `internal/api/validation.go:116-119`, `README.md:249`.
- **Условие:** ключ не из ASCII.
- **Последствия:** ключ из 150 кириллических символов отклоняется с сообщением `at most 200 characters`.

## 3. Неподтверждённые риски и необязательные рекомендации

### Неподтверждённые риски

Подтвердить или опровергнуть эти риски как дефекты в рамках проверки не удалось.

- **Голодание пула при блокировке одного события.** Механизм измерен: при 12 запросах, ждущих строку, заблокированную моей внешней транзакцией, пул из 10 соединений (`internal/db/db.go:21`) исчерпан.
  - Бронирование другого события на этом экземпляре заняло 12 с.
  - `/readyz` ответил `503 database: down`, хотя база работала.
  - Все 12 запросов получили `500` через 15 с; соединений `idle in transaction` не осталось, повтор успешен.
  - Второй экземпляр не пострадал.

  При обычной нагрузке такого не наблюдалось: блокировку держала искусственная транзакция. Неизвестно, можно ли достичь этого штатным потоком запросов.
- **Первый запрос после рестарта БД.** Каждое устаревшее соединение может дать один `500` с `57P01`, затем сервис восстанавливается сам. Наблюдалось; README об отсутствии серверных ретраев предупреждает. Дефектом не считаю.
- **Неоднозначный исход `COMMIT` при обрыве связи.** Клиент может получить 500 при фактически зафиксированной транзакции. Не воспроизводилось; повтор с тем же ключом или повторная отмена должны это покрывать.
- **PgBouncer в режиме транзакций.** Сессионная advisory-блокировка миграций и кэш подготовленных операторов pgx могут работать неверно. Не проверялось, в `TASK.md` не требуется.
- **Завершение дольше `docker stop`.** `ShutdownTimeout` 10 с равен стандартному сроку Docker, а запрос может длиться 15 с. При прямом `SIGTERM` запрос с блокировкой на 14 с завершился успешно с кодом выхода 1. С `docker stop` возможен `SIGKILL`; транзакция откатится, повтор безопасен. Этот вариант отдельно не проверялся.

## 4. Архитектура

**Общая оценка:** решение соразмерно задаче. Около 1400 строк production-кода в 7 небольших пакетах, стандартный `net/http`, pgx без ORM и фреймворков. Основные слабые места связаны не со структурой, а с порядком операций в двух транзакциях.

**Разделение ответственности и зависимости.** Направление простое и без циклов: `cmd → api → store → model`.

- Интерфейс `api.Store` (`internal/api/api.go:24-33`) ссылается на `store.CreateEventParams`, а `writeStoreError` — на типы ошибок `store`, поэтому HTTP-слой всё равно зависит от пакета хранилища. Других реализаций интерфейса нет, тесты работают с настоящей базой. *Компромисс:* заменяемость почти не используется, но и стоит всего 8 строк. Менять необязательно.
- `model.Event` и `model.Booking` несут JSON-теги, то есть доменная модель совпадает с внешним контрактом. Для такого размера это экономит код; цена в том, что изменение поля сразу меняет API.

**Бизнес-инварианты и транзакции.** Границы транзакций понятны: одна на метод `store`.

- Ёмкость защищена дважды: условным `UPDATE` и `CHECK` (`0001_init.sql:15`). Это сильное решение: нарушить ёмкость не даст сама база, даже если условие в коде будет сломано. Мутант без этого условия (M3) обнаружен тестами.
- Правила идемпотентности и отмены лежат в `store`, а не в отдельном сервисном слое. Для этой задачи это оправдано: гарантии держатся именно на SQL и блокировках, и отдельный слой только разнёс бы их. Не считаю это недостатком.
- Счётчик `reserved_seats` избыточен относительно суммы бронирований. *Компромисс:* атомарная проверка и быстрое чтение против риска расхождения. Он обновляется лишь в двух местах, и сверка после всех сбоев расхождений не показала. Разумный выбор.
- Все бронирования одного события выполняются последовательно на строке события. Это просто и надёжно, но ограничивает пропускную способность популярного события. Для объявленного масштаба приемлемо.

**Где структура ведёт к дефектам.**

- `CreateBooking` (`internal/store/store.go:188-294`, около 100 строк) решает судьбу существующего ключа в двух ветках, а должен в трёх. Третья, «нет мест», и есть D1. Единая функция разрешения ключа сделала бы такой пропуск менее вероятным.
- Разный порядок блокировок в создании и отмене приводит к D4.
- `writeJSON` пишет заголовок до кодирования, поэтому D2 незаметен. Буферизация стоит пару строк.

**Избыточность** (мелкая, не дефекты).

- `bookings_event_id_idx` дублирует префикс уникального индекса `(event_id, idempotency_key)`. По `bookings_created_at_idx` ни один запрос не фильтрует: `created_at` используется только для сортировки внутри выборки по `event_id` (`0001_init.sql:35-36`). Оба увеличивают стоимость записи. Вывод сделан по чтению запросов, планы и статистика использования индексов как доказательство не применялись.
- Две почти одинаковые функции `getBookingByKey` (`store.go:355-367`) и ручной `Scan` в `store.go:265-269` рядом с `scanBooking`.
- `event_id` входит в хеш запроса, хотя уникальность ключа и так ограничена событием.

**Упрощения, цена которых ещё приемлема.** Собственный код миграций (140 строк) понятен и надёжен при одной миграции. При росте их числа может понадобиться контроль изменений и откаты. Настройки пула и таймауты заданы константами, что достаточно для задачи, но для настройки под нагрузку потребует пересборки.

**Тестируемость.** Хорошая: `api.New(...).Handler()` и `httptest` позволяют поднять несколько экземпляров в одном тесте, `migrate.Run` вызывается отдельно, каждому тесту выделяется своя схема. `cmd/server/main.go` и `internal/config` тестами не покрыты, что при их простоте допустимо.

**Понятность и стоимость изменений.** Код читается легко, комментарии объясняют причины решений. Новое поле бронирования затрагивает примерно семь мест: запрос, валидацию, параметры, хеш, список колонок, `scanBooking` и ручной `Scan`. Изменение состава хеша заслуживает внимания: хеши уже сохранённых ключей перестанут совпадать, и повторы старых запросов получат `idempotency_key_conflict`.

## 6. Безопасность

### Модель угроз и границы доверия

Модель моя, в `TASK.md` она не задана.

- **Недоверенные:** любой HTTP-клиент, достигший порта приложения, все тела, заголовки и пути.
- **Доверенные:** переменные окружения, PostgreSQL и встроенные миграции. Сеть между приложением и базой в compose внутренняя.
- **Цели:** целостность учёта мест, доступность API, отсутствие утечек внутренних данных и секретов. Отсутствие авторизации разрешено `TASK.md` и дефектом не считается.

### Подтверждённые уязвимости

| Дефект | Предпосылка | Последствие |
|---|---|---|
| D2 (P1) | Сетевой доступ к API | Один запрос надолго выводит из строя `GET /events`, незаметно для логов |
| D5 (P2) | Доступ к порту 5432 хоста | Полный контроль над базой, выполнение команд в контейнере БД |
| D6 (P3) | Сетевой доступ к API | Ускоренный рост логов |
| D7 (P3) | Сетевой доступ к API | Раскрытие внутреннего адреса и имён типов |

### Что проверено, проблем не найдено

- **SQL-инъекции.** Все значения передаются параметрами, конкатенируются только константы (`store.go`). Нагрузки в `name`, `customer_name`, `Idempotency-Key` и в пути сохранены как обычный текст или отклонены; таблицы целы. В `testutil` имя схемы подставляется в SQL, но оно случайное и в production не попадает.
- **Недоверенный JSON.** Неизвестные поля, мусор после объекта, неверные типы и переполнение чисел дают 400. Вложенность 100 000 уровней дала 400 без падения. Недопустимый UTF-8 заменяется на `U+FFFD`.
- **Границы значений.** `seats` и `capacity` ограничены, значение `2^31` отклоняется, переполнения `int4` нет.
- **Размер и таймауты.**
  - Тело 2 МиБ → 413, заголовок 1,2 МБ → 431.
  - Неполные заголовки: соединение закрыто через 5 с; зависшее тело: через 15 с.
  - Транзакция начинается после чтения тела, так что медленный клиент её не удерживает.
  - Запрос ограничен контекстом в 15 с; соединений `idle in transaction` после таймаутов нет.
- **Ответы.** Сбои отдаются как `internal_error` без подробностей. HTML экранируется, есть `X-Content-Type-Options: nosniff`. В заголовки ответа попадают только UUID, значения клиента не отражаются. В просмотренных выборках ошибок из логов приложения паник не встретилось; отдельного поиска по всем прогонам не было.
- **Логи.** В логах запросов только метод, путь, статус, размер и длительность: нет тел, ключей идемпотентности, имён и email. Лог в формате JSON, поэтому переводы строк экранируются.
- **Секреты в ошибках запуска.** Пароль маскируется в URL и в формате `key=value`, при неверном пароле и недоступном хосте не выводится. Исключение незначительно: строка, не распознанная ни как URL, ни как `key=value`, выводится целиком (`not a url SECRETPW`). Значение конфигурации находится в доверенной зоне.
- **Контейнер приложения.** Distroless, пользователь `nonroot`, без оболочки, не привилегирован, `-trimpath`, `.git` в образ не попадает.

### Архитектурные компромиссы, а не уязвимости

- Нет пагинации и лимитов на список (заявлено в README). Измерено: при 100 000 событий один `GET /events` дал ответ 20,5 МБ и рост памяти процесса с 4,9 до 99,5 МиБ. Параллельные запросы умножат это; тяжёлая атака намеренно не проводилась.
- Ключи идемпотентности и бронирования хранятся бессрочно (заявлено), поэтому без лимита частоты любой клиент может неограниченно наращивать объём базы.
- Клиент может занять все места одним запросом: лимит на бронирование равен максимальной вместимости. Следствие выбранной модели без авторизации.

### Условия публичного развёртывания

Это не дефекты выполнения задания, но без них публиковать сервис нельзя.

- **Аутентификация и авторизация.** Сейчас любой клиент проходит цепочку `GET /events` → `GET /events/{id}/bookings` и получает имена и email всех клиентов, а затем может отменить любое бронирование. Это проверено через API.
- **TLS** на обратном прокси. В приложении его нет; соединение с БД в compose с `sslmode=disable`.
- **Лимиты** частоты и соединений, размера логов, а также сетевая изоляция БД (см. D5).
- **Учётные данные** из секретов, не из `compose.yaml`.

### Необязательные улучшения

- В compose: `read_only`, `cap_drop: [ALL]`, `no-new-privileges`, лимиты памяти и PID. Сейчас их нет.
- Закрепить базовые образы по digest: `golang:1.27-alpine` и `distroless/static-debian12:nonroot` указаны изменяемыми тегами.
- Настроить `lock_timeout` или `statement_timeout` в БД как второй рубеж.

Отсутствие других найденных проблем не означает доказанную безопасность.

## 8. Сильные стороны

- Условный `UPDATE` плюс `CHECK` реально защищают ёмкость: при `kill -9` и рестартах расхождений не появилось.
- Отмена через `SELECT … FOR UPDATE` дала ровно один возврат мест при всех конкурентных сценариях.
- Уникальный индекс и хеш запроса надёжно исключают дубликаты и обнаруживают повторное использование ключа с другим телом.
- Миграции: транзакция на файл, advisory-блокировка, безопасный повторный запуск, отказ без порчи при чужой таблице.
- Настоящая проверка на PostgreSQL с двумя экземплярами, без моков.
- Запуск воспроизводим одной командой, образ небольшой (21,8 МБ), пользователь непривилегированный, production-бинарник без тестовых зависимостей.
- Аккуратная обработка недоверенного ввода и таймаутов; строгий JSON, лимиты, отсутствие внутренних подробностей в ответах 500.
- README подробно описывает решения и ограничения, включая неудобные.

			failed := 0

				event := a.createEvent("dl", 1000)

				first := make(chan []byte, dups)
				var wg sync.WaitGroup
				for i := 0; i < dups; i++ {
					inst := a
					if i%2 == 1 {
						inst = b
					}
					wg.Add(1)
					go func(inst *instance) {
						defer wg.Done()
						s, _, body, err := inst.createBooking(event.ID, key, 1)
						if err == nil && (s == 201 || s == 200) {
							first <- body
						}
					}(inst)
				}
				var bk struct {
					ID string `json:"id"`
				}
				require.NoError(t, json.Unmarshal(<-first, &bk))
				status, _, _, err := b.doRaw(http.MethodDelete, "/bookings/"+bk.ID, nil, "", nil)
				require.NoError(t, err)
				if status != http.StatusOK {
					failed++
				}
				wg.Wait()

				status, _, _, err = b.doRaw(http.MethodDelete, "/bookings/"+bk.ID, nil, "", nil)

	}

// Tracks acknowledged results so they can be audited after crashes.

func do(method, url string, key string, body string) (int, []byte, error) {
	var r io.Reader
	if body != "" {
		r = bytes.NewBufferString(body)
	}
	req, _ := http.NewRequest(method, url, r)

	if err != nil {
		return 0, nil, err
	}
	defer resp.Body.Close()
	b, err := io.ReadAll(resp.Body)
	return resp.StatusCode, b, err
}

	events := flag.Int("events", 5, "")
	capacity := flag.Int("capacity", 20, "")
	workers := flag.Int("workers", 24, "")
	ops := flag.Int("ops", 2000, "")
	out := flag.String("out", "acks.json", "")
	flag.Parse()

	targets := []string{*a, *b}
	var evIDs []string
	for i := 0; i < *events; i++ {
		_, body, err := do("POST", *a+"/events", "", fmt.Sprintf(`{"name":"load-%d","capacity":%d,"starts_at":"2027-01-01T00:00:00Z"}`, i, *capacity))
		if err != nil {
			fmt.Println("create event:", err)
			os.Exit(1)
		}
		var e struct {
			ID string `json:"id"`
		}
		_ = json.Unmarshal(body, &e)
		evIDs = append(evIDs, e.ID)
	}

	var mu sync.Mutex
	statuses := map[string]int{}
	acked := map[string]string{} // booking id -> last acked status
	var pool []string
	var opCount atomic.Int64
	count := func(k string) { mu.Lock(); statuses[k]++; mu.Unlock() }

	var wg sync.WaitGroup
	for w := 0; w < *workers; w++ {
		wg.Add(1)
		go func(w int) {
			defer wg.Done()
			rng := rand.New(rand.NewSource(int64(w) + time.Now().UnixNano()))
			for opCount.Add(1) <= int64(*ops) {
				t := targets[rng.Intn(2)]
				switch p := rng.Intn(10); {
				case p < 6: // book, with the same key sent twice in parallel half of the time
					ev := evIDs[rng.Intn(len(evIDs))]
					key := fmt.Sprintf("k-%d-%d", w, rng.Int63())
					seats := 1 + rng.Intn(4)
					body := fmt.Sprintf(`{"seats":%d,"customer_name":"w%d"}`, seats, w)
					n := 1 + rng.Intn(2)
					var iwg sync.WaitGroup
					for i := 0; i < n; i++ {
						iwg.Add(1)
						go func(i int) {
							defer iwg.Done()
							code, data, err := do("POST", targets[(rng2(i, w))%2]+"/events/"+ev+"/bookings", key, body)
							if err != nil {
								count("book:transport")
								return
							}
							count(fmt.Sprintf("book:%d", code))
							if code == 201 || code == 200 {
								var bk booking
								_ = json.Unmarshal(data, &bk)
								mu.Lock()
								if acked[bk.ID] == "" {
									acked[bk.ID] = "confirmed"
								}
								pool = append(pool, bk.ID)
								mu.Unlock()
							}
						}(i)
					}
					iwg.Wait()
				case p < 9: // cancel a known booking, possibly several times in parallel
					mu.Lock()
					var id string
					if len(pool) > 0 {
						id = pool[rng.Intn(len(pool))]
					}
					mu.Unlock()
					if id == "" {
						continue
					}
					n := 1 + rng.Intn(3)
					var iwg sync.WaitGroup
					for i := 0; i < n; i++ {
						iwg.Add(1)
						go func(i int) {
							defer iwg.Done()
							code, _, err := do("DELETE", targets[(rng2(i, w))%2]+"/bookings/"+id, "", "")
							if err != nil {
								count("cancel:transport")
								return
							}
							count(fmt.Sprintf("cancel:%d", code))
							if code == 200 {
								mu.Lock()
								acked[id] = "cancelled"
								mu.Unlock()
							}
						}(i)
					}
					iwg.Wait()
				default:
					code, _, err := do("GET", t+"/events/"+evIDs[rng.Intn(len(evIDs))]+"/availability", "", "")
					if err != nil {
						count("avail:transport")
					} else {
						count(fmt.Sprintf("avail:%d", code))
					}
				}
			}
		}(w)
	}
	wg.Wait()
	fmt.Println("statuses:", statuses)
	fmt.Println("acked bookings:", len(acked))
	data, _ := json.Marshal(acked)
	_ = os.WriteFile(*out, data, 0o644)
	var ids []byte
	ids, _ = json.Marshal(evIDs)
	fmt.Println("events:", string(ids))
}

func rng2(i, w int) int { return i + w }

#!/usr/bin/env python3
"""One-connection slow-client probes against the reviewer's own instance."""
import socket, sys, time

HOST, PORT = "localhost", int(sys.argv[1])


def recv_all(s, timeout):
    s.settimeout(timeout)
    data = b""
    t0 = time.time()
    try:
        while True:
            chunk = s.recv(65536)
            if not chunk:
                return data, time.time() - t0, "closed"
            data += chunk
    except socket.timeout:
        return data, time.time() - t0, "timeout"
    except ConnectionError as e:
        return data, time.time() - t0, repr(e)


# 1. Slowloris: incomplete headers.
s = socket.create_connection((HOST, PORT))
s.sendall(b"GET /healthz HTTP/1.1\r\nHost: x\r\nX-A: ")
d, t, how = recv_all(s, 12)
print(f"incomplete headers: {how} after {t:.1f}s; resp={d[:60]!r}")
s.close()

# 2. Slow body: declared 100 bytes, sends 10, then silence.
s = socket.create_connection((HOST, PORT))
s.sendall(b"POST /events HTTP/1.1\r\nHost: x\r\nContent-Type: application/json\r\nContent-Length: 100\r\n\r\n{\"name\":\"x")
d, t, how = recv_all(s, 25)
print(f"stalled body: {how} after {t:.1f}s")
print("  response:", d.decode(errors="replace").replace("\r\n", " | ")[:520])
s.close()

# 3. Huge request target: within MaxHeaderBytes (1 MiB).
path = b"/" + b"a" * 900_000
s = socket.create_connection((HOST, PORT))
s.sendall(b"GET " + path + b" HTTP/1.1\r\nHost: x\r\nConnection: close\r\n\r\n")
d, t, how = recv_all(s, 10)
print(f"900 KB path: status line={d.split(b'\r\n')[0]!r}")
s.close()

# 4. Oversized headers.
s = socket.create_connection((HOST, PORT))
