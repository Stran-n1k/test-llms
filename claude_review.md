# Независимое ревью: сервис бронирования мест

Проверенный коммит: `eab4830` (рабочее дерево чистое). Дата: 2026-11-07. Окружение: Linux VM, Go 1.27.3, Docker 29.9.2, Compose 5.7.0, PostgreSQL 16 (`postgres:16-alpine`). Исходники, тесты, зависимости, `TASK.md` и `README.md` не менялись; единственный добавленный файл — этот отчёт.

## 1. Заключение

**Решение соответствует TASK.md по всем ключевым гарантиям. Дефектов P0 и P1 не найдено.** В проверках с двумя настоящими процессами, общей PostgreSQL и `kill -9` приложения и базы не обнаружено ни перепродажи, ни дублей бронирований, ни двойного освобождения мест, ни расхождения статуса бронирования с его местами.

Есть одно подтверждённое отступление от требования «некорректные запросы получают понятные ошибки»: NUL-символ в строке или невалидный UTF-8 в заголовке дают `500` вместо `400` (D-01, P2). Данные при этом не портятся. Остальные замечания имеют приоритет P3: мелкие расхождения с README, усиление защиты и пробелы в тестах.

Самая значимая для сопровождения находка: штатные тесты не заметили бы поломки подсчёта доступности после отмены и снятия блокировки миграций (D-11, D-12). Сейчас оба механизма работают, но защиты от регрессии у них нет.

## 2. Дефекты

Шкала: **P0** — нарушение основной гарантии или потеря данных; **P1** — требование не выполняется при обычном использовании; **P2** — требование нарушается в узком сценарии; **P3** — мелкое расхождение, усиление защиты или пробел в тестах без влияния на текущее поведение.

Для команд ниже: `A=http://127.0.0.1:18081`, `J='Content-Type: application/json'`, `$EV` — id существующего события (стенд описан в приложении A).

### D-01 · P2 · NUL и невалидный UTF-8 дают 500 вместо ошибки валидации

- **Где:** `internal/service/service.go:63-69` (имя), `:88-98` (ключ), `internal/httpapi/server.go:166-169` (ключ из заголовка); итоговый ответ формирует `server.go:271-273`.
- **Условие:** `name` или `idempotency_key` содержит `\u0000`, либо заголовок `Idempotency-Key` содержит байты, не являющиеся UTF-8. Проверки длины и пустоты такие значения пропускают, а PostgreSQL отвергает их с SQLSTATE 22021.
- **Последствия:** клиент получает `500 internal` за свою ошибку и может повторять запрос как при сбое сервера. В лог и мониторинг попадают ложные внутренние ошибки, и их может создать любой анонимный клиент. Данные не портятся: транзакция откатывается.
- **Доказательство:**
  ```bash
  curl -s -w ' %{http_code}\n' -XPOST $A/events -H "$J" -d '{"name":"a\u0000b","capacity":3}'
  # {"error":{"code":"internal","message":"internal server error"}} 500
  curl -s -w ' %{http_code}\n' -XPOST $A/bookings -H "$J" -d "{\"event_id\":$EV,\"seats\":[1],\"idempotency_key\":\"a\\u0000b\"}"
  # ... 500
  curl -s -w ' %{http_code}\n' -XPOST $A/bookings -H "$J" -H $'Idempotency-Key: \xff\xfe' -d "{\"event_id\":$EV,\"seats\":[1]}"
  # ... 500
  # лог: internal error: create event: ERROR: invalid byte sequence for encoding "UTF8": 0x00 (SQLSTATE 22021)
  ```
- **Исправление:** проверять в сервисе `utf8.ValidString` и отсутствие `\x00`, возвращать `ValidationError`.

### D-02 · P3 · Длина считается в байтах, а README и ошибка говорят о символах

- **Где:** `internal/service/service.go:67`, `:94`; `README.md:61`, `:91`.
- **Условие:** кириллица или другой многобайтовый текст длиннее 100 символов в имени либо 64 символов в ключе.
- **Последствия:** допустимый по README запрос отклоняется с неверным сообщением. Для русскоязычных названий предел фактически вдвое ниже заявленного.
- **Доказательство:** имя из 150 букв «я» (300 байт) → `400 name must be at most 200 characters`; 200 ASCII-символов → `201`. Ключ из 100 букв «ю» → `400 idempotency key must be at most 128 characters`.
- **Исправление:** `utf8.RuneCountInString` или формулировка «байт» в README и сообщениях.

### D-03 · P3 · Отсутствующий `event_id` даёт 404 вместо ошибки валидации

- **Где:** `internal/httpapi/server.go:58`; `internal/service/service.go:87-122` (нет проверки `eventID`); `internal/store/postgres.go:172-175`.
- **Условие:** в теле нет `event_id`, либо он равен `0` или отрицателен.
- **Последствия:** клиент видит «requested entity does not exist» и ищет несуществующее событие, а не забытое поле. Для пути то же значение даёт `400` (`pathID`), так что поведение непоследовательно.
- **Доказательство:** `curl -XPOST $A/bookings -H "$J" -d '{"seats":[1],"idempotency_key":"z"}'` → `404 not_found`.
- **Исправление:** проверять `eventID >= 1` в `service.CreateBooking`.

### D-04 · P3 · Ответы 404 и 405 маршрутизатора не в JSON

- **Где:** `internal/httpapi/server.go:20-37`; расхождение с `README.md:46` («Все ответы — JSON»).
- **Условие:** неизвестный маршрут, неверный метод, завершающий слэш.
- **Последствия:** клиент, разбирающий тело ошибки как JSON, получает ошибку разбора.
- **Доказательство:** `GET /nope` → `404 text/plain "404 page not found"`; `DELETE /events` → `405 text/plain "Method Not Allowed"`.
- **Исправление:** оборачивать ответы mux в JSON или уточнить README.

### D-05 · P3 · На распроданном событии пропадает поле `available_seat_numbers`

- **Где:** `internal/httpapi/server.go:54` (`omitempty`), `internal/store/postgres.go:156`.
- **Условие:** `GET /events/{id}` при `available_seats == 0`.
- **Последствия:** форма ответа зависит от состояния: вместо `[]` поля нет вовсе. Клиент, рассчитывающий на массив, может упасть именно на распроданном событии.
- **Доказательство:** свободное событие: `..."available_seats":1,"available_seat_numbers":[1]}`; после бронирования: `..."booked_seats":1,"available_seats":0}`.
- **Исправление:** возвращать `[]` для детального запроса, например отдельным типом ответа без `omitempty`.

### D-06 · P3 · Ответы 400 раскрывают внутренние детали (безопасность)

- **Где:** `internal/httpapi/server.go:240-241` (в ответ попадает `err.Error()`).
- **Условие:** тело не того типа, или клиент не дослал тело до `ReadTimeout`.
- **Последствия:** клиент видит имена внутренних Go-типов и адреса сокетов; в контейнере это будет внутренний IP. Прямого ущерба нет, но это упрощает разведку и ухудшает понятность ошибок.
- **Доказательство:**
  ```text
  {"capacity":"5"} → invalid JSON body: json: cannot unmarshal string into Go struct field createEventRequest.capacity of type int
  []               → invalid JSON body: json: cannot unmarshal array into Go value of type httpapi.createEventRequest
  неполное тело    → invalid JSON body: read tcp 127.0.0.1:18081->127.0.0.1:46296: i/o timeout   (через 10 с)
  ```
- **Исправление:** различать `json.SyntaxError`, `json.UnmarshalTypeError` (только имя поля), `MaxBytesError` и остальное; прочее логировать, а клиенту отвечать общим сообщением.

### D-07 · P3 · Подделка строк лога через путь URL (безопасность)

- **Где:** `internal/httpapi/server.go:294` (`%s` с декодированным `r.URL.Path`).
- **Условие:** анонимный запрос с `%0a` в пути.
- **Последствия:** атакующий может вписать в лог правдоподобные чужие строки, что запутает расследование и автоматический разбор логов. Выполнения кода и утечки данных нет.
- **Доказательство:**
  ```text
  curl "$A/x%0a2026/11/07%2000:00:00%20FORGED%20POST%20/admin%20200"
  лог:  2026/11/07 02:07:24 GET /x
        2026/11/07 00:00:00 FORGED POST /admin 200 404 21µs
  ```
- **Исправление:** логировать `%q` или `r.URL.EscapedPath()`.

### D-08 · P3 · Нет верхней границы времени запроса к БД: зависание БД занимает весь пул (безопасность, устойчивость)

- **Где:** `cmd/server/main.go:52-59` (таймауты есть только у HTTP), `internal/store/postgres.go:41` (25 соединений), все обработчики используют `r.Context()` без `WithTimeout`, `internal/httpapi/server.go:23` (`/healthz`).
- **Условие:** долгая блокировка или зависание PostgreSQL. Через одно только API создать такую блокировку не удалось: транзакции сервиса короткие. Поэтому приоритет P3, а TASK.md таймаутов прямо не требует.
- **Последствия:** `WriteTimeout` не отменяет контекст обработчика. Обработчики ждут, пока держится блокировка, очередь к пулу не ограничена. Перестают отвечать даже чтения и `/healthz`, включая запросы к незаблокированным данным. Клиенты получают пустой ответ, хотя бронирование может быть зафиксировано; повтор с тем же ключом это компенсирует. После снятия блокировки сервис восстанавливается сам, потери данных нет.
- **Доказательство:** `LOCK TABLE bookings IN ACCESS EXCLUSIVE MODE` на 45 с и 30 клиентов на один экземпляр:
  ```text
  +4 с:  healthz (экземпляр B) → таймаут клиента 3 с; healthz (A, другой пул) → 200 за 0.7 мс
         pg_stat_activity: 25 соединений B в ожидании блокировки
  +21 с: всё ещё 25 ожиданий (WriteTimeout = 15 с уже истёк)
  +44 с: все 30 клиентов: "Empty reply from server"; в БД 30 зафиксированных бронирований
  повтор с тем же ключом → 200, то же бронирование
  ```
- **Исправление:** ограничить время на запрос (`context.WithTimeout` в middleware) и/или задать `statement_timeout` и `lock_timeout`; для `/healthz` отдельный короткий таймаут. Компромисс: при отмене по таймауту исход коммита может быть неизвестен, но повтор с ключом это покрывает.

## 3. Архитектура

**Общая оценка: решение соразмерно задаче.** Примерно 1070 строк кода без тестов, четыре пакета, одна прямая зависимость (`pgx`), без фреймворков и генерации. Избыточность есть, но мелкая, и она дешевле упрощений, которых здесь нет в критичных местах.

### Что сделано удачно

- **Инварианты находятся на самом сильном уровне.** Запрет двойной продажи — это частичный уникальный индекс (`migrations.go:46-47`), идемпотентность — уникальное ограничение (`:32`). Поэтому два экземпляра не требуют отдельной логики: мутант с неуникальным индексом сразу ловят три теста.
- **Направление зависимостей чистое.** `httpapi → service → domain`, `store → domain`; порт `Store` объявлен на стороне потребителя (`service.go:25`); сборка только в `main`. `service` не импортирует ни SQL, ни HTTP.
- **Границы транзакций понятны:** один метод store — одна транзакция. Для этого объёма это проще абстракции unit-of-work, которая ничего бы не добавила. Компромисс: если появится сценарий из нескольких операций в одной транзакции, интерфейс придётся менять.
- **Доступность читается в одном снимке** (`postgres.go:124`, Repeatable Read): под конкурентной записью счётчик и список мест не разошлись.
- **Интеграционные тесты идут через настоящий HTTP и БД**, поэтому проверяют контракт, а не реализацию; 8 мутантов основных механизмов пойманы.

### Упрощения и связанность, которые стоит учитывать

Это компромиссы, а не ошибки: текущее поведение корректно.

### Избыточность (мелкая)

- `Service.Migrate` (`service.go:60`) не используется в продакшене: `main` вызывает `st.Migrate`, покрытие интеграционными тестами 0%. Это заставляет `Store` и fake содержать лишний метод. Убирается без последствий.
- `PostgresStore.DB()` (`postgres.go:73-75`) открыт для тестов и упоминает «operational tooling», которого нет. Компромисс приемлем, но тесты могли бы открывать своё подключение по DSN.
- Поля `maxCapacity` и `maxSeatsPerBooking` с названиями `Default…` (`service.go:15-16`, `:44-47`) подразумевают настройку, которой нет. Хватило бы констант.
- `booking_seats_event_active_idx` (`migrations.go:49-50`) дублирует префикс уникального индекса. В `EXPLAIN` выбран уникальный индекс. Цена — лишняя запись при каждом изменении.
- Версионирование миграций вместе с `IF NOT EXISTS` — двойная защита. Побочный эффект: если таблица с таким именем уже есть с другой структурой, миграция пройдёт без ошибки. На пустой базе это неактуально.
- Сборка `IN (...)` и `VALUES (...)` вручную (`postgres.go:318-368`) длиннее, чем `= ANY($2)` и `unnest($3::int[])`. Текущий вариант безопасен, но создаёт отдельную форму запроса на каждое число мест.
- `eventResponse` собирается в трёх местах (`server.go:100`, `:120`, `:145`). Для трёх мест это терпимо.

### Понятность и стоимость изменений

Код читается линейно, комментарии объясняют причины, а README описывает решения и совпадает с кодом за исключением D-04 и D-10. Добавить пагинацию, новый маршрут или миграцию — локальная правка. Дороже всего будет изменяемая вместимость: уменьшение потребует правил для уже занятых мест, а проверка диапазона сейчас выполняется только при бронировании. TASK.md этого не требует.

## 4. Безопасность

*Отсутствие найденных проблем не означает доказанную безопасность: ниже перечислено только то, что проверялось.*

### Модель угроз и границы доверия

- **Предположение:** сервис развёрнут в доверенной сети или за шлюзом; клиент API — анонимный и потенциально враждебный участник сети. Авторизации нет, и TASK.md это прямо разрешает; дефектом это не считается.
- **Границы доверия:** (1) HTTP-клиент → приложение: тело, путь и заголовки недоверенные; (2) приложение → PostgreSQL: сеть compose считается доверенной (`sslmode=disable`); (3) оператор → переменные окружения: доверенные.
- **Вне рамок:** компрометация хоста и Docker, цепочка поставки образов, DoS уровня сети. Тяжёлых нагрузочных атак не проводилось.

### Результаты проверок

### Подтверждённые уязвимости и слабости

Все имеют низкую серьёзность и описаны выше: **D-07** — подделка логов, анонимно; **D-06** — раскрытие внутренних деталей, анонимно; **D-08** — занятие пула при зависании БД, сама блокировка через API не создаётся. **D-01** тоже доступен анонимно и позволяет засорять лог ложными внутренними ошибками.

Удалённого выполнения кода, обхода инвариантов и порчи данных не обнаружено.

### Неподтверждённые риски

- **Усиление через большие события.** Запрос около 40 байт создаёт событие на 100 000 мест; `GET /events/{id}` затем отдаёт 589 КБ за 30 мс. 20 параллельных запросов: 0.38 с, RSS с 27.5 до 43.6 МБ (время и память из двух разных прогонов). При такой малой нагрузке проблем нет, поведение при большом параллелизме намеренно не проверялось.
- **Рост `GET /events`.** Нет пагинации, весь результат собирается в памяти (`postgres.go:107-113`). При малых объёмах запрос занял 3 мс; на миллионах событий не проверялось. Ограничение описано в README.
- **`Content-Type` не проверяется** (`text/plain` принят → `201`). Веб-страница может отправить простой межсайтовый POST на доступный браузеру адрес сервиса, например отменить бронирование во внутренней сети. Куки не используются, поэтому дополнительных прав атакующий не получает, только сетевую доступность. Сценарий через браузер не проверялся.

### Архитектурные компромиссы в области безопасности

- `wget` в итоговом образе (`Dockerfile:12`) нужен только для healthcheck: увеличивает поверхность атаки, зато проще самопроверки в бинарнике.
- Жёстко заданный пароль `booking` в `compose.yaml:6`, `:19` приемлем для локального запуска, пока БД не опубликована.
- `sslmode=disable` приемлем для внутренней сети compose, но не для БД на другом хосте.

### Условия развёртывания (не дефекты задания)

Для публичной эксплуатации нужно добавить:

- аутентификацию и разграничение доступа: сейчас при последовательных id любой клиент может прочитать или отменить любое бронирование, а также занять все места;
- TLS на шлюзе или в приложении;
- ограничение частоты и размера: создание событий и бронирований ничем не лимитировано, база может расти без предела;
- привязку порта к нужному интерфейсу вместо `0.0.0.0`: Docker публикует порты в обход типичных правил хостового файрвола;
- уникальные секреты вместо `booking/booking`;
- лимиты ресурсов контейнеров и политику `restart` (сейчас `no`: после падения приложение не поднимется само).

`scripts/integration.sh:14` и команда в README также публикуют БД с простым паролем на всех интерфейсах на время тестов; на общей машине лучше `127.0.0.1:${PORT}:5432`.

### Необязательные улучшения

Закрепить образы по digest; не хранить `# syntax=` с плавающим тегом; добавить `read_only` и `cap_drop: [ALL]` для приложения; `413` при превышении лимита тела; UUID вместо последовательных id, если сервис станет публичным.

## 5. Неподтверждённые риски и необязательные рекомендации

Риски безопасности перечислены в разделе 4. Прочее:

**Неподтверждённые риски**

- При четырёх и более экземплярах суммарный пул (`25 × N`) приблизится к `max_connections=100` по умолчанию. Значение пула не настраивается. Для двух экземпляров запаса хватает; больше не проверялось.
- Устойчивость к потере питания не доказана: `docker kill` проверяет падение процесса, а не сброс кешей диска в VM.
- Проверялась только PostgreSQL 16. Реплики и пулеры соединений (например, PgBouncer) не проверялись.

**Необязательные рекомендации**

- Повтор с тем же ключом и другими местами сейчас молча возвращает исходное бронирование (`200`). Механизм выбран автором и описан в README, поэтому это не дефект: клиент видит места в ответе. Ответ `409 idempotency_conflict` поймал бы ошибки клиента раньше.
- Сервис принимает ключи `"  K  "` и `"K"` как один и тот же (обрезка пробелов) — это стоит упомянуть в README.
- Запуск двух экземпляров через `docker compose up --scale app=2` не работает из-за фиксированного порта (`rc=1`). TASK.md этого не требует, и README не обещает. Если нужен демонстрационный стенд, подойдёт диапазон портов или второй сервис.
- `withRecovery` снаружи `withLogging` (`server.go:37`): при панике строки запроса в логе нет, и стек не пишется. Панику вызвать не удалось; мутант `no_recovery` выжил.

## 7. Сильные стороны

- Основные гарантии обеспечиваются самой базой, а не кодом приложения: они выдержали все проверки на двух процессах, включая `kill -9` приложения и базы.
- Механизм идемпотентности прост и действует на практике: ключ не расходуется при неудачной попытке, а при потере ответа после коммита повтор возвращает то же бронирование.
- Отмена атомарна и идемпотентна: `cancelled_at` не меняется, поздняя отмена не затрагивает нового владельца мест.
- Защита от deadlock через сортировку мест подтверждена: встречный порядок мест на 100 местах не дал ни одного deadlock.
- Миграции транзакционны и защищены advisory lock, что подтвердила проверка без него (10 из 10 сбоев).
- Входные данные хорошо ограничены: строгий JSON, лимит тела, HTTP-таймауты, параметризованный SQL, неразглашение ошибок БД.
- Контейнер не под root, БД не опубликована, штатное завершение по SIGTERM работает.
- Сервис сам восстанавливается после рестарта БД.
- Запуск воспроизводим с нуля одной командой; зависимости чисты и зафиксированы; README содержательно описывает решения и ограничения.
- Интеграционные тесты реально работают с PostgreSQL и ловят поломку основных механизмов: мутанты с неуникальным индексом и без обработки `23505` падают сразу в нескольких тестах.

func call(t *testing.T, method, url string, body any) (int, []byte) {

// shuffled multi-seat requests in both instances. Any deadlock gives 500.
func TestOverlappingMultiSeatStress(t *testing.T) {

	for round := 0; round < 10; round++ {
		ev := event(t, capacity)
		var mu sync.Mutex
		owned := map[int]int{}
		var statuses sync.Map
		parallel(120, func(i int) {
			n := 2 + rand.IntN(8)
			seats := rand.Perm(capacity)[:n]
			for j := range seats {
				seats[j]++
			}
			st, b, raw := book(t, inst(i), ev, fmt.Sprintf("k%d", i), seats)
			c, _ := statuses.LoadOrStore(st, new(atomic.Int64))
			c.(*atomic.Int64).Add(1)

					owned[s]++
				}

				t.Errorf("status %d %s", st, raw)
			}
		})

			if c > 1 {

			}
		}
		if got := sql1(t, fmt.Sprintf(`SELECT count(*) FROM booking_seats WHERE event_id=%d AND active`, ev)); got != fmt.Sprint(len(owned)) {
			t.Errorf("active rows=%s, seats acknowledged=%d", got, len(owned))
		}

	}
}

package blackbox

import (

// bookTolerant: returns status 0 on transport error, without failing the test.
func bookTolerant(base string, ev int64, key string, seats []int) (int, booking) {
	body := fmt.Sprintf(`{"event_id":%d,"seats":%s,"idempotency_key":%q}`, ev, strings.ReplaceAll(fmt.Sprint(seats), " ", ","), key)
	resp, err := hc.Post(base+"/bookings", "application/json", strings.NewReader(body))
	if err != nil {
		return 0, booking{}
	}
	defer resp.Body.Close()
	var b booking
	jsonDecode(resp.Body, &b)
	return resp.StatusCode, b
}

// kill -9 of instance A under load; every client retries with the same key on B.
// Expected: exactly one booking per key, seats intact, no orphans.
func TestKillAppMidLoadRetrySameKey(t *testing.T) {
	pid, _ := strconv.Atoi(os.Getenv("A_PID"))
	if pid == 0 {
		t.Skip("A_PID not set")
	}
	const n = 300
	ev := event(t, 2*n)
	var wg sync.WaitGroup
	var transportErr, firstOK, committedUnacked atomic.Int64
	acked := make([]int64, n)
	start := make(chan struct{})
	for i := 0; i < n; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			<-start
			seats := []int{2*i + 1, 2*i + 2}
			key := fmt.Sprintf("crash-%d", i)
			st, b := bookTolerant(A, ev, key, seats)
			if st == 201 || st == 200 {
				firstOK.Add(1)
				acked[i] = b.ID
			} else {
				transportErr.Add(1)
			}
			// always replay on B: client does not know if the first attempt committed
			st2, b2 := bookTolerant(B, ev, key, seats)
			if st2 != 200 && st2 != 201 {
				t.Errorf("replay key=%s status=%d", key, st2)
				return
			}
			if acked[i] == 0 && st2 == 200 {
				committedUnacked.Add(1)
			}
			if acked[i] != 0 && acked[i] != b2.ID {
				t.Errorf("key=%s acked id %d, replay id %d", key, acked[i], b2.ID)
			}
			if fmt.Sprint(b2.Seats) != fmt.Sprint(seats) {
				t.Errorf("key=%s seats=%v", key, b2.Seats)
			}
		}()
	}
	close(start)
	d, _ := time.ParseDuration(os.Getenv("KILL_DELAY"))
	if d == 0 {
		d = 15 * time.Millisecond
	}
	time.Sleep(d)
	exec.Command("kill", "-9", strconv.Itoa(pid)).Run()
	wg.Wait()
	t.Logf("first attempt ok=%d, failed on kill=%d, committed-but-unacknowledged=%d", firstOK.Load(), transportErr.Load(), committedUnacked.Load())
	if transportErr.Load() == 0 {
		t.Log("WARNING: kill did not interrupt anything; scenario inconclusive")
	}
	if v := sql1(t, fmt.Sprintf(`SELECT count(*) FROM bookings WHERE event_id=%d`, ev)); v != fmt.Sprint(n) {
		t.Errorf("bookings=%s want %d", v, n)
	}
	if v := sql1(t, fmt.Sprintf(`SELECT count(*) FROM booking_seats WHERE event_id=%d AND active`, ev)); v != fmt.Sprint(2*n) {
		t.Errorf("active seats=%s want %d", v, 2*n)
	}
	invariants(t, ev, 2*n)
}

		t.Skip("KILL_PG not set")
