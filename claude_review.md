## 2. Дефекты

### Д1. P2. Первый запуск может оставить приложение остановленным

**Файлы и строки:** `compose.yaml:13`, `compose.yaml:19-28` (нет `restart`), `cmd/booking/main.go:50-52`, `README.md:32-33`, `README.md:205-207`.

**Условие.** Первый `docker compose up` на пустом томе, когда инициализация PostgreSQL идёт медленно. Причина состоит из двух частей:

- Healthcheck вызывает `pg_isready` через unix-сокет. Он отвечает успехом от временного сервера инициализации образа, который не слушает TCP.
- Приложение не повторяет подключение и при первом отказе завершается с кодом 1. Политики перезапуска нет.

**Последствия.** `docker compose up -d` возвращает код 0, PostgreSQL работает, а API недоступен, пока оператор не запустит приложение снова. Данные не страдают. Формулировка README о «30-секундном тайм-ауте» создаёт впечатление, что короткую недоступность базы сервис переживёт. На деле при `connection refused` процесс завершился за миллисекунды: следующая команда записала лог уже через 8 мс.

**Доказательство.** Хронология на чистом каталоге данных:

```text
Обычная скорость:
t=3553ms socket_rc=0 tcp_rc=2   <- healthcheck уже видит успех, TCP закрыт
t=3646ms socket_rc=1 tcp_rc=2
t=4658ms socket_rc=2 tcp_rc=0   <- TCP открыт

Ограничение 0,15 CPU:
t=14282ms socket_rc=0 tcp_rc=2  <- окно перед открытием TCP около 3 с
t=14692ms socket_rc=1 tcp_rc=2
t=17304ms socket_rc=1 tcp_rc=0
```

Частота отказов при запуске на чистом томе:

| Условие | Отказы |
|---|---|
| Без ограничений | 0 из 37 |
| PostgreSQL ограничена 0,15 CPU | 2 из 18 |

Лог отказавшего запуска:

```text
round=5 up_rc=0 app=exited/1 healthz=000 "msg":"service stopped",
"error":"failed to connect to `user=booking database=booking`: 172.18.0.2:5432 (postgres): dial error: ... connect: c...
```

На этой VM без ограничения CPU дефект не проявился. Ограничение CPU эмулирует медленный хост и не меняет файлы проекта.

**Воспроизведение:** `bash $S/fresh_compose.sh 12 -f $S/slow-pg.override.yaml` (тексты в приложении).

**Направление исправления.** Проверять готовность по TCP (`pg_isready -h 127.0.0.1 ...`) и добавить хотя бы одно из двух: повтор подключения в пределах уже заявленного тайм-аута или `restart: on-failure`. Уточнить README.

### Д2. P2. Внутренние ошибки нигде не записываются

**Файлы и строки:** `internal/booking/handler.go:250-252`, `internal/booking/handler.go:42-44`, `cmd/booking/main.go:60`.

**Условие.** Любая ошибка базы или неожиданное состояние в обработчике. Параметр ошибки в `internalError` отброшен, а логгер в обработчик не передаётся. Журнала запросов тоже нет.

**Последствия.** Клиент корректно получает обобщённый `500`, но оператор не может узнать причину. Отказы в логах сервиса не видны.

**Доказательство.** PostgreSQL остановлена, сервис работает:

```text
healthz            -> 503 database_unavailable
POST /events       -> 500 internal_error
GET /bookings/{id} -> 500 internal_error
new app log lines during outage: 0
```

**Направление исправления.** Передать `*slog.Logger` в обработчик и писать ошибку с методом и маршрутом. Клиенту по-прежнему возвращать обобщённое сообщение.

### Д3. P2. Операции с базой не ограничены по времени

**Файлы и строки:** `internal/booking/handler.go:42`, `:70`, `:94`, `:107`, `:144`, `:169`, `:176` (используется только `r.Context()`), `cmd/booking/main.go:44`, `:49`, `:63`, `:74-77`.

**Условие.** Строка события надолго заблокирована извне (ручной запрос, транзакция администратора, миграция) либо база зависла. Через API удержать транзакцию нельзя: тело читается до её начала, а запись ответа идёт после её завершения.

**Последствия.**

- `WriteTimeout` не отменяет контекст обработчика, поэтому запросы ждут, пока жив клиент.
- 20 ожидающих запросов занимают весь пул. Экземпляр перестаёт отвечать на все маршруты, включая `/healthz` и чтение других событий.
- После `SIGTERM` процесс не завершается за заявленные 10 с: `pool.Close()` ждёт возврата соединений. В Docker это закончится `SIGKILL`.

Целостность не страдает: после снятия блокировки инварианты верны.

**Доказательство.** Внешняя сессия 75 с держит `FOR UPDATE` на одном событии, запущено 25 запросов брони:

```text
backends: 21 total, waiting=20
healthz on saturated pool:  [000] 4.03s (клиентский лимит 4 с)
GET other event:            [000] 4.02s
t=43s (WriteTimeout=30s passed) responses so far: 0
все 25 клиентов не получили ответа за 70 с
still running 12s after SIGTERM (Shutdown limit 10s)
process exit rc=1 after 31s from SIGTERM; error "context deadline exceeded"
```

**Воспроизведение:**

```bash
docker exec crv-pg psql -q -U crv -d l1 -c "begin; select id from events where id='$E' for update; select pg_sleep(75); rollback;" &
for i in $(seq 1 25); do curl -s -o /dev/null -m 70 -w "%{http_code} %{time_total}\n" \
  -H 'Content-Type: application/json' -d "{\"event_id\":\"$E\",\"seats\":1,\"idempotency_key\":\"stuck-$i\"}" \
  127.0.0.1:18081/bookings & done
curl -m4 127.0.0.1:18081/healthz
```

**Направление исправления.** Добавить тайм-аут на запрос или транзакцию (`context.WithTimeout`, либо `lock_timeout` и `statement_timeout`) и отображать его в `503`. Для `/healthz` задать короткий собственный тайм-аут. При завершении отменять контекст запросов до `pool.Close()`.

### Д4. P2. PostgreSQL опубликована на всех интерфейсах со слабым паролем и ролью суперпользователя

**Файлы и строки:** `compose.yaml:6-9`, `compose.yaml:22`, `README.md:14-15`.

**Условие.** Запуск compose на хосте, адрес которого доступен другим машинам.

**Последствия.** Любой, кто достиг порта, получает полный доступ к данным и выполнение команд в контейнере PostgreSQL. README называет конфигурацию демонстрационной, но не предупреждает о сетевой доступности. Docker публикует порты в обход типичных правил локального файрвола: это общеизвестное поведение, в этой проверке отдельно не проверялось.

**Доказательство** (только собственный тестовый контейнер):

```text
LISTEN 0.0.0.0:5432, [::]:5432
psql -h 10.0.2.15 -U booking -> connected as booking, superuser=true
copy o from program 'id'     -> uid=70(postgres) gid=70(postgres)
```

**Направление исправления.** Убрать публикацию порта или привязать его к `127.0.0.1`. Брать пароль из окружения. Для приложения завести отдельную роль без прав суперпользователя.

### Д5. P3. Команда тестов из README падает на чистом томе

**Файлы и строки:** `README.md:186-188`.

**Условие.** `docker compose up -d postgres` на новом томе и сразу `go test`. Команда не ждёт готовности базы.

**Последствия.** Все тесты падают из-за окружения, хотя код исправен. При точном следовании README это выглядит как поломка проекта.

**Доказательство:**

```text
--- FAIL: TestMigrationAndPersistence (0.01s)
    create test schema: failed to connect ... read: connection reset by peer
```

После перехода контейнера в `healthy` все 5 тестов прошли.

**Направление исправления.** Использовать `docker compose up -d --wait postgres`. Флаг `--wait` опирается на тот же healthcheck, поэтому надёжным он станет только вместе с исправлением Д1.

### Д6. P3. Тесты не покрывают большую часть валидации и несколько заявленных свойств

**Файлы и строки:** `internal/booking/integration_test.go:349-355` (все проверки ошибок запросов), `:113-129` (сохранность), нет тестов для `cmd/booking`.

**Условие.** Регрессия в валидации, в лимитах, в `/healthz` или в блокировке миграции.

**Последствия.** Такие регрессии не будут обнаружены. Ключевая логика при этом защищена хорошо: все 6 мутаций конкурентности и отмены убиты.

**Доказательство.** Покрытие 67,1 % операторов; `health`, `Ping` и `internalError` имеют 0 %. Результаты мутаций на копии проекта:

```text

  store: cancel does not release seats
```

Выжившие мутации схемы ожидаемы: `CHECK` и `UNIQUE` здесь работают как второй рубеж защиты. Остальное — реальные пробелы. Кроме того:

- Заявленная в README безопасность параллельной миграции (`README.md:169-170`) тестом не подтверждена, хотя при ручной проверке она выполнилась.
- Тест бронирования использует только запросы на одно место и не проверяет смешанную нагрузку.
- `go test ./...` без `TEST_DATABASE_URL` пишет `ok`, пропустив все тесты. README об этом предупреждает, но в CI такой запуск можно принять за успех.

**Воспроизведение:** `bash $S/mutate.sh <проект> "$TEST_DATABASE_URL"`.

**Направление исправления.** Табличный тест валидации, тест параллельного `Migrate`, смешанный конкурентный тест с проверкой `booked_seats = SUM(active seats)`.

### Д7. P3. В текст ошибки 400 попадают внутренние детали

**Файлы и строки:** `internal/booking/handler.go:221`.

**Условие.** Тело JSON неверного типа или прерванное чтение тела. Сообщение ошибки декодера и сети возвращается клиенту как есть.

**Последствия.** Раскрываются определение Go-структуры и внутренние адрес и порт контейнера. Сообщения также неудобны для клиента, а тайм-аут чтения выдаётся за ошибку JSON. Прямого пути к компрометации нет.

**Доказательство:**

```text
POST /events '[]' ->
  invalid JSON: json: cannot unmarshal array into Go value of type
  struct { Title string "json:\"title\""; Capacity int "json:\"capacity\"" }

Частичное тело, ожидание 15 с ->
```

**Направление исправления.** Различать типы ошибок (`json.SyntaxError`, `json.UnmarshalTypeError`, `http.MaxBytesError`, сетевые) и возвращать стабильные сообщения с именем поля.

### Д8. P3. Разные невалидные ключи идемпотентности схлопываются в один

**Файлы и строки:** `internal/booking/handler.go:126`, `:140`.

**Условие.** Ключ содержит одиночный суррогат или байты не UTF-8. `encoding/json` заменяет их на U+FFFD до проверки.

**Последствия.** Разные ключи считаются одним. Вторая операция с теми же `event_id` и `seats` вместо новой брони получает чужую, а при других параметрах получает `409`. Условие узкое: клиент должен прислать некорректный ключ.

**Доказательство.** Создана одна запись с ключом в hex `efbfbd`:

```text
"\ud800"  -> 201, id=a9ae3a15-...
"\ud801"  -> 200, id=a9ae3a15-...
байт 0xFF -> 200, id=a9ae3a15-...
```

**Воспроизведение:** блок `surrogate key` в `validation.sh` (см. приложение).

**Направление исправления.** Отклонять ключи с U+FFFD или ограничить допустимый набор символов и описать это в README.

### Д9. P3. `pool_max_conns` из `DATABASE_URL` молча игнорируется

**Файлы и строки:** `cmd/booking/main.go:44`.

**Условие.** Оператор задаёт размер пула штатным параметром pgx.

**Последствия.** Настройка не действует и об этом не сообщается. При малом `max_connections` или нескольких экземплярах размер пула нельзя уменьшить без пересборки.

**Доказательство.** С `pool_max_conns=2` под нагрузкой: `backends_v1=20`.

**Направление исправления.** Применять значение 20 только когда параметр не задан, либо описать ограничение в README.

### Д10. P3. Повторная миграция берёт блокировку `SHARE` на `bookings`

**Файлы и строки:** `internal/booking/migrate.go:31-32`, `README.md:202-204`.

**Условие.** Старт ещё одного экземпляра при открытой длинной транзакции записи в `bookings`. `CREATE INDEX IF NOT EXISTS` запрашивает блокировку таблицы, даже если индекс уже есть.

**Последствия.** Создание и отмена броней на уже работающих экземплярах встают в очередь за миграцией, а новый экземпляр завершается через 30 с. Данные не страдают, чтение работает. При обычных миллисекундных транзакциях влияние незаметно: 10 перезапусков под нагрузкой дали 0 ответов 5xx и 0 взаимоблокировок.

**Доказательство:**

```text
Внешний писатель открыт, миграции нет:  m2 201 за 0.013s
Старт второго экземпляра, ожидание:     CREATE INDEX IF NOT EXISTS ... | Lock
Бронь через работающий экземпляр:       m3 нет ответа за 6 с (лимит клиента)
Чтение через работающий экземпляр:      200 за 0.004s
Второй экземпляр: rc=1 через 30 с, "apply schema: timeout: context deadline exceeded"
```

**Воспроизведение:**

```bash
docker exec crv-pg psql -q -U crv -d r1 -c "begin; update bookings set seats=seats where id='$BI'; select pg_sleep(40); rollback;" &
sleep 1
HTTP_ADDR=127.0.0.1:18082 DATABASE_URL="$DATABASE_URL" "$S/bin/booking" &
sleep 2
curl -m6 -H 'Content-Type: application/json' -d "{\"event_id\":\"$E\",\"seats\":1,\"idempotency_key\":\"m3\"}" 127.0.0.1:18081/bookings
```

**Направление исправления.** Сначала проверять наличие схемы без DDL (например, таблицу версий), либо задать `lock_timeout` на миграцию.

## 3. Неподтверждённые риски и необязательные рекомендации

### Неподтверждённые риски

- **Мягкая взаимоблокировка при миграции под нагрузкой.** Теоретически возможен цикл: отмена держит `bookings` и ждёт событие, создание держит событие и стоит в очереди на `bookings` за миграцией, миграция ждёт отмену. PostgreSQL должен разрешить такой цикл перестановкой очереди, возможна пауза порядка `deadlock_timeout`. В 10 перезапусках под нагрузкой не воспроизведено.
- **`.env` попадает в контекст сборки.** Файл есть в `.gitignore`, но не в `.dockerignore`, а `Dockerfile:6` выполняет `COPY . .`. Секрет может остаться в кеше сборочного этапа. В итоговый образ копируется только бинарник. Сценарий не запускался, вывод сделан по файлам.
- **Плавающие теги образов** (`Dockerfile:1`, `Dockerfile:9`, `compose.yaml:3`). Будущие сборки могут получить другое содержимое. Сейчас сборка без кеша проходит.

### Необязательные рекомендации

- Возвращать `413` вместо `400` для тела больше 1 МиБ (сейчас ограничение работает, статус на усмотрение автора).
- `README.md:38` обещает JSON во всех ответах, но `net/http` отдаёт не-JSON в служебных случаях: `//events` даёт `307`, слишком большой заголовок — `431 text/plain`. Достаточно уточнить README.
- `cmd/booking/main.go:68` пишет «HTTP server started» до привязки порта: при занятом порте в логе сначала идёт успех, потом ошибка. Лучше вызывать `net.Listen` до записи.
- Описать в README запуск двух экземпляров. `docker compose up --scale app=2` падает из-за фиксированного порта 8080. Это не нарушает TASK.md: второй контейнер того же образа работает корректно.
- Описать в README, что `insufficient_capacity` не запоминается: повтор с тем же ключом после освобождения мест может создать бронь. Это разумная семантика, сейчас она явно не описана (`store.go:161-163`).
- `store.go:224-226` отобразился бы в `404 booking not found` при отсутствии события. Сейчас ветка недостижима из-за внешнего ключа, замечание касается только будущих изменений.

## 4. Архитектура

**Общая оценка: решение соразмерно задаче.** Около 700 строк кода без тестов в двух пакетах, из прямых зависимостей только `pgx` и `uuid`, нет фреймворка и лишних слоёв. Новый читатель проходит путь запроса за несколько минут. Избыточности почти нет, а основные упрощения, которые мешают поддержке, легко исправить.

| Аспект | Оценка | Пример и последствия |
|---|---|---|
| Разделение ответственности | Хорошо | `handler.go` отвечает за HTTP и валидацию формы запроса, `store.go` — за SQL и транзакции, `types.go` — за модель и ошибки, `main.go` — за сборку |
| Направление зависимостей | Хорошо | `main` → `booking` → `pgx`. Ошибки хранилища сводятся к доменным (`ErrNotFound`, `CapacityError`), HTTP-коды знает только обработчик |
| Бизнес-инварианты | Хорошо | Проверка вместимости находится внутри транзакции под блокировкой строки (`store.go:151-163`), а `CHECK` в схеме даёт второй рубеж (`migrate.go:14`). Инвариант не обойти даже при ошибке в коде |
| Границы транзакций | Хорошо | Один метод хранилища равен одной транзакции. Порядок блокировок постоянный: ключ → событие → вставка; для отмены бронь → событие. Циклов нет, 0 взаимоблокировок в проверках |
| Связанность | Приемлемо | `Handler` зависит от конкретного `*Store` (`handler.go:16`) |
| Тестируемость | Компромисс | Из-за прямой зависимости нельзя проверить обработчик без базы или подставить отказ. Отсюда 0 % покрытия у `internalError`. Плюс: тесты работают с настоящей PostgreSQL. Небольшой интерфейс оправдан только если понадобятся такие тесты |
| Понятность | Хорошо | Комментарии объясняют причину решений, например порядок блокировок (`store.go:131-132`) |
| Стоимость изменений | Средняя | См. ниже |

**Удачные компромиссы:**

- **Счётчик `booked_seats` в `events`.** Доступность читается за O(1), а блокировка одной строки просто сериализует брони. Цена в том, что брони одного события идут последовательно и счётчик дублирует данные. Для небольшого сервиса это оправдано; расхождение возможно только при ручной правке базы.
- **Advisory lock плюс `UNIQUE`.** Блокировка позволяет проверить ключ до вместимости и не получать ошибку уникальности внутри транзакции. Цена: лишний запрос и соединение, занятое на время ожидания. `UNIQUE` остаётся страховкой. Два механизма здесь не избыточны, у них разные роли.
- **Ручная маршрутизация** (`pathParts`, `handler.go:203`). Встроенные шаблоны Go 1.22+ сократили бы код, но их автоматические ответы 405 не в формате JSON. Менять не обязательно.

**Упрощения, затрудняющие поддержку:**

- **Логгер не доходит до обработчика** (`NewHandler(store)`). Это прямая причина Д2.
- **Нет версионирования миграций.** README это честно указывает. Для текущей задачи достаточно, но первое изменение таблицы потребует нового механизма. Миграция при каждом старте требует прав на DDL у роли приложения, что связано с Д4.
- **Лимиты повторяются.** Значение 200 записано в `types.go:12`, в сообщении `handler.go:63` и в `migrate.go:11`, `:22`; 1 000 000 — в `types.go:13` и в сообщениях `handler.go:67`, `:137`. Смена лимита затрагивает несколько мест и README.
- **Один длинный тест HTTP** (`integration_test.go:299-362`). Первый сбой скрывает остальные проверки, а добавлять случаи дорого. Табличный тест снизит цену и закроет часть Д6.

**Небольшая избыточность:** индекс `bookings_event_status_idx` (`migrate.go:31-32`) не используется ни одним запросом кода: брони ищутся только по `id` и ключу. Он добавляет стоимость записи и является источником блокировки из Д10. Его стоит добавить вместе с запросом, которому он нужен.

## 5. Безопасность

### Модель угроз и границы доверия

- **Недоверенная сторона:** HTTP-клиент; содержимое запросов считается враждебным.
- **Доверенные стороны:** оператор, переменные окружения, сеть между приложением и PostgreSQL, Docker-хост.
- **Вне рамок задания:** авторизация (прямо исключена TASK.md), TLS.
- **Ограничение:** активные проверки шли только против собственных контейнеров в этой VM, без тяжёлых нагрузочных атак.

### Неподтверждённые риски безопасности

- Переполнение диска массовым созданием событий и броней: ограничений нет, брони хранятся бессрочно (указано в README). Не проверялось, это нагрузочная атака.
- Много одновременных соединений: `MaxConns` ограничивает только базу, а не число HTTP-соединений. Не проверялось по той же причине.

### Архитектурные компромиссы

- **Общая роль для миграции и работы.** Упрощает запуск, но расширяет полномочия приложения.
- **Глобальные ключи идемпотентности.** Просто и описано в README, но при публичном доступе ключи разных клиентов конфликтуют.
- **Оболочка в итоговом образе.** Busybox нужен для `wget` в healthcheck; цена — немного большая поверхность атаки.

### Условия публичного развёртывания

Это не дефекты выполнения задания, а условия эксплуатации:

- Аутентификация и проверка владельца брони. Сейчас владелец UUID может отменить бронь, а знающий ключ и параметры запроса получит чужую бронь с её `id`. Предсказуемые ключи вроде `order-42` это облегчают.
- TLS на внешнем прокси или в самом сервисе.
- `sslmode=verify-full` вместо `sslmode=disable`, если база находится вне доверенной сети.
- Ограничение частоты запросов и квоты на обратном прокси.
- Закрытый порт PostgreSQL и секреты вне `compose.yaml`.

### Необязательные улучшения

- Для приложения в compose: `read_only: true`, `cap_drop: [ALL]`, `security_opt: [no-new-privileges:true]`, лимиты памяти и `pids`.
- Заголовок `X-Content-Type-Options: nosniff`.
- `.env` в `.dockerignore`.
- Закрепление образов по digest.

Отсутствие других находок не означает доказанную безопасность.

## 7. Сильные стороны

- Вместимость, идемпотентность и отмена реализованы на транзакциях и блокировках PostgreSQL, поэтому гарантии работают между экземплярами. Это подтверждено сбоями, а не только чтением кода.
- `CHECK`, `UNIQUE` и внешний ключ защищают данные даже при ошибке в коде.
- Потерянный ответ безопасен: повтор с тем же ключом возвращает уже созданную бронь, это наблюдалось при обрывах.
- Строгий разбор JSON с понятными кодами ошибок.
- Все значения передаются в SQL параметрами.
- Повторный запуск не теряет данные, а параллельный старт нескольких экземпляров на пустой базе прошёл без ошибок.
- Контейнер приложения не работает от root, образ небольшой, есть корректное завершение по `SIGTERM`.
- README точно описывает API и механизм идемпотентности и честно перечисляет ограничения.
- Тесты работают с настоящей PostgreSQL, изолированы случайными схемами и за собой убирают.
- Код небольшой и читается легко.

```go
// Stand-alone black-box harness for two running service instances.
// Usage: go run . -a http://127.0.0.1:18081 -b http://127.0.0.1:18082 -scenario all
// Prints event ids so that invariants can be checked in the database with psql.
package main

import (
	"bytes"
	"context"
	"encoding/json"
	"flag"
	"fmt"
	"io"
	"math/rand"
	"net/http"
	"os"
	"sync"
	"sync/atomic"
	"time"
)

var (
	urlA, urlB string
	client     = &http.Client{Transport: &http.Transport{MaxIdleConnsPerHost: 200, MaxConnsPerHost: 0}}
)

type resp struct {
	code int
	body map[string]any
	err  error
}

func call(ctx context.Context, method, url, body string) resp {
	var rd io.Reader
	if body != "" {
		rd = bytes.NewBufferString(body)
	}
	req, err := http.NewRequestWithContext(ctx, method, url, rd)
	if err != nil {
		return resp{err: err}
	}
	if body != "" {
		req.Header.Set("Content-Type", "application/json")
	}
	r, err := client.Do(req)
	if err != nil {
		return resp{err: err}
	}
	defer r.Body.Close()
	data, err := io.ReadAll(r.Body)
	if err != nil {
		return resp{err: err}
	}
	out := resp{code: r.StatusCode}
	_ = json.Unmarshal(data, &out.body)
	return out
}

func inst(i int) string {
	if i%2 == 0 {
		return urlA
	}
	return urlB
}

func createEvent(capacity int) string {
	r := call(context.Background(), "POST", urlA+"/events", fmt.Sprintf(`{"title":"harness","capacity":%d}`, capacity))
	if r.err != nil || r.code != 201 {
		fmt.Println("createEvent failed", r.code, r.err, r.body)
		os.Exit(2)
	}
	return r.body["id"].(string)
}

func availability(event string) map[string]any {
	return call(context.Background(), "GET", urlB+"/events/"+event+"/availability", "").body
}

func bookBody(event string, seats int, key string) string {
	return fmt.Sprintf(`{"event_id":%q,"seats":%d,"idempotency_key":%q}`, event, seats, key)
}

// Scenario 1: multi-seat requests with unique keys against a small event.
func oversell(runID string) {
	const capacity, requests = 100, 400
	event := createEvent(capacity)
	var wg sync.WaitGroup
	var sold, ok, conflict, other atomic.Int64
	for i := 0; i < requests; i++ {
		wg.Add(1)
		go func(i int) {
			defer wg.Done()
			seats := 1 + i%5
			r := call(context.Background(), "POST", inst(i)+"/bookings", bookBody(event, seats, fmt.Sprintf("%s-os-%d", runID, i)))
			switch {
			case r.err == nil && r.code == 201:
				sold.Add(int64(seats))
				ok.Add(1)
			case r.err == nil && r.code == 409:
				conflict.Add(1)
			default:
				other.Add(1)
				fmt.Println("  unexpected", r.code, r.err, r.body)
			}
		}(i)
	}
	wg.Wait()
	fmt.Printf("oversell event=%s capacity=%d sold=%d ok=%d conflict=%d other=%d availability=%v\n",
		event, capacity, sold.Load(), ok.Load(), conflict.Load(), other.Load(), availability(event))
}

// Scenario 2: the same key through both instances.
func idem(runID string) {
	const requests = 200
	event := createEvent(10)
	key := runID + "-idem"
	var wg sync.WaitGroup
	var mu sync.Mutex
	codes := map[int]int{}
	ids := map[string]int{}
	for i := 0; i < requests; i++ {
		wg.Add(1)
		go func(i int) {
			defer wg.Done()
			r := call(context.Background(), "POST", inst(i)+"/bookings", bookBody(event, 3, key))
			mu.Lock()
			defer mu.Unlock()
			if r.err != nil {
				codes[-1]++
				return
			}
			codes[r.code]++
			if id, ok := r.body["id"].(string); ok {
				ids[id]++
			}
		}(i)
	}
	wg.Wait()
	fmt.Printf("idempotency event=%s codes=%v distinct_ids=%d availability=%v\n", event, codes, len(ids), availability(event))
}

// Scenario 3: parallel cancellation of one booking through both instances.
func cancel(runID string) {
	const requests = 200
	event := createEvent(10)
	r := call(context.Background(), "POST", urlA+"/bookings", bookBody(event, 4, runID+"-cancel"))
	id := r.body["id"].(string)
	keep := call(context.Background(), "POST", urlA+"/bookings", bookBody(event, 2, runID+"-keep"))
	_ = keep
	var wg sync.WaitGroup
	var mu sync.Mutex
	codes := map[int]int{}
	stamps := map[string]int{}
	for i := 0; i < requests; i++ {
		wg.Add(1)
		go func(i int) {
			defer wg.Done()
			r := call(context.Background(), "DELETE", inst(i)+"/bookings/"+id, "")
			mu.Lock()
			defer mu.Unlock()
			if r.err != nil {
				codes[-1]++
				return
			}
			codes[r.code]++
			if s, ok := r.body["cancelled_at"].(string); ok {
				stamps[s]++
			}
		}(i)
	}
	wg.Wait()
	fmt.Printf("cancel event=%s codes=%v distinct_cancelled_at=%d availability=%v (expected booked=2)\n", event, codes, len(stamps), availability(event))
}

// Scenario 4: mixed load. Workers create bookings with client-side timeouts and
// retry the same key through the other instance until a definite answer arrives,
// then cancel a part of them, sometimes concurrently and with aborted requests.
// With -kill set, an instance may die in the middle; retries move to the other one.
func mixed(runID string, dur time.Duration, capacity int) {
	event := createEvent(capacity)
	deadline := time.Now().Add(dur)
	var wg sync.WaitGroup
	var created, replayed, full, aborted, cancelled, fivexx, netErr atomic.Int64
	for w := 0; w < 24; w++ {
		wg.Add(1)
		go func(w int) {
			defer wg.Done()
			rng := rand.New(rand.NewSource(int64(w) + time.Now().UnixNano()))
			for n := 0; time.Now().Before(deadline); n++ {
				key := fmt.Sprintf("%s-mix-%d-%d", runID, w, n)
				seats := 1 + rng.Intn(4)
				var id string
				for attempt := 0; attempt < 400; attempt++ {
					timeout := 2 * time.Second
					if rng.Intn(3) == 0 {
						timeout = time.Duration(rng.Intn(2500)) * time.Microsecond
					}
					ctx, stop := context.WithTimeout(context.Background(), timeout)
					r := call(ctx, "POST", inst(w+attempt)+"/bookings", bookBody(event, seats, key))
					stop()
					if r.err != nil {
						aborted.Add(1)
						continue
					}
					if r.code >= 500 {
						fivexx.Add(1)
						fmt.Println("  5xx on create:", r.code, r.body)
						continue
					}
					switch r.code {
					case 201:
						created.Add(1)
						id = r.body["id"].(string)
					case 200:
						replayed.Add(1)
						id = r.body["id"].(string)
					case 409:
						full.Add(1)
					default:
						fmt.Println("  unexpected create:", r.code, r.body)
					}
					break
				}
				if id == "" || rng.Intn(10) < 3 {
					if id == "" {
						time.Sleep(time.Millisecond)
					}
					continue
				}
				// Cancel: parallel duplicates through both instances, with retry until definite.
				var cw sync.WaitGroup
				for c := 0; c < 3; c++ {
					cw.Add(1)
					go func(c int) {
						defer cw.Done()
						for attempt := 0; attempt < 400; attempt++ {
							ctx, stop := context.WithTimeout(context.Background(), time.Duration(200+rng2(c, attempt)*20)*time.Millisecond)
							r := call(ctx, "DELETE", inst(w+c+attempt)+"/bookings/"+id, "")
							stop()
							if r.err != nil {
								netErr.Add(1)
								continue
							}
							if r.code >= 500 {
								fivexx.Add(1)
								fmt.Println("  5xx on cancel:", r.code, r.body)
								continue
							}
							if r.code == 200 {
								cancelled.Add(1)
							} else {
								fmt.Println("  unexpected cancel:", r.code, r.body)
							}
							return
						}
					}(c)
				}
				cw.Wait()
			}
		}(w)
	}
	wg.Wait()
	fmt.Printf("mixed event=%s capacity=%d created=%d replayed=%d full=%d aborted_create_attempts=%d cancel_ok=%d cancel_net_err=%d 5xx=%d availability=%v\n",
		event, capacity, created.Load(), replayed.Load(), full.Load(), aborted.Load(), cancelled.Load(), netErr.Load(), fivexx.Load(), availability(event))
}

func rng2(a, b int) int { return (a*31 + b*17) % 50 }

func main() {
	flag.StringVar(&urlA, "a", "http://127.0.0.1:18081", "instance A")
	flag.StringVar(&urlB, "b", "http://127.0.0.1:18082", "instance B")
	scenario := flag.String("scenario", "all", "oversell|idem|cancel|mixed|all")
	dur := flag.Duration("dur", 20*time.Second, "mixed duration")
	capacity := flag.Int("capacity", 60, "mixed capacity")
	flag.Parse()
	runID := fmt.Sprintf("%d", time.Now().UnixNano())
	if *scenario == "all" || *scenario == "oversell" {
		oversell(runID)
	}
	if *scenario == "all" || *scenario == "idem" {
		idem(runID)
	}
	if *scenario == "all" || *scenario == "cancel" {
		cancel(runID)
	}
	if *scenario == "all" || *scenario == "mixed" {
		mixed(runID, *dur, *capacity)
	}
}
```

### `invariants.sql`

```sql
-- Must return zero rows: stored counter differs from the sum of active bookings or exceeds capacity.
SELECT e.id, e.capacity, e.booked_seats, COALESCE(sum(b.seats) FILTER (WHERE b.status='active'),0) AS active_sum
FROM events e LEFT JOIN bookings b ON b.event_id = e.id
GROUP BY e.id
HAVING e.booked_seats <> COALESCE(sum(b.seats) FILTER (WHERE b.status='active'),0)
    OR e.booked_seats > e.capacity OR e.booked_seats < 0;
SELECT 'events='||count(*) FROM events;
SELECT 'bookings='||count(*)||' active='||count(*) FILTER (WHERE status='active')||' cancelled='||count(*) FILTER (WHERE status='cancelled') FROM bookings;
SELECT 'duplicate_keys='||count(*) FROM (SELECT idempotency_key FROM bookings GROUP BY 1 HAVING count(*)>1) x;
```

```bash
#!/bin/bash
# Fresh-volume first start, repeated. Uses a private compose project name.
# Args: rounds [extra compose -f args...]
# Project files are only read; the private project and its volume are removed each round.
P=/home/petr/review/project
ROUNDS=$1; shift
EXTRA=("$@")
fail=0
for r in $(seq 1 "$ROUNDS"); do
  NAME=crv-fresh
  docker compose -p $NAME --project-directory $P -f $P/compose.yaml "${EXTRA[@]}" up -d >/dev/null 2>/tmp/booking-review/logs/up.err
  uprc=$?
  sleep 3
  state=$(docker inspect -f '{{.State.Status}}/{{.State.ExitCode}}' $NAME-app-1 2>/dev/null)
  err=$(docker logs $NAME-app-1 2>&1 | grep '"ERROR"' | cut -c50-220)
  code=$(curl -s -o /dev/null -m3 -w '%{http_code}' http://127.0.0.1:8080/healthz)
  echo "round=$r up_rc=$uprc app=$state healthz=$code ${err}"
  [ "$code" = 200 ] || fail=$((fail+1))
  docker compose -p $NAME --project-directory $P -f $P/compose.yaml "${EXTRA[@]}" down -v >/dev/null 2>&1
done
echo "failed_rounds=$fail of $ROUNDS"
```
