# Независимое техническое ревью

Дата: 2026-11-06. Проверены TASK.md, README.md, OpenAPI, исходники, Dockerfile, compose.yaml и автоматические тесты. Реализация, зависимости и штатные тесты не изменялись. Собственные проверки находятся в `/tmp/codex-independent-review`, их полный текст приведён ниже. Другие агенты, соседние проекты и готовые решения не использовались.

## Заключение

Основные требования TASK.md выполнены: HTTP JSON API работает, данные сохраняются, перепродажа и повторный возврат мест предотвращаются транзакциями PostgreSQL, идемпотентность действует между экземплярами и переживает перезапуск. Сборка Docker и запуск двух экземпляров воспроизведены. Полный штатный набор тестов с настоящей PostgreSQL прошёл; независимые HTTP-проверки также подтвердили основные гарантии.

Обнаружены два подтверждённых дефекта: P2 в классификации недоступности БД и P3 в обработке нижней границы допустимой даты. Они не опровергают подтверждённые гарантии сохранности и конкурентности. Дефектов P0/P1 и подтверждённых уязвимостей безопасности в пределах выполненных проверок не обнаружено. Это не доказательство отсутствия иных ошибок или уязвимостей.

## Подтверждённые дефекты

### 1. P2 — недоступность БД возвращает 500 вместо документированного 503

**Место:** `internal/handler/rest/errors.go:69–77`, прежде всего ветка `default` на строках 75–77.

**Условие:** после успешного запуска сервиса PostgreSQL становится недоступной; драйвер возвращает ошибку подключения раньше истечения контекстного таймаута. Проверка `r.Context().Err()` не распознаёт такую ошибку как недоступность зависимости, поэтому она превращается в `internal_error`.

**Последствие:** клиент получает неверную классификацию временного отказа. Обещанный в README машинный код `service_unavailable` отсутствует, обработка повторов и мониторинг по 503 могут работать неправильно. Повтор бронирования с прежним ключом остаётся безопасным; потери данных в этом сценарии не обнаружено. Требование конкретного статуса не добавляется к TASK.md: замечание относится к контракту, выбранному и описанному самим решением.

**Доказательство:** на собственном compose-проекте после `stop postgres`:

```text
GET /events  -> 500 {"error":{"code":"internal_error","message":"internal server error"}}
GET /healthz -> 503 {"error":{"code":"service_unavailable","message":"the database is unavailable"}}
```

В журнале `/events` зафиксирована ошибка разрешения имени остановленного контейнера PostgreSQL, а не программная ошибка бизнес-логики; ответ получен примерно за 27 мс, до таймаута. Отказ базы намеренно вызван тестом, дефектом считается именно его отображение в API.

**Воспроизведение:** запустить compose командой из раздела проверок, выполнить `docker compose -p codex-independent-review stop postgres`, затем `python3 /tmp/codex-independent-review/check.py outage`. Полный текст скрипта ниже. После проверки восстановить базу через `up --wait`.

**Направление исправления:** различать ошибки недоступности зависимости и внутренние ошибки, передавать устойчивую категорию ошибки из адаптера PostgreSQL в HTTP-слой и возвращать для неё 503. Добавить тест отказа уже работающей базы; не превращать без разбора все SQL-ошибки в 503.

### 2. P3 — допустимая дата совпадает с Go zero time и считается отсутствующей

**Место:** `internal/service/event/service.go:38–42`; транспортное поле — `internal/handler/rest/gen/server.gen.go:76–77`.

**Условие:** явно передать `starts_at: "0001-01-01T00:00:00Z"`. README разрешает годы от 1 до 9999 UTC, но эта конкретная дата совпадает с нулевым значением `time.Time`.

**Последствие:** корректный по описанным допущениям запрос отклоняется с неверным сообщением `starts_at: is required`. Другие события и данные не повреждаются. Практическая значимость невелика, поэтому P3.

**Доказательство:** независимый HTTP-запрос с телом

```json
{"name":"Boundary","starts_at":"0001-01-01T00:00:00Z","capacity":1}
```

вернул 400 `validation_failed`, поле `starts_at`, сообщение `is required`. Этот запрос включён в скрипт ниже.

**Направление исправления:** отдельно учитывать присутствие обязательного поля, например указателем или признаком присутствия при декодировании; не использовать допустимое значение времени как признак отсутствия. Либо явно сузить документированный диапазон, если это осознанное ограничение API.

## Архитектура

Решение в целом соразмерно небольшой задаче. Есть один исполняемый файл и одна PostgreSQL, нет распределённого состояния в памяти, дополнительных брокеров или инфраструктурных сервисов. `internal/app/app.go:43–84` служит понятной точкой сборки зависимостей и жизненного цикла.

Направление зависимостей выдержано: HTTP-адаптер зависит от интерфейсов сервисов (`internal/handler/rest/dependency.go`), сервисы — от интерфейсов репозитория (`internal/service/{booking,event}/dependency.go`), реализация PostgreSQL использует общие модели. Сервисы не импортируют HTTP и pgx. Это позволяет отдельно проверять валидацию и отображение ошибок, а транзакционные свойства — интеграционно. Общий пакет `model` также содержит команды чтения/записи и ошибки: связь слоёв явная, хотя при расширении API изменение одной операции потребует синхронно обновить OpenAPI, маппинг, команды и моки.

Критические бизнес-инварианты находятся в транзакционных методах репозитория, а не только в сервисном слое. Для этой задачи это оправданно: проверка доступности, вставка бронирования и увеличение счётчика должны составлять одну атомарную операцию (`internal/repository/postgres/booking.go:27–82`). Блокировка `FOR NO KEY UPDATE` сериализует операции одного события, не конфликтуя с обычной проверкой внешнего ключа. Проверка повтора выполняется до проверки остатка; поэтому повтор успешного запроса работает даже на заполненном событии. Глобальный UNIQUE и обработка `ON CONFLICT` закрывают гонку одинакового ключа между разными событиями. Всё это проверено на настоящей БД.

Отмена использует условный UPDATE статуса и возврат мест в одной транзакции (`booking.go:159–196`). Повторная отмена читает уже отменённое бронирование, не меняя счётчик. По рассмотренным путям блокировок цикла не обнаружено: создание блокирует событие и вставляет новую строку, отмена блокирует существующее бронирование и затем событие; повторное создание читает существующее бронирование без блокировки. Конкурентные и смешанные штатные тесты прошли.

Денормализованный `events.booked_seats` позволяет быстро читать доступность и ограничивать перепродажу CHECK-ограничением. Цена — необходимость изменять счётчик только вместе с бронированием. Схема сама не доказывает равенство счётчика сумме активных бронирований; его поддерживает репозиторий. Это приемлемо при единственном доверенном пути записи через приложение. Штатный `requireSeats` и независимый SQL-запрос проверяют именно это равенство, а не только попадание в диапазон.

Блокировка строки события ограничивает пропускную способность популярного события, но делает доказательство корректности простым. Пагинация offset также проста, имеет индекс по порядку выдачи и ограниченный размер страницы, но дорожает на больших смещениях. Оба компромисса явно раскрыты в README; оснований требовать другой архитектуры для данного TASK.md нет.

Миграции встроены в бинарник и выполняются транзакционно под advisory lock (`migrate.go:28–61`), с проверкой checksum применённого файла (`:72–94`). Это небольшой механизм с ограниченным назначением; параллельный первый запуск, повтор без потери данных и несовпадение checksum покрыты тестами. Отдельная библиотека миграций здесь не обязательна. Автомиграции упрощают локальный запуск, но связывают runtime-процесс с правами изменения схемы.

Есть умеренная цена формализации: одинаковые по полям `CreateServiceCommand` и `CreateRepositoryCommand`, интерфейсы и сгенерированные моки для коротких методов Fetch/Cancel. Они обозначают границу нормализации и упрощают изоляцию тестов, но часть тестов проверяет преимущественно передачу аргументов. Генерация HTTP-кода из OpenAPI добавляет объём кода, зато контракт находится в одном явном месте. Это компромиссы поддержки, а не подтверждённые дефекты или повод требовать иное количество слоёв.

## Безопасность

### Модель угроз и границы доверия

Рассматривается недоверенный HTTP-клиент, способный присылать произвольные JSON, пути, параметры и ключи, в том числе конкурентно. Процесс приложения, DATABASE_URL, схема и сервер БД считаются доверенными. Границы: HTTP → разбор и валидация → транзакционный адаптер → PostgreSQL; отдельно — окружение запуска и доступ к журналам. Активные запросы направлялись только собственным контейнерам на локальных портах VM, без внешних целей и тяжёлой нагрузки (не более 16 одновременных клиентов собственного скрипта).

Отсутствие авторизации разрешено TASK.md и не считается дефектом. Публичное развёртывание требует отдельно определить контроль доступа, доступность данных бронирований и TLS. Любой имеющий сетевой доступ клиент сейчас может читать/отменять любые бронирования и создавать новые данные — это известная модель API, а не найденный обход авторизации.

### Проверенные свойства

- **SQL-инъекции:** значения передаются через параметры `$1…`, включая имена и ключи. Динамическое построение SQL в рабочем коде использует константный список колонок и встроенные миграции, а не HTTP-ввод. Независимый запрос с именем `x'); DROP TABLE events; --` сохранил строку буквально; таблица осталась доступна. Этот пример дополняет анализ SQL, но не заменяет полный аудит драйвера.
- **Недоверенный JSON:** `decode.go:18–44` проверяет Content-Type, ограничивает читаемое тело 1 МиБ, запрещает неизвестные поля и требует EOF после единственного значения. Числа транспорта имеют тип int32, затем проверяется положительность. Текст ограничен 200 символами и проверяется на управляющие символы; ключ ограничен 255 печатными ASCII-байтами. Штатные и собственные проверки отрицательных/переполненных чисел, лишних полей, второго JSON и превышения размера прошли.
- **Ресурсы и таймауты:** HTTP задаёт 5 с на заголовки, 15 с на чтение, 20 с на запись и 60 с idle; операции получают контекст 10 с (`app.go:28–32,74–80`, `server.go:64–71`). Контекст сам по себе не прерывает чтение тела, его ограничивает ReadTimeout. Пул ограничивает подключения; результаты списков ограничены 200 записями. Нет явного лимита числа ожидающих HTTP-запросов, rate limit или квоты роста таблиц — оценка этих условий вынесена ниже, отказ в обслуживании экспериментально не демонстрировался.
- **Ошибки и журналы:** HTTP скрывает неожиданные внутренние ошибки за общим сообщением, что подтверждено тестами и сценарием отключения БД. Журнал запросов содержит метод, шаблон маршрута, статус и длительность, не тела и не Idempotency-Key. Ошибки драйвера попадают в операторский журнал; в просмотренном журнале недоступности БД пароль не обнаружен. По исходнику используемого pgx проверено наличие редактирования пароля в ParseConfigError; исчерпывающая проверка всех ошибочных строк подключения не проводилась. Найденная ошибка 500/503 описана отдельно и не является утечкой.
- **Контейнеры и порты:** приложение работает от UID 10001 (`Dockerfile:11–13`), runtime-образ не содержит Go toolchain. PostgreSQL не публикует порт хоста; приложения публикуют 8080/8081 на всех интерфейсах по умолчанию (`compose.yaml:38–46`). Пароль учебный, соединение без TLS — это прямо раскрыто README. Учётная запись `POSTGRES_USER=booking` одновременно служит приложению и администратору инициализации БД; для публичного окружения следует ограничить её права и отделить миграции. Доказательства компрометации контейнера или SQL-инъекции нет.

### Неподтверждённые риски и необязательные рекомендации

1. При открытом доступе и большом числе запросов возможны рост таблиц без квот, очереди ожидания блокировки популярного события, расход goroutine/памяти и заполнение логов. Ограничения времени и размера смягчают это, но не дают общего предела потребления. Массовая нагрузка и предел отказа не измерялись. Для соответствующего развёртывания полезны сетевой контроль, ограничение частоты/конкурентности и мониторинг; это не новое требование TASK.md.
2. Глобальные ключи без привязки к клиенту требуют непредсказуемости; README рекомендует UUID. Коллизии/подбор могут приводить к 422 либо раскрытию существующего бронирования при точном совпадении данных. Это известное следствие разрешённой модели без авторизации, не доказанная уязвимость с новым нарушением границы доступа. Ключи и бронирования не истекают — объём хранилища нужно планировать.
3. Для публичного размещения: TLS на доверенном входе, секреты вне compose, минимальные права БД, при необходимости read-only filesystem/capability/resource limits контейнеров. Без этих предпосылок учебный compose не следует считать готовым публичным сервисом. В рамках локальной задачи это рекомендации, а не дефекты.
4. Семантика стандартного `encoding/json` допускает повторяющиеся ключи и сопоставление имён без учёта регистра. Это не противоречит явно заявленному запрету неизвестных полей; при добавлении прокси/подписей/второго JSON-парсера стоит унифицировать трактовку неоднозначного JSON. Эксплуатация через разные парсеры не проверялась и не подтверждена.
5. Проверка зависимостей по базам известных уязвимостей (govulncheck, Trivy и т. п.) не выполнялась. Зафиксированные версии и успешные тесты не доказывают отсутствия CVE или применимости/неприменимости конкретных уязвимостей.

### Что действительно покрывают штатные тесты

Репозиторий тестируется на настоящей PostgreSQL с отдельной БД для каждого теста. Проверяются перепродажа, одинаковый ключ на одном и разных событиях, ожидание чужого незавершённого INSERT ключа с последующим COMMIT/ROLLBACK, повтор после заполнения события и после отмены, конкурентные отмены и смешивание отмен с новыми бронированиями. Проверка состояния сравнивает счётчик с суммой подтверждённых бронирований. Миграции проверяются на пустой БД, параллельно, повторно и при изменённом checksum.

E2E запускают два реальных процесса на общей PostgreSQL, отправляют конкурентные HTTP-запросы, проверяют корректное завершение по SIGTERM и сохранность после SIGKILL с повторной миграцией. Это сильнее тестов только с моками. Ограничение: дочерний бинарник e2e собирается обычным `go build`, без `-race`; опция `go test -race` инструментирует тестовый процесс и интеграционные пакеты, но не этот дочерний сервер. Инварианты серверов в e2e проверяются функционально.

### Не выполнено и ограничения

- Не запускались govulncheck, сканер контейнеров, fuzzing, длительный soak/нагрузочный тест, массовый slowloris, испытания нехватки диска/памяти и повреждения файлов БД. Это выходит за выбранную ограниченную проверку; безопасность не объявляется доказанной.
- Не проверялись сетевые разрывы непосредственно в момент COMMIT и авария самого PostgreSQL/хоста. Перезапуск приложения с SIGKILL покрыт штатным e2e; остановка/старт PostgreSQL и сохранность уже подтверждённых данных проверены отдельно, но не эквивалентны аварийному восстановлению хоста.
- Генераторы не запускались, поскольку `go generate ./...` перезаписывает файлы проверяемой реализации, что запрещено инструкцией. Использованы предоставленные сгенерированные файлы.
- Не тестировались внешняя инфраструктура, TLS и аутентификация; по TASK.md они не обязательны. Не проверялись альтернативные версии PostgreSQL/Go и операционные системы.
- Не вводились намеренно некорректные записи напрямую в БД вне штатных интеграционных тестов: оценка гарантий относится к поддерживаемому API и доверенной схеме.

## Сильные стороны

- Атомарные операции с понятными инвариантами, контролируемые самой БД и работающие между процессами.
- Корректный порядок разрешения повтора до проверки остатка и обработка глобальной гонки ключей.
- Отмена сохраняет время первого выполнения и возвращает места единожды.
- Транзакционная подготовка схемы, защита параллельного запуска, контроль checksum, данные в отдельном томе.
- Строгие ошибки JSON, ограничения входных данных и таймауты, отсутствие деталей внутренних ошибок в HTTP.
- Воспроизводимые Docker-сборка и тесты; README подробно объясняет выбранное поведение и ограничения.

## Полный текст независимой воспроизводящей проверки

Создать `/tmp/codex-independent-review/check.py` с содержимым ниже. Нужен только Python 3 (стандартная библиотека). Поднять два экземпляра командой `up --build --wait` из таблицы; затем выполнить `python3 /tmp/codex-independent-review/check.py`. Конкурентные проверки содержат assertions. Проверка граничной даты выводит фактический результат, чтобы отдельно показать дефект P3, не прерывая остальные сценарии. После остановки собственной БД выполнить `python3 /tmp/codex-independent-review/check.py outage` — этот режим печатает фактические ответы для дефекта P2.

```python
import concurrent.futures as cf
import json, uuid, urllib.request, urllib.error, sys
BASE=['http://127.0.0.1:18080','http://127.0.0.1:18081']
def req(method,path,body=None,key=None,i=0):
    data=body if isinstance(body,bytes) else None if body is None else json.dumps(body).encode()
    headers={'Content-Type':'application/json'}
    if key: headers['Idempotency-Key']=key
    r=urllib.request.Request(BASE[i%2]+path,data=data,headers=headers,method=method)
    try: response=urllib.request.urlopen(r,timeout=25)
    except urllib.error.HTTPError as e: response=e
    with response:
        return response.status,json.loads(response.read())
def event(cap):
    status,b=req('POST','/events',dict(name='Review',starts_at='2030-01-01T00:00:00Z',capacity=cap))
    assert status==201,(status,b)
    return b['id']
def book(e,key,seats=2,i=0):
    return req('POST',f'/events/{e}/bookings',dict(customer_name='Review',seats=seats),key,i)
def parallel(fn,n):
    with cf.ThreadPoolExecutor(max_workers=16) as ex: return list(ex.map(fn,range(n)))
if len(sys.argv)>1 and sys.argv[1]=='outage':
    for p in ['/events','/healthz']:
        print(p,req('GET',p))
    sys.exit()
e=event(12)
a=parallel(lambda i:book(e,str(uuid.uuid4()),i=i),60)
assert sum(s==201 for s,b in a)==6 and sum(s==409 for s,b in a)==54,a
print('oversell: 6 created, 54 conflicts')
e=event(8); key=str(uuid.uuid4())
a=parallel(lambda i:book(e,key,3,i),40)
assert sum(s==201 for s,b in a)==1 and sum(s==200 for s,b in a)==39,a
bid=a[0][1]['id']; assert len({b['id'] for s,b in a})==1
print('idempotency: 1 created, 39 replays')
a=parallel(lambda i:req('POST',f'/bookings/{bid}/cancel',i=i),40)
assert all(s==200 and b['status']=='cancelled' for s,b in a),a
assert len({b['cancelled_at'] for s,b in a})==1
assert req('GET',f'/events/{e}')[1]['available_seats']==8
assert book(e,key,3)[1]['status']=='cancelled'
print('cancel: 40 OK, identical cancellation timestamp, seats restored once, replay stays cancelled')
e1,e2=event(10),event(10); key=str(uuid.uuid4())
a=parallel(lambda i:book([e1,e2][i%2],key,1,i),40)
assert sum(s==201 for s,b in a)==1 and all(s in [200,201,422] for s,b in a),a
assert sum(req('GET',f'/events/{e}')[1]['booked_seats'] for e in [e1,e2])==1
print('global key across events: exactly one booking')
for b,want in [(b'{"name":"x","starts_at":"2030-01-01T00:00:00Z","capacity":-1}',400),(b'{"name":"x","starts_at":"2030-01-01T00:00:00Z","capacity":2147483648}',400),(b'{"unknown":1}',400),(b'{} {}',400),(b'{"name":"'+b'x'*(1<<20)+b'"}',413)]:
    status,res=req('POST','/events',b)
    assert status==want,(status,res)
print('validation: negative/overflow/unknown/trailing/oversized rejected')
s,b=req('POST','/events',dict(name="x'); DROP TABLE events; --",starts_at='2030-01-01T00:00:00Z',capacity=1))
assert s==201 and req('GET','/events')[0]==200
print('SQL-looking name stored literally, events table remains available')
s,b=req('POST','/events',dict(name='Boundary',starts_at='0001-01-01T00:00:00Z',capacity=1))
print('year-1 boundary:',s,b)
```
