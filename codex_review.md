## Подтверждённые дефекты

### 1. P2 — NUL в строковых полях приводит к 500 вместо ошибки валидации

**Место:** `internal/service/service.go:62–76` и `87–98`; передача в SQL — `internal/store/postgres.go:86–96`, `188–207`; общий ответ 500 — `internal/httpapi/server.go:271–273`.

**Условие:** JSON содержит `\u0000` в имени события или ключе идемпотентности, при этом остальные поля корректны. Стандартный JSON-декодер принимает такую строку; проверки пустоты и длины её пропускают, но PostgreSQL text не поддерживает NUL.

**Последствие:** управляемый клиентом некорректный ввод получает непрозрачный `500 internal`, хотя TASK.md требует понятных ошибок для некорректных запросов. Ошибка вводит клиента в заблуждение о возможности повтора и создаёт внутренние error-логи. Повреждения данных и обхода SQL не обнаружено; транзакция бронирования откатывается.

**Доказательство:** `check.py` ниже получил 500 и `{"error":{"code":"internal","message":"internal server error"}}` для обоих полей. Лог собственного сервиса: `ERROR: invalid byte sequence for encoding "UTF8": 0x00 (SQLSTATE 22021)`.

**Направление исправления:** проверять недопустимый NUL на границе валидации строк и возвращать 400 с указанием поля; закрепить оба случая тестами. Не раскрывать клиенту SQL-ошибку целиком.

### 2. P2 — документированные ограничения в символах фактически считаются в байтах

**Место:** `internal/service/service.go:67–68`, `94–96`.

**Условие:** имя или ключ содержит многобайтные символы UTF-8. README обещает до 200 символов в имени и до 128 символов в ключе, текст ошибки также говорит `characters`, но Go `len(string)` считает байты.

**Последствие:** допустимые по опубликованному контракту запросы отклоняются: имя из 101 буквы «Я» получает 400 (202 байта), ключ из 65 букв «Я» — 400 (130 байт). Это влияет и на русскоязычные названия событий. Данные не повреждаются.

**Доказательство:** оба случая воспроизведены `check.py`; ответы соответственно `name must be at most 200 characters` и `idempotency key must be at most 128 characters`.

**Направление исправления:** согласовать реализацию и контракт: считать Unicode code points, если ограничение действительно в символах, либо явно документировать байты. Определить смысл «символа», если нужны графемы, и проверить границы ASCII/кириллицы/emoji.

## Архитектура

Для небольшой задачи архитектура соразмерна: стандартный net/http, один PostgreSQL-драйвер, четыре небольших пакета без внешних очередей, кешей и инфраструктурных фреймворков. Направление зависимостей понятно: HTTP зависит от service, service задаёт интерфейс Store и использует domain, PostgreSQL-реализация использует domain; сборка зависимостей находится в `cmd/server/main.go:39–54`. Циклических зависимостей нет. Отдельные DTO в HTTP позволяют менять внешний формат без изменения SQL-моделей; цена — некоторое повторение полей и преобразований, оправданное размером API.

Бизнес-валидация расположена в service, а инварианты конкурентности и границы транзакций — в store. Это разумно: только БД видит все экземпляры. Частичный UNIQUE `(event_id, seat_no) WHERE active` в `internal/store/migrations.go:41–46` защищает места независимо от предварительного SELECT. UNIQUE ключа события и токена защищает повторы. `CreateBooking` охватывает запись бронирования и всех мест одной транзакцией (`postgres.go:164–236`), `CancelBooking` меняет статус и активность мест вместе (`243–275`). Повтор отмены не меняет места нового бронирования: UPDATE ограничен старым booking_id. Read-only repeatable-read в `GetEvent` обеспечивает согласованность счётчика и списка доступных мест.

Издержка такого выбора: Store является интерфейсом законченных бизнес-операций, а не простого CRUD. Новая реализация Store обязана повторить транзакционные гарантии, и unit-тесты service с fakeStore этого не доказывают. Здесь это компенсировано реальными PostgreSQL-тестами. Не требуется переносить транзакции в ещё один слой ради шаблона.

Есть небольшая лишняя связанность: `service.Store` требует `Migrate`, а service предоставляет его транзитно (`service.go:27,60`), хотя точка входа вызывает миграцию непосредственно у store. Это увеличивает интерфейс и заглушки без пользы для бизнес-логики; возможное упрощение, не функциональный дефект.

Валидация частично распределена: форма запроса и лимиты находятся в service, проверка диапазона места требует capacity и находится внутри store. Это экономит запросы и сохраняет атомарность; добавляя новые способы изменения вместимости или записи, придётся учитывать оба участка. Сама схема не запрещает seat_no > capacity, несовпадение event_id у booking и booking_seats либо активные места отменённого booking при прямом SQL. Нынешний API таких записей не делает. Это граница доверия к единственному писателю, а не подтверждённая ошибка API. При появлении других писателей нужны дополнительные ограничения/единый протокол записи.

Схема миграций мала и понятна: выделенное соединение удерживает session advisory lock, миграция и запись версии выполняются в транзакции. Для одной версии этого достаточно. `IF NOT EXISTS` и max(version) не проверяют соответствие уже существующей схемы ожидаемой; ручной drift и изменения старых миграций не поддерживаются. Это разумное ограничение небольшой задачи, которое стоит учитывать при развитии. Очистка advisory lock через `context.WithoutCancel` не имеет собственного deadline: при сетевой неисправности завершение может задержаться; отказоустойчивость этого пути не проверялась.

Стоимость обычных изменений невысока: новая проверка добавляется в service, маршрут и отображение ошибок — в httpapi, SQL — в store. Динамический SQL для набора мест параметризован и ограничен 100 элементами. Предварительная проверка занятости добавляет round trip, зато обычно даёт конкретные номера конфликтов; при проигранной гонке возвращается общий конфликт без списка (`postgres.go:220–224`). Это компромисс качества сообщения, а не нарушение атомарности.

## Безопасность

**Модель угроз:** недоверенный HTTP-клиент может посылать произвольные JSON, пути и заголовки, выполнять все документированные операции и повторять их конкурентно. Проверяемая граница — HTTP → service → SQL. PostgreSQL, его администратор, DSN и окружение процесса считаются доверенными. Отсутствие авторизации явно разрешено TASK.md; создание/просмотр/отмена чужого бронирования не объявляются дефектом задания.

**Подтверждено:**

- SQL-значения передаются через параметры `$n`; динамическая часть запросов в `takenSeats`/`insertSeats` содержит только структуру и номера placeholders. Строка ключа `'; DROP TABLE events;--` успешно сохранилась как данные; повтор вернул тот же booking. Это ограниченная практическая проверка плюс чтение кода, не доказательство отсутствия любых SQL-инъекций во всех будущих изменениях.
- JSON разбирается с `DisallowUnknownFields`, второе значение запрещено, тело ограничено 1 MiB (`httpapi/server.go:236–247`). Второй JSON и тело больше лимита получили 400. Имя, ключ, число мест и capacity ограничены; ошибки NUL и Unicode описаны выше. Декодер не отклоняет повторяющиеся JSON-ключи и заменяет некоторые некорректные Unicode-последовательности; обхода основных инвариантов этим не установлено.
- Внутренние SQL-ошибки маскируются общим ответом 500; для NUL это проверено. Тело бронирования, ключ идемпотентности и DATABASE_URL не логируются напрямую в обычном access log. Внутренние ошибки попадают в серверный лог, поэтому доступ к нему должен быть ограничен.
- В main настроены таймауты чтения заголовков 5 с, чтения 10 с, записи 15 с, idle 60 с, graceful shutdown 10 с; пул ограничен 25 соединениями на экземпляр. Это снижает часть рисков исчерпания ресурсов, но не задаёт верхнюю границу времени SQL-операции.
- Docker-образ многостадийный, runtime работает от `USER app` (UID 10001), исходники и сборочный Go в финальный образ не копируются. PostgreSQL в compose не публикует порт на хост; фактический `compose ps` это подтвердил. HTTP публикуется на всех интерфейсах IPv4/IPv6, что нужно учитывать при запуске на доступном извне хосте.

**Условия публичного развёртывания, не дефекты задания:** аутентификация/авторизация и TLS на доверенном ingress, собственные секреты вместо `booking:booking`, ограничение сетевой доступности, роли БД с минимальными правами. Созданный POSTGRES_USER получает повышенные права для локальной простоты и миграций; отдельная runtime-роль уменьшит последствия компрометации. `sslmode=disable` годится только для доверенного канала. В compose нет лимитов CPU/RAM и жёстких настроек read-only/capabilities — возможное усиление контейнеров при публичной эксплуатации.

**Неподтверждённые риски и необязательные рекомендации:**

- `WriteTimeout` ограничивает запись в сокет, но не отменяет контекст SQL сам по себе. Обработчики передают r.Context без deadline; при блокировке/медленной БД ожидающие запросы могут удерживать пул и goroutine дольше таймаута ответа (`main.go:52–59`, `postgres.go:164–169,243–248`). Массовая эксплуатация и сетевые отказы не моделировались. Для эксплуатации полезны request deadline, statement/lock timeout и отдельный короткий deadline healthz. Не заявляется подтверждённый DoS.
- GET /events не имеет пагинации, а GET /events/{id} генерирует до 100000 номеров мест; история отменённых мест растёт без retention. Это прямо указано в README. При большой базе стоимость запросов и ответов растёт, rate limiting отсутствует. Нагрузка и пороги отказа не измерялись; для текущего задания не вводятся новые требования по масштабированию.
- Access log пишет декодированный URL.Path через `%s` (`httpapi/server.go:294`); для публичного входа полезно экранирование управляющих символов и ограничение длины. Подделка строк логов активным тестом не проверялась.
- Образы заданы изменяемыми тегами, apk-пакеты не закреплены по digest/версии. go.mod/go.sum фиксируют Go-зависимости, но побитовая воспроизводимость контейнера этим не гарантируется. Digest pinning и контролируемые обновления — необязательное улучшение.
- Аудит известных уязвимостей зависимостей (`govulncheck`, Trivy и т.п.) не проводился. Утверждения об отсутствии CVE или об их применимости не делаются. Отсутствие выявленных серьёзных проблем не доказывает безопасность.

## Качество автоматических тестов

В integration есть 13 основных тестов: API/доступность, валидация, последовательная и конкурентная идемпотентность, конкурентное бронирование, отмена, гонка отмены и перебронирования, две HTTP-сборки с разными пулами, повторное открытие хранилища и миграции. Проверяются ответы API и ограничения через прямые SQL-запросы, что существенно лучше проверки только status code. Все прошли с PostgreSQL 16 и race detector. Unit-тесты проверяют отсутствие вызова Store на невалидном вводе и сортировку мест; реализация клонирует входной slice перед сортировкой.

Ограничения покрытия: без BOOKING_TEST_DATABASE_URL интеграционные тесты пропускаются; обычный `go test ./...` не доказывает работу с БД. Штатный тест перезапуска закрывает и открывает сервер/пул в одном процессе, а тест двух экземпляров использует httptest в одном процессе; собственная проверка ниже дополняет их двумя OS-процессами и SIGTERM/новым запуском. Конкурентные миграции в штатном тесте запускаются уже на подготовленной БД, а не одновременно на пустой. Случайные конкурентные тесты не исчерпывают все interleavings; `confirmedSeats` в TestConcurrentNoOversell накапливается, но затем не сравнивается с числом строк, и комментарий о связи активных мест со статусом booking проверяется лишь частично. Это направления усиления тестов, не доказательства ошибки реализации. NUL и многобайтные граничные длины текущие тесты пропускают.

## Сильные стороны

Корректность защищена самой БД и транзакциями; нет зависимости от локальных mutex и памяти одного экземпляра. Многоместное бронирование атомарно, сортировка мест уменьшает риск взаимных блокировок конкурентных вставок. Отмена не может освободить места другого booking. Явно описан контракт повторов с изменёнными местами и после отмены. Схема и запуск просты, автоматические интеграционные тесты содержательны, README объясняет решения и ограничения. Docker-сборка и реальный запуск воспроизведены.

### processes.py

```python
import subprocess, os, time, json, urllib.request, urllib.error, concurrent.futures
BIN='/tmp/booking-review-server'
DSN='postgres://booking:booking@127.0.0.1:55439/booking_test?sslmode=disable'
procs=[]
def start(port):
    p=subprocess.Popen([BIN],env={**os.environ,'DATABASE_URL':DSN,'HTTP_ADDR':f'127.0.0.1:{port}'},stdout=subprocess.DEVNULL,stderr=subprocess.DEVNULL); procs.append(p)
    for _ in range(100):
        try:
            with urllib.request.urlopen(f'http://127.0.0.1:{port}/healthz',timeout=1): return p
        except Exception: time.sleep(.05)
    raise RuntimeError('startup failed')
def call(port,path,body=None):
    req=urllib.request.Request(f'http://127.0.0.1:{port}'+path,data=None if body is None else json.dumps(body).encode(),headers={'Content-Type':'application/json'})
    try: r=urllib.request.urlopen(req,timeout=10)
    except urllib.error.HTTPError as e: r=e
    return r.code,json.loads(r.read())
try:
    a=start(58093); b=start(58094)
    _,e=call(58093,'/events',{'name':'process-review','capacity':2})
    def book(i,key): return call(58093+i%2,'/bookings',{'event_id':e['id'],'seats':[1,2],'idempotency_key':key})
    with concurrent.futures.ThreadPoolExecutor(16) as pool: results=list(pool.map(lambda i:book(i,'shared'),range(16)))
    assert sum(s==201 for s,_ in results)==1 and all(s in (200,201) for s,_ in results),results
    ids={v['id'] for _,v in results}; assert len(ids)==1; bid=ids.pop()
    with concurrent.futures.ThreadPoolExecutor(16) as pool: results=list(pool.map(lambda i:call(58093+i%2,f'/bookings/{bid}/cancel',{}),range(16)))
    assert all(s==200 and v['status']=='cancelled' for s,v in results)
    assert len({v['cancelled_at'] for _,v in results})==1
    with concurrent.futures.ThreadPoolExecutor(16) as pool: results=list(pool.map(lambda i:book(i,f'new-{i}'),range(16)))
    assert sum(s==201 for s,_ in results)==1 and sum(s==409 for s,_ in results)==15,results
    newbid=next(v['id'] for s,v in results if s==201)
    a.terminate(); b.terminate(); a.wait(timeout=15); b.wait(timeout=15)
    a=start(58093); b=start(58094)
    assert call(58093,f'/bookings/{bid}')[1]['status']=='cancelled'
    assert call(58094,f'/bookings/{newbid}')[1]['status']=='confirmed'
    assert call(58093,f'/events/{e["id"]}')[1]['available_seats']==0
    print('PASS: two OS processes, 16 concurrent idempotent creates, 16 cancels, 16 conflicting rebooks, restart of both processes and persisted statuses/availability')
finally:
    for p in procs:
        if p.poll() is None: p.terminate(); p.wait(timeout=15)
```
