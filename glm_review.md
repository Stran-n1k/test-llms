# Независимое техническое ревью (GLM)

Дата: 2026-11-07. Объект: сервис бронирования мест (Go + PostgreSQL), каталог `~/review/project`.

## 1. Краткое заключение о соответствии TASK.md

Решение соответствует всем обязательным свойствам TASK.md. Проверено фактически, включая
работу с настоящей PostgreSQL и конкурентные сценарии на уровне HTTP с двумя экземплярами
и общей базой:

- **Сохранность данных** — подтверждена перезапуском обоих экземпляров приложения, полным
  перезапуском контейнера PostgreSQL и циклом `docker compose down`/`up` (данные целы).
- **Отсутствие перепродажи** — подтверждено: 30 конкурентных броней на 10 мест через два
  экземпляра дали ровно 10×201 и 20×409; смешанный шторм из 60 созданий и отмен —
  `booked_seats` в базе равен сумме активных броней и не превышает вместимость.
- **Идемпотентность создания** — подтверждена: 20 конкурентных запросов с одним ключом дали
  ровно одну бронь (один `id`), повтор с теми же параметрами возвращает исходную бронь,
  с другими параметрами — 409 `idempotency_conflict`; повтор после отмены возвращает исходную
  бронь в статусе `cancelled`, не занимая места.
- **Отмена ровно один раз** — подтверждена: 20 конкурентных отмен вернули все 200 с одним и
  тем же `cancelled_at`, места освобождены ровно один раз; повторная отмена не меняет состояние.
- **Два экземпляра с общей базой** — подтверждено на бинарниках (порты 18081/18082) и в Docker;
  одновременный старт двух экземпляров на пустой базе безопасен (advisory-блокировка миграции).
- **Валидация** — ~45 HTTP-проверок некорректных запросов (Content-Type, размер тела, границы
  полей, NUL-байты, несуществующие объекты, методы): поведение соответствует README, данные
  не портятся.
- **Подготовка схемы и повторный запуск** — миграция идемпотентна, повторный запуск на
  непустой базе не теряет данные (проверено тестами проекта и моими перезапусками).
- **Автотесты** — 5 интеграционных тестов с реальной PostgreSQL (изолированные схемы) проходят
  с `-race`; README точно описывает запуск, решения и ограничения.

Подтверждённых функциональных дефектов, нарушающих требования TASK.md, не найдено.
Найдены: одна проблема уровня зависимостей (P2) и одна проблема наблюдаемости (P3) — см. ниже.

## 2. Подтверждённые дефекты

### Д-1. P2 — известные уязвимости в зависимостях (pgx, golang.org/x/text)

- **Файлы и строки:** `go.mod:7` (`github.com/jackc/pgx/v5 v5.7.6`), `go.mod:16`
  (`golang.org/x/text v0.24.0`, indirect); достижимые пути — `cmd/booking/main.go:45`
  (`pgxpool.NewWithConfig`), `internal/booking/store.go:109` (`Pool.QueryRow`).
- **Условие проявления:** инструмент `govulncheck` (см. раздел 6) сообщил о трёх достижимых
  на уровне символов уязвимостях:
  - GO-2026-5004 — SQL-инъекция через подмену плейсхолдеров при доллар-квотированных строках
    в pgx < v5.9.2;
  - GO-2026-5970 — бесконечный цикл на некорректном вводе в `x/text/norm` (< v0.39.0);
  - GO-2026-6629 — паника на специально сформированном вводе в `x/text/secure/precis` (< v0.41.0).
- **Последствия и применимость к используемому коду:** практическая применимость в этом
  проекте низкая: весь SQL — статические константы с параметрами `$1..$4`, пользовательский
  ввод в текст запросов не попадает (GO-2026-5004 требует подконтрольного атаканту текста
  запроса); пути к `x/text` проходят через SCRAM-аутентификацию pgx, где вход — пароль из
  `DATABASE_URL`, то есть данные оператора, а не удалённого клиента. Тем не менее уязвимости
  достижимы по символам, исправление тривиально, и оставлять известные CVE в зависимостях
  не стоит.
- **Доказательство:** команда и вывод в разделе 6 (`Your code is affected by 3 vulnerabilities
  from 2 modules`).
- **Направление исправления:** поднять `github.com/jackc/pgx/v5` до ≥ v5.9.2 и, вслед за ним,
  `golang.org/x/text` до ≥ v0.41.0; перезапустить `go mod tidy` и тесты.

### Д-2. P3 — внутренние ошибки (HTTP 500) не журналируются

- **Файлы и строки:** `internal/booking/handler.go:250-252` (`internalError` отбрасывает
  `err`), `cmd/booking/main.go:58-60` (в `Handler` не передаётся логгер; единственный
  логгер — `main.go:18`).
- **Условие проявления:** любой сбой БД или неожиданная ошибка хранилища при обработке запроса.
- **Последствия:** клиент получает 500 `internal_error`, но на стороне сервиса не остаётся
  ни одной записи. Проверено: при остановленной PostgreSQL экземпляры вернули 500, а в их
  логах — только строка запуска (`grep -ci error` по логам = 0). В эксплуатации причину 500
  диагностировать будет нечем; это также снижает ценность заявленной диагностики при деградации
  (503 на `/healthz` при этом формируется корректно).
- **Доказательство:** раздел 6, сценарий «остановка БД»: `500 {"error":{"code":"internal_error",...}}`
  при пустом логе.
- **Направление исправления:** передать `*slog.Logger` в `NewHandler` и записывать ошибку
  (с путём и кодом ответа) в `internalError` до отправки ответа.

## 3. Неподтверждённые риски и необязательные рекомендации

Неподтверждённые риски (проверить не удалось или эффект теоретический):

- `hashtextextended` (`internal/booking/store.go:133`) — внутренняя, официально не
  документированная функция PostgreSQL (стабильна с PG 11). Изменение её поведения в будущих
  версиях потребовало бы правки. Коллизии 64-битного хеша ключей между собой или с константой
  блокировки миграции (`internal/booking/migrate.go:44`) ведут лишь к лишней сериализации,
  не к ошибке: после захвата блокировки идёт точная проверка ключа.
- Поведение при обрыве соединения в момент коммита: если экземпляр упал после коммита, но до
  ответа, повтор с тем же ключом корректно возвращает созданную бронь (проверено семантикой
  идемпотентности); сценарий «упал до коммита» даёт чистое создание при повторе. Риска не
  вижу, но полноценно протестировать падение процесса между коммитом и ответом не пытался.
- Отсутствие ограничения частоты запросов — теоретический DoS-вектор при публичном
  развертывании (см. «Безопасность»).

Необязательные рекомендации (не ошибки, предпочтения по стилю не навязываю):

- Расширить HTTP-тесты краевыми случаями, не покрытыми сейчас: 415 (неверный Content-Type),
  тело свыше 1 МиБ, границы длины `idempotency_key`, 503 `/healthz` при недоступной БД.
  Основные сценарии по TASK.md покрыты, это именно «желательные» дополнения.
- `uuid.Parse` принимает нестандартные формы (без дефисов, `urn:uuid:…`, `{…}`) — проверено,
  все формы адресуют ту же сущность (200). Ошибкой целостности это не является; при желании
  можно ужесточить разбор до канонической формы.
- `HEAD` на GET-маршрутах возвращает 405 (RFC 9110 ожидает обработку HEAD как GET). Косметика.
- Ограничение размера тела (`http.MaxBytesReader`, `handler.go:217`) применяется только к
  POST-обработчикам с `decodeRequest`; на остальных маршрутах тело не читается и сбрасывается
  сервером, поэтому исчерпания памяти нет — но единый лимит был бы аккуратнее.
- В `compose.yaml` нет `restart:` для сервиса `app`: после перезапуска хоста стек не поднимется
  сам. README честно описывает, что перезапуск при недоступной базе — зона ответственности
  оркестратора; для compose достаточно `restart: unless-stopped`.

## 4. Архитектура

Соразмерность. Решение пропорционально задаче: один пакет `internal/booking` из четырёх
файлов (`store`, `handler`, `types`, `migrate`) плюс тонкий `cmd/booking/main.go` на 84 строки.
Нет лишних слоёв, DI-фреймворков и генерации — для «небольшого законченного backend» это
правильный размер. Избыточной сложности не вижу; упрощений, мешающих поддержке, тоже.

Разделение ответственности и направления зависимостей. Зависимости направлены строго внутрь:
`main` → `Handler` → `Store` → `pgxpool`; обратных связей и циклов нет. Транспортная логика
(разбор HTTP, маппинг кодов ответов в `handler.go:187-201`), валидация входа (`handler.go:49-154`)
и работа с данными (`store.go`) разделены чисто. `Store` совмещает простые CRUD и
транзакционные сценарии — при текущем объёме это разумно, выделение отдельных репозиториев
было бы уже избыточным слоем.

Размещение бизнес-инвариантов и границы транзакций — сильная сторона. Ключевые инварианты
реализованы в самой PostgreSQL и потому одинаковы для любого числа экземпляров:
`CreateBooking` (`store.go:119-187`) — одна транзакция: advisory-блокировка по хешу ключа →
проверка существующей брони → `SELECT … FOR UPDATE` строки события → проверка вместимости →
инкремент `booked_seats` → вставка; `CancelBooking` (`store.go:191-231`) — условный
`UPDATE … WHERE status='active' RETURNING` плюс декремент в той же транзакции. Порядок
блокировок детерминирован (advisory → строка события; отмена: строка брони → строка события),
циклов не образуется — смешанный шторм из 60 конкурентных созданий и отмен прошёл без
дедлоков. Дополнительно инварианты защищены `CHECK`-ограничениями схемы (`migrate.go:11-14,
26-29`) — эшелонированная защита: даже ошибка в приложении не позволит счётчику выйти за
границы.

Тестируемость. Интеграционные тесты используют `rowScanner`-интерфейс для сканирования и
изолированные случайные схемы на тест (создание/удаление только своей схемы,
`integration_test.go:29-78`) — тесты параллельно-безопасны и не конфликтуют между собой.
Компромисс: `Handler` зависит от конкретного `*Store`, поэтому HTTP-тесты без PostgreSQL
невозможны (юнит-моков нет). Для этого размера проекта компромисс осознанный и допустимый —
цена: чуть более медленный полный прогон и обязательная БД для любых тестов handler'а.

Понятность и стоимость изменений. Код читается легко, нетривиальные места комментированы
с объяснением причин (комментарии о сериализации ключей и порядке блокировок в `store.go:131-132`,
условной отмене в `store.go:189-190`, advisory-блокировке миграции в `migrate.go:35-36`).
Ошибки типизированы (`ErrNotFound`, `ErrIdempotencyConflict`, `CapacityError`) и единообразно
маппятся в HTTP-коды. Стоимость изменения умеренная: новое поле сущности затронет
`types.go`, SQL в `store.go` и схему в `migrate.go` — предсказуемо. Ограничение подхода к
миграциям (`CREATE … IF NOT EXISTS`, без версионирования изменений уже существующих таблиц)
честно задокументировано в README и для стартовой схемы достаточно; эволюция схемы потребует
версионированного инструмента — это задокументированный компромисс, а не дефект.

## 5. Безопасность

Модель угроз и границы доверия. Сервис — публичный HTTP API без аутентификации (прямо
разрешено TASK.md и указано в README). Недоверенный вход: любые HTTP-запросы. Полудоверенные:
сеть между приложением и PostgreSQL (в demo-развертывании — docker-сеть), операторский
`DATABASE_URL`. Активные проверки выполнялись только против собственных тестовых сервисов
на моей машине.

SQL-инъекции. Не найдены. Все запросы к данным параметризованы (`$1..$4`,
`store.go`/`migrate.go`), конкатенация пользовательского ввода в текст SQL отсутствует;
единственная «динамическая» сборка — соединение константных фрагментов (`eventSelect + " WHERE id = $1"`).
В тестах имя схемы экранируется `pgx.Identifier.Sanitize` (`integration_test.go:46-57`).
Отдельно отмечена GO-2026-5004 в pgx (Д-1): применимость к этому коду низкая по указанным
причинам, но зависимость стоит обновить.

Обработка недоверенного JSON. Строгая: обязательный `Content-Type: application/json` (415),
лимит тела 1 МиБ через `http.MaxBytesReader` (`handler.go:217`), `DisallowUnknownFields`,
отклонение второго JSON-значения в теле, строго типизированные поля int (дроби и строки
отклоняются), запрет NUL-байтов в `title` и `idempotency_key` (защищает и от ошибок
PostgreSQL text), границы длины проверены на границах значений, включая мультибайтовые ключи
(200 байт = 100 символов проходит; 201 байт отклоняется). Проверено ~45 кейсами (раздел 6).

Утечки внутренних ошибок и секретов. Ответы на 500 генерируются без подробностей
(`internal_error`), SQL и трассировки наружу не попадают; сообщения об ошибках декодирования
JSON содержат только текст декодера — стандартная практика. Секретов в коде нет;
демо-учётные данные только в `compose.yaml` (задокументированы как демонстрационные).
Обратная сторона — сами 500 не логируются (Д-2).

Таймауты и исчерпание ресурсов. У сервера выставлены все таймауты
(`main.go:61-64`: ReadHeader 5с, Read 15с, Write 30с, Idle 60с) — slowloris-атака
ограничена; пул соединений ограничен (`MaxConns = 20`); ожидание advisory-блокировок
ограничено контекстом запроса и WriteTimeout. Лимита частоты запросов нет — для публичной
эксплуатации нужен внешний rate limit/прокси (условие развертывания, не дефект учебной задачи).
Затратных операций с неограниченным потреблением CPU/памяти по входу не обнаружено.

Контейнеры и порты. Образ многоэтапный, статический бинарник, непривилегированный пользователь
`app` (проверено `docker inspect`: `user=app`), `wget` для healthcheck присутствует.
`compose.yaml` публикует на хосте порт 5432 PostgreSQL с демо-паролем `booking` — для
демонстрации допустимо (README это оговаривает), для чего-то большего следует убрать
публикацию порта или привязать к `127.0.0.1`.

Условия развертывания для публичной эксплуатации (не дефекты выполнения задания):
аутентификация/авторизация, TLS на входе и до БД (`sslmode=disable` допустим только в
закрытой сети), ограничение частоты запросов, приватная сеть для PostgreSQL.

Проверка зависимостей: `govulncheck` — инструмент, результат и применимость указаны в Д-1.
Утверждать отсутствие других уязвимостей не берусь; отсутствие найденных проблем не означает
доказанную безопасность.

## 6. Выполненные команды проверок и результаты

Окружение: Go 1.27.3, Docker 29.9.2, Compose 5.7.0, linux/amd64. Собственная PostgreSQL 16
(контейнер `review-pg-glm` на 127.0.0.1:55432, удалён по завершении). Временные файлы —
`/tmp/opencode/review-glm/` (скрипты `stress.sh`, `stress_g.sh`, `validate.sh`).

1. `go vet ./...` — без замечаний.
2. `go build ./...` — успешно.
3. `go mod verify` — all modules verified.
4. `go test ./...` (без `TEST_DATABASE_URL`) — ok, PostgreSQL-тесты корректно пропущены.
5. `TEST_DATABASE_URL='postgres://booking:booking@127.0.0.1:55432/booking?sslmode=disable'
   go test -race -count=1 -v ./...` — все 5 тестов PASS (миграция/персистентность,
   конкурентные брони двух пулов, идемпотентность, конкурентная отмена, HTTP e2e).
6. Два экземпляра бинарника (`:18081`, `:18082`) против общей PostgreSQL, нагрузочные
   сценарии (bash+curl, чередование экземпляров):
   - 30 конкурентных броней на 10 мест: 10×201, 20×409, `booked_seats=10` — перепродажи нет;
   - 20 конкурентных запросов с одним ключом (seats=4): 1×201 + 19×200, один `booking id`,
     `booked_seats=4` — дубликата нет;
   - тот же ключ с другими параметрами: 409 `idempotency_conflict`;
   - 20 конкурентных отмен: 20×200, один `cancelled_at`, `booked_seats=0` — места возвращены
     один раз; повтор отмены — 200 без изменений; бронь всех 10 мест после отмены — 201;
   - смешанный шторм (60 конкурентных созданий seats=2 + немедленные отмены каждой второй
     успешной брони): без дедлоков, `booked=32 = sum(active)=32`, `cancelled=12`;
   - повтор того же ключа после отмены: 200, `status=cancelled`, места не занимаются
     (available=5/5).
7. Перезапуск: остановка обоих экземпляров → `docker restart` PostgreSQL → повторный запуск
   обоих экземпляров: данные целы (events=9, bookings=82, доступность и отменённые брони
   неизменны), повторная миграция на непустой базе прошла без потерь.
8. Валидация HTTP (~45 кейсов, скрипт `validate.sh`): 415 без/с неверным Content-Type; 400
   для пустого/битого/двойного JSON, неизвестных полей, массива вместо объекта, тела 1.1 МиБ;
   400 для всех выходов за границы полей (title 0/201/NUL, capacity 0/-5/1000001/строка/float,
   seats 0/-1/1000001, ключ пустой/201 байт/NUL); 201 на граничных валидных значениях
   (title 200, capacity 1000000, ключ 200 байт, мультибайтовый ключ); 404/400/405 по маршрутам
   и методам, `Allow` на 405. Пять несовпадений в выводе скрипта — ошибки ожиданий самого
   скрипта (разобраны: новый ключ → 201; несуществующее событие → 404; не-UUID → 400;
   контрольные символы в ключе разрешены спецификацией «1–200 байт»; последний случай —
   `curl -d` неявно выполняет POST). Все они — корректное поведение приложения.
9. Формы идентификаторов: UUID без дефисов, `urn:uuid:`, `{…}` — принимаются (200, та же
   сущность); `HEAD`/`OPTIONS` — 405; путь 2000 символов — 404.
10. `go run golang.org/x/vuln/cmd/govulncheck@latest ./...` — «Your code is affected by
    3 vulnerabilities from 2 modules» (GO-2026-5004, GO-2026-5970, GO-2026-6629) — см. Д-1.
11. `docker build -t review-booking-glm:check .` — успешно; запуск контейнера против общей
    тестовой БД — healthy, отдаёт данные; без `DATABASE_URL` — аккуратная ошибка и выход;
    пользователь `app`.
12. `docker compose config` — валидно; полный цикл `docker compose up -d --build` →

    том сохраняет состояние) → `down` и удаление тестового тома. Оба контейнера healthy.
13. Одновременный старт двух контейнеров приложения на полностью пустой базе `empty_race`:
    оба healthy, схема создана один раз, ошибок в логах нет.
14. Остановка PostgreSQL: `/healthz` → 503 `database_unavailable`, обычные запросы → 500
    `internal_error` без подробностей, экземпляры остаются живыми и восстанавливаются после
    старта БД.

Не выполненные проверки и причины:

- Работа на других версиях PostgreSQL (проверялась только 16-alpine из compose проекта) —
  задача не требует, а полное матричное тестирование вышло бы за разумные рамки ревью.
- Производственное нагрузочное тестирование (RPS, латентность) — TASK.md требует корректности
  при конкурентности, а не производительности; тяжёлые нагрузочные атаки запрещены инструкцией
  ревью.
- Фаззинг HTTP/JSON — выходит за рамки задачи; статический анализ входа выполнен чтением кода
  и ~45 направленными кейсами.
- Воспроизведение падения процесса строго между коммитом и ответом клиента — практическая
  реализация ненадёжна; корректность следует из семантики транзакций и проверена поведением
  повторов (см. риски).

## 7. Сильные стороны решения

- Корректные конкурентные гарантии реализованы там, где им место — в PostgreSQL
  (advisory-блокировка ключа идемпотентности, `SELECT … FOR UPDATE` события, условный UPDATE
  отмены, `CHECK`-ограничения как второй рубеж), поэтому они автоматически масштабируются на
  N экземпляров; заявленные свойства воспроизведены внешними проверками, а не только тестами
  автора.
- Отличные интеграционные тесты: реальная PostgreSQL, изолированные случайные схемы на тест,
  повторная миграция, два независимых пула как модель двух экземпляров, проверка инвариантов
  прямыми SQL-запросами к базе; проходят под `-race`.
- Строгая и продуманная валидация входа: Content-Type, лимит тела, unknown fields, один
  JSON-объект, запрет NUL, границы с юнит-тестами на границах значений (мультибайтовые ключи).
- Чистая HTTP-семантика: 201/200 для повтора, осмысленные 409 с кодами `insufficient_capacity`
  и `idempotency_conflict`, `Allow` на 405, единый формат ошибок.
- Пропорциональная архитектура без лишней сложности, комментарии объясняют нетривиальные
  решения, README точно и честно документирует команды, решения и ограничения (все проверенные
  заявления README подтвердились).
- Качественная контейнеризация: многоэтапная сборка, статический бинарник, непривилегированный
  пользователь, healthcheck'и на уровне compose, таймауты HTTP-сервера выставлены полностью.
- Корректная деградация: 503 на `/healthz` при недоступной базе, восстановление без
  перезапуска, аккуратное завершение по сигналам.

Подтверждённых дефектов, нарушающих требования TASK.md, нет; единственные подтверждённые
замечания — обновляемые уязвимости зависимостей (P2) и отсутствие журналирования 500 (P3).
