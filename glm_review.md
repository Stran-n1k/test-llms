# Независимое техническое ревью

Проект: Go-сервис бронирования мест (~/review/project).
Дата ревью: 2026-11-06. Проверяющий: GLM-агент (независимое ревью, исходники не изменялись).

## 1. Краткое заключение

Решение соответствует требованиям TASK.md. Все заявленные обязательные свойства
воспроизведены на практике, в том числе на двух экземплярах с общей PostgreSQL:
сохранность данных после перезапуска (включая SIGKILL), отсутствие перепродажи при
конкурентных запросах, идемпотентность создания по `Idempotency-Key`, возврат мест
ровно один раз при повторной и конкурентной отмене, корректная работа с неверными
запросами, воспроизводимая подготовка схемы и безопасный повторный запуск.
Запуск по README (`docker compose up --build --wait`, профиль `two-instances`)
воспроизводится. Автотесты трёхуровневые, с настоящей PostgreSQL и конкурентными
сценариями, и проходят с `-race`.

**Подтверждённых дефектов не найдено.** Ниже перечислены неподтверждённые риски,
архитектурные компромиссы и необязательные рекомендации; ни одно из них не является
нарушением TASK.md.

## 3. Подтверждённые дефекты

**Подтверждённых дефектов не найдено.** Активные проверки (конкурентность,
идемпотентность, отмена, перезапуск, валидация, границы значений, SQL-инъекции,
воспроизводимость сборки и генерации кода) не выявили расхождений между TASK.md,
README и фактическим поведением.

Два наблюдения уровня «заметка», которые я не считаю дефектами:

- `internal/repository/postgres/booking.go:196` — на пути «нечего отменять»
  (`ErrNoRows` из транзакции) повторное чтение брони выполняется вне транзакции
  новым запросом. Если БД откажет именно в этот момент, клиент получит 500/503 при
  корректном состоянии; повтор запроса безопасен и вернёт бронь. Последствий для
  данных нет.
- `internal/handler/rest/decode.go:35-42` — для тела с корректным JSON-значением и
  «хвостом» в виде объекта с неизвестным полем сообщение ошибки говорит
  «single JSON value», а не «unknown field»; статус и код (`400 invalid_json`) те же.
  Косметика.

## 4. Архитектура

**Соразмерность.** Для «небольшого» сервиса решение на верхней границе разумного:
4 слоя (handler/rest → service → repository/postgres + контракты в model), OpenAPI
codegen, генерируемые моки, ~45 файлов исходников и ~3000 строк тестов. При этом
каждый элемент мал и несёт нагрузку: строгий разбор JSON руками написан ради
точных ошибок (`decode.go:18-45`), собственный раннер миграций — ~100 строк вместо
внешней библиотеки (`migrate.go:28-100`), что даёт нужные advisory-lock и
транзакционность без зависимости. Избыточной сложности, мешающей поддержке, я не
вижу; альтернатива «всё в одном main.go» для конкурентной задачи была бы проще по
структуре, но хуже по тестируемости.

**Разделение ответственности и направление зависимостей.** Чистое: transport
(биндинг, маппинг ошибок в статусы) → service (валидация, нормализация) →
repository (SQL и транзакции). Интерфейсы объявлены на стороне потребителя
(`handler/rest/dependency.go`, `service/*/dependency.go`) — инверсия зависимостей,
без циклов импортов; сборка только в `internal/app/app.go:43-85`. Слой service
тонкий: правила вида «имя 1-200 символов без управляющих» живут в
`model/validation`, и это правильное место.

**Размещение инвариантов и границы транзакций.** Главный инвариант (непродажа
сверх вместимости) реализован в репозитории: транзакция с
`SELECT ... FOR NO KEY UPDATE` строки события, затем проверка и
`booked_seats + n` (`booking.go:27-82`), с `CHECK`-ограничением в схеме как
последней линией (`migrations/0001_init.sql:11`). Это осознанный и корректный
компромисс: инвариант по природе относится к данным, и размещение его рядом с
транзакцией делает его проверяемым на двух экземплярах без общей памяти. Цена —
часть бизнес-логики бронирования живёт в SQL-слое, и это надо учитывать при
изменениях (тесты репозитория это компенсируют). Порядок блокировок
задокументирован и непротиворечив: создание держит только событие, отмена —
бронь, затем событие (`booking.go:161-186`); циклов, приводящих к дедлокам,
я не нашёл, и стресс-тесты (в т.ч. смешанные создания/отмены) это подтверждают.

**Тестируемость.** Образцовая: модульные тесты на моках (91 тестовая функция),
интеграционные на Testcontainers с отдельной базой на тест, сквозные с реальным
бинарником, двумя процессами и SIGKILL. Проверяется не только результат операции,
но и согласованность счётчика с суммой подтверждённых броней
(`repository_integration_test.go:173-187`).

**Понятность и стоимость изменений.** Код читается легко, комментарии объясняют
«почему», а не «что». README честно фиксирует решения и ограничения. Стоимость
изменений типична для contract-first: новое поле требует правки openapi →
`go generate` → model/service/repo; сгенерированный код соответствует спецификации
(проверено регенерацией и сравнением). Тонкие места (подмена 404/405 на JSON через
`discardWriter` в `server.go:34-54`, различение 201/200 + `Idempotent-Replayed`)
сложны, но изолированы и покрыты тестами.

## 5. Безопасность

**Модель угроз и границы доверия.** HTTP-клиент недоверен; PostgreSQL и внутренняя
сеть доверены; авторизация отсутствует по условию TASK.md и дефектом не является.
Ниже требования для публичной эксплуатации отмечены отдельно.

**SQL-инъекции.** Все запросы параметризованы (`$1..$n`), конкатенаций с
недоверенными данными нет; SQL-текст состоит только из констант и имён колонок из
пакетных констант. Проверено активно: имя события `Robert'); DROP TABLE events;--`
и аналогичное `customer_name` принимаются, сохраняются литерально, таблицы живы,
бронь создаётся. Миграции выполняются из встроенных файлов, не из ввода.

**Недоверенный JSON.** Строгий разбор (`decode.go`): неизвестные поля и данные
после JSON-значения отклоняются, размер тела ограничен 1 МиБ (`MaxBytesReader`,
проверено: 2 МБ → 413), типы и границы int32 проверяются, год timestamp — 1..9999
UTC (защищает от неэнкодируемых ответов). Заголовок ограничен дефолтом Go,
`ReadHeaderTimeout` 5 с закрывает slowloris-паттерн на заголовках.

**Таймауты и исчерпание ресурсов.** Каждый запрос получает дедлайн 10 с
(`server.go:56-63`), у сервера выставлены Read/Write/Idle-таймауты
(`app.go:28-32`); ожидание блокировки или соединения из пула заканчивается 503 с
безопасным повтором (протестировано на уровне handler). Пул соединений
настраивается через `pool_max_conns` в DATABASE_URL.

**Утечки внутренних ошибок и секретов.** Ответы 500 обезличены
(«internal server error»), детали только в логе — есть тест, что строка с
«password=secret» не попадает в ответ, и тест на панику. Логи запросов содержат
только метод/маршрут/статус/длительность — без тел, query-строк и PII.

**Контейнеры и порты.** Не-root пользователь (uid 10001), минимальный alpine,
CGO выключен, порт PostgreSQL наружу не публикуется, healthcheck по localhost.
Учебный пароль и `sslmode=disable` явно задокументированы в README как
локальные значения.

**Зависимости.** `govulncheck` v1.9.0 (база уязвимостей Go, анализ на уровне
символов): «No vulnerabilities found» для всего модуля с зависимостями.
Базовые образы (alpine, postgres, golang-build) этим инструментом не
сканировались — см. раздел «не выполненные проверки».

**Условия развёртывания для публичной эксплуатации (не дефекты выполнения
задания):** аутентификация и авторизация, TLS-терминация, замена учебного пароля
БД и включение sslmode, ограничение частоты запросов (rate limiting). Без
авторизации ключи идемпотентности образуют общее пространство: узнавший чужой
ключ и точные данные запроса получит чужую бронь в ответе (автор честно описал
это в README и требует непредсказуемые ключи).

## 6. Выполненные проверки и результаты

Команды (из каталога проекта, если не указано иное):

1. `go vet ./...` — чисто.
2. `go build ./...` — собирается.
3. `go test -short -race ./...` — все пакеты ok.
4. `go test -race ./...` (Docker: Testcontainers-PostgreSQL + e2e) — все ok
   (репозиторий ~43 с, e2e ~41 с, включая конкурентные сценарии двух экземпляров
   и SIGKILL-перезапуск).
5. Копия проекта в /tmp/opencode/review_check/project: `go generate ./...` и
   сравнение — сгенерированный код (oapi-codegen, mockgen) идентичен
   закоммиченному.
6. `go run golang.org/x/vuln/cmd/govulncheck@latest ./...` (в копии) — уязвимостей
   не найдено.
7. `docker compose --profile two-instances up --build --wait` — оба экземпляра и
   PostgreSQL здоровы; после проверок `docker compose --profile two-instances
   down -v` (созданные мной контейнеры и том удалены).
8. Собственные сценарии через curl/xargs против `:8080` и `:8081`
   (скрипты: /tmp/opencode/review_check/scenarios*.sh):

   - **Перепродажа.** 200 параллельных запросов по 1 месту (событие capacity=50,
     чередование экземпляров): `50×201, 150×409`, `booked_seats=50`,
     `available_seats=0`.
     Воспроизведение ядра сценария:
     ```bash
     seq 1 200 | xargs -P 50 -I{} bash -c 'B=:8080; (( {} % 2 )) || B=:8081; \
       curl -s -o /dev/null -w "%{http_code}\n" -X POST http://localhost$B/events/$EVENT_ID/bookings \
       -H "Content-Type: application/json" -H "Idempotency-Key: r{}" \
       -d "{\"customer_name\":\"C{}\",\"seats\":1}"' | sort | uniq -c
     ```
   - **Идемпотентность.** 30 параллельных запросов с одним ключом: `1×201,
     29×200` с заголовком `Idempotent-Replayed: true`, одна бронь, места взяты
     один раз. Тот же ключ с другим числом мест/именем → 422
     `idempotency_key_reused`; исходный payload после этого → 200-реплей. На
     заполненном событии тот же новый ключ во всех попытках → 409 (неудачные
     попытки не расходуют ключ, как задокументировано).
   - **Отмена.** 30 параллельных отмен одной брони на двух экземплярах: все 200,
     одно значение `cancelled_at`, `booked_seats` −3 ровно один раз;
     последовательные повторы — 200 без изменений.
   - **Перезапуск.** `docker compose restart app app2`: данные, счётчики и
     реплей ранее использованного ключа (200 + заголовок, места не изменены)
     сохранились.
   - **Валидация/ошибки.** Битый JSON, неизвестное поле, хвост после значения →
     400 `invalid_json`; без Content-Type → 415; тело >1 МиБ → 413; `seats=0`,
     отсутствие ключа, невалидный UUID, `limit=999`, `offset=-1` → 400
     `validation_failed`; несуществующие событие/бронь → 404; `DELETE /events` →
     405, неизвестный путь → 404 (оба в JSON с кодами); `capacity=0`, год 10000,
     `null`-имя, имя с переносом строки, имя 201 символ → 400; имя 200 символов,
     emoji/кириллица, ключ 255 символов → 201; ключ 256 символов и ключ с
     пробелом → 400. После всех отказов данные события не изменились.

## 7. Не выполненные проверки и причины

- **Нагрузочное тестирование до предела** (очередь на блокировку одного события,
  исчерпание пула соединений, поведение при >10 с ожидания): исключено условиями
  ревью (без тяжёлых нагрузочных атак); поведение при таймауте покрыто модульным
  тестом `TestServer_TimedOutRequestIsReportedAsRetryable` и задокументировано.
- **Скан образов на CVE** (alpine/postgres/golang): инструмент типа trivy в
  окружении не использовался; govulncheck покрывает только Go-модули, поэтому о
  уязвимостях базовых образов суждений нет.
- **TLS/реверс-прокси и реальное развёртывание**: вне рамок задачи (авторизация и
  TLS не требуются TASK.md).
- Сборка под другие платформы и `go generate` на Windows не проверялись
  (окружение Linux/amd64).

## 8. Неподтверждённые риски

- **Отказ одного популярного события при высокой нагрузке**: бронирования одного
  события сериализуются блокировкой строки; при шторме запросов часть получит 503
  по таймауту 10 с. Задокументировано автором; мною не воспроизводилось (нет
  нагрузочных проверок). Это компромисс дизайна, а не ошибка.
- **Смещение страниц при вставках между запросами** (offset-пагинация) и её
  замедление на больших смещениях — задокументировано; для текущих объёмов
  некритично.
- **Ключи идемпотентности не истекают** — задокументировано; таблица растёт
  неограниченно при очень длинной жизни сервиса.
- **Поведение при потере БД на середине отмены** (запись в бронь зафиксирована,
  ответ клиенту потерян): клиент повторит отмену и получит актуальное состояние;
  риск только в лишнем клиентском ретрае.

## 9. Необязательные рекомендации

- Для публичного окружения: аутентификация, TLS, rate limiting, замена учебного
  пароля — уже отмечены автором как условия развёртывания.
- Рассмотреть request-id в логах запросов для корреляции с ошибками.
- При росте числа событий/броней — пересмотреть пагинацию (курсорная) и
  `pool_max_conns`; сейчас оба пункта задокументированы как осознанные упрощения.
- Сообщение об ошибке для «хвоста» с неизвестным полем можно уточнить
  (см. заметку в разделе 3), это чистая косметика.

## 10. Сильные стороны

- Корректная и хорошо документированная конкурентная модель: блокировка строки
  события + `ON CONFLICT` по ключу + `CHECK`-ограничение как последняя линия
  защиты; редкий для учебных решений аккуратный разбор случая «незакоммиченный
  тот же ключ на другом событии» с отдельным тестом
  (`TestCreateBooking_WaitsForAnUncommittedSameKey`).
- Отмена одной транзакцией с условным UPDATE — простой и надёжный механизм
  «ровно один раз».
- Миграции: транзакционно, под advisory-lock, с контролем чексумм; безопасный
  одновременный старт двух экземпляров.
- Тщательная обработка ввода: строгий JSON, границы значений, отклонение
  непредставимых в ответах дат (с тестом-обоснованием).
- Тесты трёх уровней с настоящей PostgreSQL, реальным бинарником, двумя
  процессами и SIGKILL; проверка согласованности счётчика с суммой броней.
- Честный и точный README: все проверенные мной утверждения совпали с фактическим
  поведением, включая тонкости семантики ключей.
- Качественная эксплуатационная обвязка: таймауты запросов и сервера,
  graceful shutdown, структурные логи, healthz, не-root контейнер.
