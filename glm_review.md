# Независимое техническое ревью

Объект: сервис бронирования мест (`cmd/server`, `internal/api`, `internal/store`).
Дата проверки: 2026-11-06. Проверка выполнялась по TASK.md, README.md и исходникам; код не изменялся.

---

## 1. Краткое заключение

Заявленные в TASK.md обязательные свойства **подтверждены проверками, дефектов уровня P0–P2 не найдено**:

- **Сохранность данных** — проверена перезапуск приложения, перезапуск БД и полный цикл `docker compose down` / `up` (без `--volumes`): данные сохраняются.
- **Отсутствие перепродажи при конкурентных запросах** — подтверждено собственным стресс-тестом (400 конкурентных запросов на 50 мест через 3 экземпляра) и интеграционными тестами проекта; инвариант `available + SUM(активных) = capacity` проверен прямым SQL.
- **Идемпотентность создания** — 300 одновременных одинаковых запросов с одним `Idempotency-Key` дают ровно одно бронирование; повтор после перезапуска возвращает тот же ID.
- **Однократный возврат мест при отмене** — 100 одновременных отмен дают один `cancelled_at` и однократный возврат мест.
- **Два экземпляра с общей PostgreSQL** — все конкурентные проверки выполнялись на 2–3 экземплярах с отдельными пулами соединений; состояние в процессах не кэшируется.
- **Валидация** — некорректные запросы дают структурированные ошибки 4xx и не создают строк в БД (проверено, в т.ч. отказ 4xx не «резервирует» идемпотентный ключ).
- **Подготовка схемы и повторный запуск** — миграция транзакционна под advisory lock; три одновременных старта на пустой базе корректны; повторный запуск не пересоздаёт данные.
- **Воспроизводимость запуска и тесты** — `docker compose up --build`, `go vet`, `go build`, `go test` и полный интеграционный набор с настоящей PostgreSQL 17 под `-race` проходят с первого раза.

Найдено два подтверждённых замечания уровня **P3** (не влияют на выполнение требований TASK.md): устаревшие версии зависимостей с известными уязвимостями (недостижимые из HTTP-поверхности в текущей конфигурации) и не-JSON ответы net/http на уровне протокола. Подробности ниже.

## 2. Подтверждённые дефекты

### D1. P3 — зависимости содержат известные уязвимости (применимость к коду ограничена)

- **Файлы/строки**: `go.mod:5` (`github.com/jackc/pgx/v5 v5.7.6`), `go.mod:11` (`golang.org/x/crypto v0.37.0` → `golang.org/x/text v0.24.0`).
- **Условие проявления**: для GO-2026-5004 — использование pgx в режиме `default_query_exec_mode=simple_protocol` (проект его не включает: DSN в `compose.yaml:19` и README не задают режим, действует умолчание `QueryExecModeCacheStatement`); для GO-2026-5970/GO-2026-6629 — аутентификация SCRAM с паролем из `DATABASE_URL`, контролируемым оператором, а не HTTP-клиентом.
- **Последствия**: в текущей конфигурации эксплуатация из недоверенного HTTP-ввода не подтверждена. Теоретические эффекты: паника/зависание при старте (x/text по пути SASLprep пароля DSN) и SQL-инъекция при клиентской интерполяции аргументов (pgx `sanitize.SanitizeSQL` — вызывается только из `sanitizeForSimpleQuery`, см. `conn.go:555,831,991` в pgx v5.7.6).
- **Доказательство**: `govulncheck ./...` — «Your code is affected by 3 vulnerabilities from 2 modules» (GO-2026-6629, GO-2026-5970, GO-2026-5004), трассы ведут в `internal/store/store.go:46` (`store.Open` → pgxpool.New) и `store.go:129` (`GetBooking` → QueryRow → SanitizeSQL). Анализ применимости: в `pgx v5.7.6/conn.go` `sanitizeForSimpleQuery` вызывается только в ветках `QueryExecModeSimpleProtocol`, а умолчание — `QueryExecModeCacheStatement` (`conn.go:195`), т.е. параметры биндятся на стороне сервера и `SanitizeSQL` в рантайме проектом не вызывается.
- **Направление исправления**: поднять `pgx/v5` до ≥ v5.9.2 и `x/text` (транзитивно через `x/crypto`) до ≥ v0.41.0, обновить `go.sum`. Дешёвая, безопасная правка гигиены зависимостей.

### D2. P3 — ответы на уровне протокола net/http не соответствуют заявленному формату JSON

- **Файл/строки**: `cmd/server/main.go:49` (конфигурация `http.Server`), обёртка `internal/api/api.go:43-58` не покрывает этот случай.
- **Условие проявления**: заголовки больше ~20 КиБ (MaxHeaderBytes 16384 + внутренний запас net/http 4096) или синтаксически некорректная строка запроса.
- **Последствия**: клиент получает `431 Request Header Fields Too Large` / `400 Bad Request` обычным текстом, что противоречит README («Все ответы API — JSON»). Функционального влияния нет; ошибки возникают до маршрутизатора, ниже уровня приложения.
- **Доказательство**: `curl -H "X-Big: $(python3 -c 'print("a"*100000)')" http://localhost:8081/healthz` → `HTTP/1.1 431 Request Header Fields Too Large` + `Content-Type: text/plain`. Заголовки до 20 000 байт проходят (стандартное поведение Go: `initialReadLimitSize = MaxHeaderBytes + 4096`).
- **Направление исправления**: такие ответы формирует сам `net/http` до хендлера; практичнее уточнить формулировку README («все ответы маршрутов API — JSON; протокольные ошибки соединения — нет») либо, при желании, терминировать HTTP за прокси, нормализующим ошибки.

Дефектов P0/P1/P2 (нарушение guarantees TASK.md, потеря/порча данных, перепродажа, дубли, race, невоспроизводимый запуск) **не обнаружено**.

## 3. Неподтверждённые риски и необязательные рекомендации

### Неподтверждённые риски

- **Отсутствие лимита соединений/частоты запросов**: `net/http` принимает неограниченное число соединений; локальная атака локальным процессом может исчерпать память/файлы или пул соединений pgx (по умолчанию max conns = числу CPU). Для локального запуска допустимо (README это документирует), для публичного развёртывания — обязательное условие (reverse proxy с лимитами).
- **Переполнение таблиц**: ключи идемпотентности и бронирования хранятся бессрочно, автоочистки нет. Заявлено в README как ограничение; рост диска — вопрос эксплуатации, не дефект.
- **Образы по тегам, не digest** (`compose.yaml:3`, `Dockerfile:1,9`): supply-chain риск дрейфа образа при пересборке. README честно отмечает; при воспроизводимой поставке стоит закрепить digest.
- **Прямые записи в БД вне сервиса** могут нарушить инвариант `available + SUM(active) = capacity` — задокументировано; CHECK-ограничения снижают, но не устраняют риск.
- **`New(nil, ...)` в `internal/api/api_test.go:12`**: хендлеры получают nil-хранилище; тест работает только потому, что отвергаемые запросы не доходят до store. При изменении порядка проверок в хендлерах появится nil-panic в тесте. Скрытая хрупкость, не влияет на продакшн-код.

### Необязательные рекомендации

- `GET /events/{id}/cancel` возвращает 404, тогда как `GET /bookings/{id}/cancel` — 405 c `Allow` (асимметрия в `api.go:61-76`). HTTP-семантике не противоречит; полировка.
- `store.Store` публично раскрывает `*pgxpool.Pool` (`store.go:26`): транспортный слой пингует пул напрямую (`api.go:264`). На текущем масштабе оправдано (healthz, тестовые SQL-проверки), но связывает api с деталью хранения.
- Дубликаты JSON-полей (`{"capacity":5,"capacity":7}`) принимаются, действует «последнее значение» (стандарт `encoding/json`). При желании можно отвергать.
- В `api.go:47-57` на каждый запрос выполняется двойный поиск маршрута (`mux.Handler` + `mux.ServeHTTP`) — сознательная плата за JSON-обёртку ошибок маршрутизации; на этом масштабе несущественно.

Стилистические предпочтения (имена, расположение функций, отсутствие интерфейсов) дефектами не считал.

## 4. Архитектура

**Соразмерность.** Решение соответствует небольшой задаче: 3 пакета, ~560 строк кода приложения (`main.go` 67, `api.go` 271, `store.go` 200, `schema.sql` 21). Нет лишних слоёв, интерфейсов «на всякий случай», DI-фреймворков, генерации. Избыточной сложности не найдено; упрощений, мешающих поддержке, тоже.

**Разделение ответственности и направление зависимостей.** Зависимости однонаправленны: `cmd/server` → `internal/api` → `internal/store` → PostgreSQL. Транспорт (парсинг, валидация, маппинг ошибок в HTTP-коды) — в `api`; SQL, транзакции и схема — в `store`; склейка и жизненный цикл — в `main.go` (`main.go:26-67`: проверка DATABASE_URL, миграция до открытия порта, graceful shutdown). Каждый файл читается за один присест.

**Размещение инвариантов и границы транзакций.** Ключевое архитектурное решение — все межпроцессные гарантии перенесены в PostgreSQL, в процессах нет локальных mutex/кэшей. Примеры: создание бронирования — `INSERT ... ON CONFLICT (idempotency_key) DO NOTHING` + условный `UPDATE events SET available=available-$2 WHERE available>=$2` в одной транзакции (`store.go:135-173`); отмена — условный `UPDATE ... WHERE status='active'` + возврат мест в одной транзакции (`store.go:179-199`). Отсюда корректность для двух и более экземпляров «бесплатно» и проверяема. Диапазоны и связи дополнительно защищены CHECK/FK/UNIQUE (`schema.sql:1-21`), что подтверждено тестом `TestIntegrationDatabaseConstraints`. Компромисс — денормализованный счётчик `available`: сериализация записей на строке популярного события; README явно называет это ограничение. Для задачи такого размера компромисс разумный: альтернатива (агрегирующий SELECT) усложнила бы условие атомарности.

**Тестируемость.** Высокая: API тестируется через `httptest` без БД (таблица отвергаемых запросов, `api_test.go`), интеграционные тесты поднимают два «процесса» с независимыми пулами на общую схему (`integration_test.go:80-105`), каждая проверка получает случайную схему и убирает её за собой. Миграции тестируются на параллельный старт из двух пулов на пустой схеме — это именно то место, где обычно ошибаются.

**Понятность и стоимость изменений.** SQL собран из именованных констант (`store.go:99-100`), комментарии объясняют не «что», а «почему» (спеку конкурентности: `store.go:57,132-133,165,176-177`). Добавление поля затрагивает schema.sql, структуру, константу колонок, DTO и тесты — изменения локализованы по одному месту на уровень. README фиксирует принятые решения и ограничения честно и точно, включая неочевидное поведение (ключ не резервируется при 4xx; повтор после отмены возвращает отменённую бронь).

**Замечания к архитектуре** — только перечисленные выше рекомендации (публичный `Pool`, `New(nil, ...)` в тесте); ни одно не блокирующее.

## 5. Безопасность

**Предполагаемая модель угроз и границы доверия** (явно в README не сформулирована, восстанавливается из кода и конфигурации): HTTP-клиент на loopback — недоверенный (любой локальный процесс); оператор, задающий `DATABASE_URL` — доверенный; PostgreSQL — доверенный, во внутренней сети контейнера. Авторизация отсутствует — прямо разрешено TASK.md и задокументировано («любой клиент с ID может просмотреть/отменить бронирование»). Для публичной эксплуатации необходимы: TLS-терминация, аутентификация/авторизация, rate limiting, собственные секреты вместо пароля из compose, резервное копирование и HA PostgreSQL — README перечисляет эти условия сам (`README.md:226-228`).

**SQL-инъекции.** Все запросы параметризованы (`$1`, `$2` — `store.go:121,125,129,140,146,152,166,184,187,196`); конкатенация применяется только к статическим константам `eventColumns`/`bookingColumns`. В `api` SQL отсутствует. Имя схемы в интеграционных тестах (`integration_test.go:56,67`) генерируется из hex `crypto/rand` — инъекция невозможна. Эксплуатируемых путей не найдено. См. также D1 по pgx.

**Недоверенный JSON.** Строгий и продуманный конвейер (`api.go:106-139`): обязательный `Content-Type: application/json` (415), лимит 16 КиБ с корректным 413, проверка валидности UTF-8, `DisallowUnknownFields`, ровно один JSON-документ, строгая типизация int (дробные/экспоненциальные/строки/переполнение отвергаются — проверено live), диапазоны 1..1 000 000, имя 1–200 code points без NUL, ключ 1–128 ASCII по whitelist-регексу, UUID только в канонической форме. Отмена требует пустое тело. Проверено вживую ~30 некорректными запросами — все 4xx, формат единый, данных не портят.

**Ограничения размера и таймауты.** Тело 16 КиБ; заголовки 16 КиБ (см. D2); `ReadHeaderTimeout` 5с, `ReadTimeout`/`WriteTimeout` 15с, `IdleTimeout` 60с (`main.go:49`); per-request контекст 10с → 503 `timeout` (проверено live на приостановленной БД). Лимитов соединений/RPS нет — риск задокументирован выше.

**Утечки внутренних ошибок и секретов.** 500 отдаёт generic-сообщение, детали — только в серверный лог (`api.go:100-103`); SQL-ошибки клиенту не транслируются. Проверено: при остановленной БД ответы содержат только код/сообщение без внутренних деталей. Ошибки старта с некорректным `DATABASE_URL` логируются с маскированием пароля (`xxxxx` — поведение pgx, проверено live двумя вариантами битого DSN). В логах нет параметров запросов и секретов.

**Логирование.** JSON slog в stdout, только ошибки и событие старта. Отрицательный момент для эксплуатации — отсутствие access-лога (не требовалось задачей).

**Контейнеры и порты.** Образ: multi-stage, `CGO_ENABLED=0`, alpine 3.22, непривилегированный пользователь (проверено: `uid=10001(app)`), минимальный `.dockerignore`. Приложение публикуется только на `127.0.0.1` (`compose.yaml:22`), PostgreSQL наружу не публикуется вовсе. Тестовая БД (`compose.test.yaml`) — tmpfs, случайный loopback-порт, уникальное имя проекта, очистка строго своих ресурсов (`scripts/test-integration.sh`) — проверено: после прогона контейнеров/сетей/томов не остаётся. Пароль в compose захардкожен и задокументирован как локальная конфигурация.

**Зависимости.** Инструмент: `govulncheck` (последняя версия, symbol-level). Результат: 3 достижимые уязвимости в 2 модулях (GO-2026-6629, GO-2026-5970, GO-2026-5004) — детали и анализ применимости в D1: ни одна не достижима из недоверенного HTTP-ввода в текущей конфигурации (pgx — только режим simple_protocol, который не включён; x/text — только пароль DSN оператора). Утверждать полное отсутствие уязвимостей нельзя; подтверждённых эксплуатируемых — нет.

**Условия развёртывания (не дефекты)**: TLS, аутентификация, лимиты, секреты, бэкапы — перечислены в README как необходимые для внешней публикации.

## 7. Сильные стороны решения

- **Корректность конкурентных гарантий через СУБД**: уникальный индекс + `ON CONFLICT DO NOTHING` + условный UPDATE с повторной проверкой предиката в READ COMMITTED — без локальных блокировок; доказано тестами на двух-трёх экземплярах и моими стресс-проверками.
- **Точная семантика идемпотентности**: сравнение нормализованного `event_id` и `quantity`; 4xx не резервирует ключ; повтор после отмены возвращает исходную бронь — всё задокументировано и покрыто тестами, включая гонку разных тел с одним ключом.
- **Качественный тестовый набор**: настоящая PostgreSQL, race-детектор, два HTTP-сервера с независимыми пулами, точные ожидания (18 созданных из 60, одинаковый `cancelled_at`), SQL-проверка инварианта, изоляция по случайным схемам, безопасный самодельный compose-раннер с гарантированной очисткой.
- **Аккуратный HTTP-слой**: единый JSON-формат ошибок, 413/415/405+`Allow`, `Location`, `Cache-Control: no-store`, отклонение мультидокументного/unknown-field/невалидного UTF-8 JSON, пустое тело отмены.
- **Безопасное развёртывание по умолчанию**: non-root контейнер, публикация только на loopback, БД не экспонирована, tmpfs-тестовая база, fail-fast при ошибке старта, миграция до открытия порта, graceful shutdown.
- **Честная документация**: README фиксирует решения, компромиссы (сериализация на строке события, бессрочное хранение ключей, отсутствие лимитов) и сценарий «неизвестный исход транзакции — повтори с тем же ключом».
