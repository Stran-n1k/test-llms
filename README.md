# Бронирование мест

Небольшой HTTP JSON API на Go и PostgreSQL. Событие имеет фиксированную
вместимость, бронирование занимает несколько мест целиком. Состояние хранится
в PostgreSQL; несколько процессов приложения могут работать с одной базой.

## Запуск

Нужны Docker и Docker Compose v2+:

```sh
docker compose up --build -d
curl -i http://localhost:8080/healthz
docker compose logs app
```

Если порт занят: `PORT=8081 docker compose up --build -d`. API опубликован
только на loopback; PostgreSQL наружу не опубликована. Данные находятся в
именованном томе `postgres_data` текущего Compose-проекта и сохраняются при
перезапуске приложения, БД и `docker compose down`:

```sh
docker compose restart app
docker compose down
docker compose up -d
```

`docker compose down --volumes` удаляет данные этого проекта; для обычной
остановки эту опцию использовать не нужно. Пароль из Compose предназначен
для локального запуска.

Дополнительный экземпляр на той же БД можно запустить в другом терминале:

```sh
docker compose run --rm -p 127.0.0.1:8081:8080 app
```

Для запуска без контейнера нужны Go 1.24+ и доступная PostgreSQL 17:

```sh
go mod download
export DATABASE_URL='postgres://user:password@localhost:5432/booking?sslmode=disable'
export HTTP_ADDR='127.0.0.1:8080'
go run ./cmd/server
# либо
go build -o bin/server ./cmd/server
./bin/server
```

`DATABASE_URL` обязателен. `HTTP_ADDR` по умолчанию `:8080`. Параметры пула
pgx можно задать в URL, например `pool_max_conns=16&connect_timeout=5`.
Приложение проверяет БД и применяет схему до открытия HTTP-порта. При ошибке
старта завершается с ненулевым кодом. На SIGINT/SIGTERM завершает текущие
запросы (до 20 секунд) и закрывает пул. Логи — JSON в stdout.

## API

POST с JSON требует `Content-Type: application/json`. Максимальный JSON —
16 KiB, неизвестные поля, несколько JSON-документов, некорректные типы и
невалидный UTF-8 отвергаются. UUID передаётся с дефисами; регистр hex не важен.
Вместимость и число мест — целые от 1 до 1 000 000. Имя после удаления
пробелов по краям — от 1 до 200 символов Unicode, без NUL.

| Метод и маршрут | Назначение | Успех |
| --- | --- | --- |
| `POST /events` | Создать событие: `name`, `capacity` | `201` + событие |
| `GET /events/{id}` | Событие и актуальное число свободных мест | `200` + событие |
| `POST /bookings` | Забронировать: `event_id`, `quantity`; заголовок `Idempotency-Key` | `201` при создании, `200` при повторе |
| `GET /bookings/{id}` | Просмотреть бронирование | `200` + бронирование |
| `POST /bookings/{id}/cancel` | Отменить бронирование, пустое тело | `200` + бронирование, в том числе при повторе |
| `GET /healthz` | Проверить соединение с БД | `200 {"status":"ok"}` или `503` |

GET также поддерживает HEAD. Успешное создание возвращает `Location` с
адресом ресурса. Все ответы API — JSON; время в RFC 3339 с часовым поясом.

### Примеры

```sh
curl -i -X POST http://localhost:8080/events \
  -H 'Content-Type: application/json' \
  -d '{"name":"Концерт","capacity":100}'
```

Пример тела ответа:

```json
{"id":"11618235-37a5-45bb-808b-73bb4b6cb132","name":"Концерт","capacity":100,"available":100,"created_at":"2026-11-06T00:00:00Z"}
```

Подставьте фактический `id` из ответа:

```sh
EVENT_ID='11618235-37a5-45bb-808b-73bb4b6cb132'
curl -i "http://localhost:8080/events/$EVENT_ID"
curl -i -X POST http://localhost:8080/bookings \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: order-2026-001' \
  -d "{\"event_id\":\"$EVENT_ID\",\"quantity\":3}"
```

Пример бронирования:

```json
{"id":"15dff259-a630-44b1-bca1-31658c99f5dd","event_id":"11618235-37a5-45bb-808b-73bb4b6cb132","quantity":3,"status":"active","created_at":"2026-11-06T00:01:00Z","cancelled_at":null}
```

Повторите тот же POST с тем же ключом — получите `200` и тот же `id`, без
дополнительного списания. Для просмотра и отмены подставьте `id` бронирования:

```sh
BOOKING_ID='15dff259-a630-44b1-bca1-31658c99f5dd'
curl -i "http://localhost:8080/bookings/$BOOKING_ID"
curl -i -X POST "http://localhost:8080/bookings/$BOOKING_ID/cancel"
curl -i -X POST "http://localhost:8080/bookings/$BOOKING_ID/cancel"
curl -i "http://localhost:8080/events/$EVENT_ID"
```

Отмена возвращает `status: "cancelled"` и заполненный `cancelled_at`.
Повторы сохраняют этот timestamp и возвращают места только один раз.

### Ошибки

Единый формат, например при нехватке мест:

```json
{"error":{"code":"insufficient_capacity","message":"not enough available seats"}}
```

| HTTP | Причины |
| --- | --- |
| `400` | Некорректный JSON, UUID, имя, вместимость, количество, ключ; непустое тело отмены |
| `404` | Событие, бронирование или маршрут не найден |
| `405` | Неподдерживаемый метод; заголовок `Allow` содержит разрешённые |
| `409 insufficient_capacity` | Недостаточно мест; частичного бронирования нет |
| `409 idempotency_conflict` | Ключ уже относится к другому событию или количеству |
| `413` | JSON больше 16 KiB |
| `415` | Отсутствующий/неверный Content-Type для JSON POST |
| `500` / `503` | Внутренняя ошибка, таймаут (10 секунд операций API) или недоступная БД |

Технические ошибки SQL не выдаются клиенту. При обрыве соединения/таймауте
исход транзакции может быть неизвестен клиенту: повторите запрос с тем же
ключом, с задержкой. Отмену также можно безопасно повторить по тому же ID.

## Целостность и повтор запросов

* `Idempotency-Key` обязателен при создании бронирования: ровно один заголовок,
  1–128 ASCII-символов из `A-Z a-z 0-9 . _ : -`. Клиент создаёт новый случайный
  ключ (например UUID) на каждое намерение бронирования, сохраняет его до
  отправки и использует при всех повторах. Ключ глобален в рамках этой БД.
* Уникальное ограничение PostgreSQL на ключе разрешает только одну вставку.
  `INSERT ... ON CONFLICT DO NOTHING` ждёт незавершённый конкурентный запрос.
  Следующий SELECT при `READ COMMITTED` видит его результат. Сравниваются
  нормализованный `event_id` и `quantity`, а не байты JSON.
* Вставка бронирования и `UPDATE events SET available=available-quantity
  WHERE available>=quantity` выполняются в одной транзакции. Конкурентные
  UPDATE сериализуются на строке события и перепроверяют условие после
  ожидания. Неудача откатывает и вставку, и ключ. Нехватка мест/ошибка 4xx
  ключ не резервирует: последующий запрос может выполниться после отмены
  другого бронирования. Записываются только успешные бронирования.
* Отмена условно обновляет только `status='active'` и в той же транзакции
  возвращает места. Проигравшие конкурентные отмены читают готовое состояние.
  Ключ остаётся навсегда: повтор создания после отмены возвращает исходное
  **отменённое** бронирование и не создаёт новое. Для нового нужен новый ключ.
* Все блокировки и уникальность находятся в PostgreSQL, локальных mutex для
  обеспечения этих гарантий нет. При падении процесса незавершённая транзакция
  откатывается. CHECK/FK дополнительно защищают диапазоны и связи. Инвариант
  сервиса: `available + SUM(quantity активных бронирований) = capacity`.

Схема находится в `internal/store/schema.sql`, встраивается в бинарник.
Версия в `schema_migrations`. Миграция и запись версии — одна транзакция под
advisory lock PostgreSQL: одновременно стартующие процессы безопасно готовят
пустую БД. Повторный запуск ничего не пересоздаёт и не очищает; неизвестная
версия схемы останавливает приложение. Права роли должны позволять DDL.

## Проверки

Быстрые проверки (интеграционные тесты явно пропускаются, если URL не задан):

```sh
go test ./...
go vet ./...
go build ./cmd/server
```

Полный набор с настоящей PostgreSQL и детектором гонок:

```sh
./scripts/test-integration.sh -v
```

Скрипт создаёт отдельный Compose-проект с уникальным именем, PostgreSQL на
случайном локальном порту и tmpfs, ждёт готовности и запускает
`go test -race -count=1 -timeout=120s ./...`. По завершении удаляет только
собственные контейнер/сеть. Нужны Docker, Go и C-компилятор для `-race`.

Можно использовать свою тестовую PostgreSQL, без Docker:

```sh
TEST_DATABASE_URL='postgres://user:password@localhost:5432/booking_test?sslmode=disable' \
  REQUIRE_INTEGRATION=1 go test -race -count=1 -timeout=120s ./... -v
```

Роль тестов должна иметь право создавать схемы. Каждый интеграционный тест
создаёт собственную случайную схему, задаёт `search_path` у обоих пулов и
удаляет только эту схему. Нельзя направлять тесты на production.
`REQUIRE_INTEGRATION=1` превращает отсутствие URL в ошибку вместо пропуска.

Покрыты полный жизненный цикл и доступность, перезапуск всех серверов и
пулов с повторной миграцией, параллельные миграции на пустой схеме,
60 конкурентных попыток купить места, 50 повторов одного ключа, гонка разных
тел с одним ключом, 50 одновременных отмен, смешанная гонка создания/повтора/
отмены, ограничения БД и некорректные HTTP-запросы. Конкурентные проверки
чередуют два HTTP-сервера с независимыми пулами к общей схеме PostgreSQL.

## Допущения и ограничения

* Нет авторизации, пользователей, UI, Redis, Kubernetes, платежей и срока
  действия брони. Любой клиент с ID может просмотреть/отменить бронирование.
* Места не нумеруются. Время проведения события не моделируется; событие —
  имя и фиксированная вместимость. Списков, поиска, изменения/удаления событий
  и бронирований нет; чтение по ID. Создание события не идемпотентно.
* Доступность — снимок на момент чтения; успех гарантирует только POST
  бронирования. Популярное событие сериализует записи на своей строке БД.
* Ключи и бронирования хранятся бессрочно; автоматической очистки нет.
  Прямые записи в БД вне сервиса могут нарушить межтабличный инвариант.
* Compose — локальная конфигурация: нет TLS, резервного копирования,
  ограничения частоты запросов и высокой доступности PostgreSQL. Для внешней
  публикации нужны соответствующая инфраструктура и собственные секреты.
* При отмене/таймауте клиента commit может уже завершиться: безопасный повтор
  требует сохранённого ключа. Автоматического повтора SQL в сервере нет.
  Образы Docker закреплены по версиям веток, а не digest; Go-модули закреплены
  точными версиями и контрольными суммами.
