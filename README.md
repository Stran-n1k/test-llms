# Сервис бронирования мест

Backend на Go и PostgreSQL: события с ограниченной вместимостью, просмотр
доступности, бронирование нескольких мест одним запросом, просмотр и отмена
бронирований. Контракт API описан в [`api/rest/openapi.yaml`](api/rest/openapi.yaml).

## Запуск

Нужны Docker и Docker Compose.

```bash
docker compose up --build --wait     # приложение на http://localhost:8080
docker compose --profile two-instances up --build --wait   # плюс второй экземпляр на :8081
docker compose --profile two-instances down                # остановить; данные остаются в томе
docker compose --profile two-instances down -v             # остановить и удалить данные
```

Порты меняются через `APP_PORT` и `APP2_PORT`. Схема базы готовится автоматически
при старте приложения.

Без Docker для приложения (нужны Go 1.27 и доступная PostgreSQL):

```bash
DATABASE_URL='postgres://user:pass@localhost:5432/booking?sslmode=disable' \
HTTP_ADDR=':8080' \
go run ./cmd/booking
```

| Переменная | Значение |
| --- | --- |
| `DATABASE_URL` | Обязательна. Строка подключения; размер пула задаётся параметром `pool_max_conns`. |
| `HTTP_ADDR` | Адрес HTTP-сервера, по умолчанию `:8080`. |

## Тесты

```bash
go test -short -race ./...   # только модульные, Docker не нужен
go test -race ./...          # все, включая настоящую PostgreSQL; нужен Docker
```

Без `-short` и без Docker тесты завершаются ошибкой, а не пропускаются молча.

| Уровень | Где | Что проверяет |
| --- | --- | --- |
| Модульные | `internal/model`, `internal/service`, `internal/handler/rest` | Валидация, разбор запросов, отображение ошибок в статусы |
| Интеграционные | `internal/repository/postgres` | Все методы репозитория на PostgreSQL в Testcontainers, конкурентность, миграции; у каждого теста своя база |
| Сквозные | `test/e2e` | Настоящий бинарник: два процесса на одной базе, конкурентные HTTP-запросы, перезапуск после `SIGKILL` |

После изменения `api/rest/openapi.yaml` или интерфейсов в `dependency.go`
перегенерируйте код: `go generate ./...`.

## Примеры запросов

Создать событие:

```bash
curl -i -X POST localhost:8080/events \
  -H 'Content-Type: application/json' \
  -d '{"name":"Концерт","starts_at":"2030-01-31T19:00:00+03:00","capacity":10}'
```

```json
{"available_seats":10,"booked_seats":0,"capacity":10,"created_at":"2026-11-05T16:55:39.733361Z","id":"40ab1065-1a1e-4f9e-97ec-4c87cc23e39a","name":"Концерт","starts_at":"2030-01-31T16:00:00Z"}
```

Посмотреть доступность и список событий:

```bash
curl localhost:8080/events/$EVENT_ID
curl 'localhost:8080/events?limit=20&offset=0'
```

Забронировать места. Повтор с тем же ключом не создаёт дубликат:

```bash
KEY=$(uuidgen)
curl -i -X POST localhost:8080/events/$EVENT_ID/bookings \
  -H 'Content-Type: application/json' \
  -H "Idempotency-Key: $KEY" \
  -d '{"customer_name":"Анна","seats":3}'
```

```json
{"created_at":"2026-11-05T16:56:00.1Z","customer_name":"Анна","event_id":"40ab1065-1a1e-4f9e-97ec-4c87cc23e39a","id":"7f0c3f7e-8a51-4a57-9d3c-0d3a1c9a2b11","seats":3,"status":"confirmed"}
```

Посмотреть бронирования и отменить:

```bash
curl localhost:8080/bookings/$BOOKING_ID
curl 'localhost:8080/events/'$EVENT_ID'/bookings?limit=20'
curl -X POST localhost:8080/bookings/$BOOKING_ID/cancel
```

Пример ошибки:

```json
{"error":{"code":"insufficient_seats","message":"not enough seats: requested 5, available 2"}}
```

## Маршруты и ответы

| Запрос | Успех | Ошибки |
| --- | --- | --- |
| `POST /events` | 201 | 400, 413, 415 |
| `GET /events?limit&offset` | 200 | 400 |
| `GET /events/{event_id}` | 200 | 400, 404 |
| `POST /events/{event_id}/bookings` | 201, повтор 200 | 400, 404, 409, 413, 415, 422 |
| `GET /events/{event_id}/bookings?limit&offset` | 200 | 400, 404 |
| `GET /bookings/{booking_id}` | 200 | 400, 404 |
| `POST /bookings/{booking_id}/cancel` | 200 | 400, 404 |
| `GET /healthz` | 200 | 503 |

Все ошибки имеют вид `{"error":{"code","message","fields"?}}`. Поле `code`
стабильно и предназначено для программ:

| Код | Статус | Значение |
| --- | --- | --- |
| `invalid_json` | 400 | Тело не разбирается, лишнее поле, неверный тип |
| `validation_failed` | 400 | Значения недопустимы; подробности в `fields` |
| `unsupported_media_type` | 415 | `Content-Type` не `application/json` |
| `payload_too_large` | 413 | Тело больше 1 МиБ |
| `not_found`, `method_not_allowed` | 404, 405 | Нет такого маршрута или метода |
| `event_not_found`, `booking_not_found` | 404 | Нет такого события или бронирования |
| `insufficient_seats` | 409 | Мест не хватает; ничего не забронировано |
| `idempotency_key_reused` | 422 | Ключ уже использован для другого запроса |
| `service_unavailable` | 503 | База недоступна или запрос не уложился в 10 с; повтор безопасен |
| `internal_error` | 500 | Внутренняя ошибка; детали только в логе |

## Принятые решения

**Места взаимозаменяемы.** Бронирование берёт количество мест, а не конкретные
номера: в задаче есть вместимость, но нет схемы зала. Бронирование одним запросом
выполняется целиком или не выполняется совсем.

**Защита от перепродажи.** Бронирование идёт в транзакции и начинается с
`SELECT ... FOR NO KEY UPDATE` строки события. Поэтому все бронирования одного
события выполняются по очереди во всех экземплярах сервиса, а проверка остатка и
его изменение не разделены гонкой. Счётчик `events.booked_seats` дополнительно
защищён ограничением `CHECK (booked_seats BETWEEN 0 AND capacity)`: даже ошибка в
коде не сможет записать перепродажу.

**Безопасный повтор создания бронирования: заголовок `Idempotency-Key`.** Клиент
генерирует ключ (например, UUID) один раз на одно намерение и передаёт его при
каждом повторе. Заголовок обязателен: необязательная защита от дублей не защищает
именно тогда, когда клиент о ней забыл.

- Первый успешный запрос отвечает 201. Повтор отвечает 200, заголовком
  `Idempotent-Replayed: true` и тем же бронированием в его текущем состоянии.
- Ключ глобален, и его хранит `UNIQUE` на `bookings.idempotency_key`. Повтор
  распознаётся под блокировкой события, поэтому ожидавший запрос получит готовое
  бронирование, даже если первый запрос занял последние места.
- Ключ с другими данными (событие, имя, число мест) получает 422 и ничего не меняет.
- Неудачные попытки не запоминаются: повтор после 409 проверяется заново и может
  пройти, если места освободились. Ключ расходуется только успешным бронированием.
- Повтор после отмены возвращает отменённое бронирование и не бронирует заново.
  Чтобы забронировать снова, нужен новый ключ.

Ответ 500, 503 или обрыв связи не говорят о том, зафиксирована ли транзакция.
Поэтому клиент повторяет запрос с тем же ключом и получает правильный результат в
любом случае.

**Отмена ровно один раз.** Отмена — это транзакция из условного
`UPDATE bookings ... WHERE id = $1 AND status = 'confirmed'` и возврата мест.
Конкурентные запросы ждут блокировку строки бронирования, затем видят новый статус
и не меняют ни одной строки. Все вызовы отвечают 200 с отменённым бронированием, а
`cancelled_at` хранит время первой отмены. Статус переходит только из `confirmed`
в `cancelled`.

**Два экземпляра.** Вся координация находится в PostgreSQL: блокировки строк,
ограничения и advisory lock для миграций. В памяти приложения общего состояния нет.
Блокировки всегда берутся в порядке, исключающем цикл: создание держит только
событие, отмена — бронирование и затем событие, а новую строку бронирования никто
другой заблокировать не может.

**Схема.** Миграции встроены в бинарник (`internal/repository/postgres/migrations`)
и применяются при старте в одной транзакции под `pg_advisory_xact_lock`. Поэтому
одновременный старт экземпляров безопасен, сбой не оставляет схему наполовину
применённой, а повторный запуск ничего не меняет. Если файл уже применённой миграции
изменён, сервис откажется стартовать.

**Строгий разбор запросов.** Неизвестные поля и данные после JSON-значения
отклоняются: опечатка в поле не должна молча менять смысл запроса.

**Структура.** `handler/rest` (код сгенерирован из OpenAPI через `oapi-codegen`,
JSON разбирается вручную ради строгих ошибок) → `service` (правила и нормализация)
→ `repository/postgres` (SQL и транзакции), общие контракты лежат в `model`. Драйвер
— `pgx`. Миграции написаны без отдельной библиотеки: это около 80 строк, и они дают
нужную блокировку и транзакционность.

**Допущения.**

- `customer_name` и `name` обязательны, от 1 до 200 символов после обрезки пробелов,
  без управляющих символов.
- `capacity` и `seats` — целые от 1 до 2147483647.
- `starts_at` — RFC 3339 с годом от 1 до 9999 в UTC; в ответах всегда UTC.
- Списки упорядочены от старых к новым; `limit` от 1 до 200 (по умолчанию 50),
  `offset` от 0.

## Известные ограничения

- **Нет авторизации** (по условию задачи): любой клиент читает и отменяет любое
  бронирование, а ключи идемпотентности общие для всех клиентов. Поэтому ключ должен
  быть непредсказуемым, например UUID: чужой повтор с тем же ключом и теми же данными
  получит чужое бронирование.
- **Ключи идемпотентности не истекают**: они живут столько же, сколько бронирование.
- **Создание события не идемпотентно**: повтор `POST /events` создаст второе событие.
  Гарантия из задачи относится к бронированиям.
- **Время не учитывается**: можно создать событие в прошлом и бронировать или
  отменять места на уже прошедшее событие.
- **Нет изменения и удаления** событий, изменения бронирований и повторной активации
  отменённых.
- **Одно популярное событие обрабатывается последовательно**: бронирования одного
  события ждут блокировку его строки. Разные события друг другу не мешают. При очень
  высокой нагрузке на одно событие запросы упрутся в таймаут 10 с и получат 503.
- **Пагинация по смещению** проста, но при вставках между запросами страницы могут
  сдвигаться; на больших смещениях она медленнее.
- **Пароль в `compose.yaml` учебный**, а `sslmode=disable` рассчитан на локальный
  запуск. Для реального окружения их нужно заменить. Порт PostgreSQL наружу не
  публикуется.
- **Нет метрик и трассировки**: только структурные JSON-логи запросов и `GET /healthz`.
- **Откат миграций не предусмотрен**: схема только дополняется новыми файлами.
