# Сервис бронирования мест

Небольшой законченный backend на Go + PostgreSQL для бронирования мест на
событиях: создание событий с ограниченной вместимостью, просмотр
доступности, бронирование нескольких мест одним запросом, просмотр и
отмена бронирований. Гарантии корректности работают и для нескольких
экземпляров сервиса с общей базой.

## Быстрый старт

```bash
docker compose up --build -d
# приложение: http://localhost:8080, PostgreSQL опубликован только внутри compose
docker compose ps          # оба сервиса healthy
curl -s localhost:8080/healthz
```

Останов и удаление (данные в volume `booking-pgdata` сохраняются, пока не
удалён volume):

```bash
docker compose down        # без удаления данных
docker compose down -v     # с удалением данных
```

Запуск без Docker (нужна доступная PostgreSQL):

```bash
export DATABASE_URL='postgres://booking:booking@localhost:5432/booking?sslmode=disable'
export HTTP_ADDR=':8080'   # необязательно, по умолчанию :8080
go run ./cmd/server
```

При старте приложение само применяет миграции (идемпотентно, без потери
данных при повторном запуске на существующей базе).

## HTTP API

Все ответы — JSON. Ошибки имеют вид
`{"error": {"code": "...", "message": "..."}}`.

### `POST /events` — создать событие

```bash
curl -s -XPOST localhost:8080/events -H 'Content-Type: application/json' \
  -d '{"name": "Концерт", "capacity": 100}'
```

```json
{"id":1,"name":"Концерт","capacity":100,"created_at":"2026-11-06T00:00:00Z",
 "booked_seats":0,"available_seats":100}
```

Ограничения: `name` 1–200 символов, `capacity` 1–100000. Ошибка валидации —
`400 invalid_request`.

### `GET /events` — список событий

Возвращает массив событий с количеством занятых/свободных мест.

### `GET /events/{id}` — событие и доступность

```json
{"id":1,"name":"Концерт","capacity":100,"created_at":"...",
 "booked_seats":2,"available_seats":98,"available_seat_numbers":[3,4,5,...]}
```

`available_seat_numbers` — номера свободных мест (места нумеруются от 1 до
`capacity`). Неизвестный id — `404 not_found`.

### `POST /bookings` — забронировать места

```bash
curl -s -XPOST localhost:8080/bookings -H 'Content-Type: application/json' \
  -d '{"event_id": 1, "seats": [1, 2, 3], "idempotency_key": "order-4711"}'
```

```json
{"id":5,"event_id":1,"seats":[1,2,3],"status":"confirmed",
 "created_at":"2026-11-06T00:00:00Z"}
```

Ключ идемпотентности передаётся в теле (`idempotency_key`) или в заголовке
`Idempotency-Key` (заголовок приоритетнее), 1–128 символов, уникален в
рамках события. Первый успешный запрос возвращает `201 Created`, точное
повторение (тот же ключ и то же событие) — `200 OK` с тем же бронированием
и **не создаёт дубликат**. Повтор с другими местами возвращает исходное
бронирование без изменений. Повтор после отмены возвращает то же
бронирование со статусом `cancelled` (для новой попытки используйте новый
ключ).

Ошибки:
- `400 invalid_request` — невалидное тело, дубликаты мест в списке,
  пустой список, отсутствие ключа идемпотентности;
- `400 seat_out_of_range` — номер места вне `1..capacity`;
- `404 not_found` — событие не существует;
- `409 seat_taken` — некоторые места уже заняты (сообщение перечисляет
  какие). Бронирование атомарно: при конфликте не бронируется ни одно
  место из запроса.

Ограничение: не более 100 мест в одном запросе.

### `GET /bookings/{id}` — посмотреть бронирование

### `POST /bookings/{id}/cancel` — отменить бронирование

```bash
curl -s -XPOST localhost:8080/bookings/5/cancel
```

Возвращает бронирование со статусом `cancelled` и полем `cancelled_at`.
Отмена **идемпотентна**: повторный вызов (в т.ч. одновременный) возвращает
`200 OK` с тем же бронированием и освобождает места ровно один раз —
после отмены места сразу доступны для нового бронирования. Неизвестный id —
`404 not_found`.

### `GET /healthz` — проверка живости (`200` или `503`, если БД недоступна)

## Принятые решения

### Модель данных и гарантии

- **Схема** (миграции в `internal/store/migrations.go`): `events`,
  `bookings`, `booking_seats`. Место — это строка `booking_seats` с
  флагом `active`; бронирование владеет своими строками мест.
- **Запрет перепродажи** — частичный уникальный индекс
  `UNIQUE (event_id, seat_no) WHERE active`: одно активное место — не
  более чем у одного бронирования. Гарантия на уровне БД, поэтому
  действует при любом числе экземпляров сервиса и при любой конкуренции.
- **Идемпотентность создания** — уникальный констрейнт
  `(event_id, client_token)`: повторный `INSERT` с тем же ключом не
  создаёт вторую строку, а возвращает существующее бронирование
  (`INSERT ... ON CONFLICT DO NOTHING`). Именно поэтому клиент может
  безопасно повторить запрос при таймауте/обрыве сети.
- **Отмена ровно один раз** — отмена выполняет
  `UPDATE bookings SET status='cancelled' WHERE id=? AND status='confirmed'`
  и `UPDATE booking_seats SET active=false WHERE booking_id=? AND active`
  в одной транзакции. Вторая (или параллельная) отмена не находит строку
  со статусом `confirmed`, уходит в идемпотентное чтение и не трогает
  места повторно: `WHERE active` делает повторное освобождение
  невозможным, а строка блокируется до коммита первой отмены.
- **Многоместное бронирование атомарно** — все места вставляются в одной
  транзакции; места вставляются в порядке возрастания номера, поэтому
  конкурирующие транзакции берут блокировки индекса в одинаковом порядке
  и не могут зайти в deadlock.
- **Два экземпляра** — все гарантии обеспечиваются транзакциями и
  ограничениями БД, состояние в процессе не хранится (нет кешей/локов в
  памяти). Это явно проверяется тестом `TestTwoInstancesSharedDB` (два
  инстанса с раздельными пулами соединений).

### Миграции

- Применяются при старте приложения; каждая — в транзакции, все DDL
  идемпотентны (`IF NOT EXISTS`), прогресс фиксируется в
  `schema_migrations`. Повторный запуск на базе с данными — no-op без
  потери данных; конкурентный запуск двух экземпляров сериализуется
  advisory lock `pg_advisory_lock`.
- Внешних миграторов (golang-migrate и т.п.) нет — одна зависимость
  `pgx`.

### Прочее

- Драйвер: `github.com/jackc/pgx/v5` (stdlib-режим через `database/sql`);
  зависимости зафиксированы в `go.mod`/`go.sum`.
- Роутинг: стандартный `net/http` (Go ≥ 1.22), без веб-фреймворков.
- Строгий разбор JSON (`DisallowUnknownFields`, лимит тела 1 МБ).
- Логирование запросов, recovery-middleware, graceful shutdown.
- Данные хранятся только в PostgreSQL — переживают перезапуск приложения
  (проверено тестом `TestPersistenceAcrossRestart`).

## Тесты

Юнит-тесты (валидация, без БД):

```bash
go test ./...
```

Интеграционные тесты (настоящая PostgreSQL, race detector, включая
конкурентные сценарии и два экземпляра). Скрипт поднимает одноразовый
контейнер PostgreSQL, прогоняет все тесты и удаляет контейнер:

```bash
scripts/integration.sh
```

Эквивалентно вручную:

```bash
docker run -d --rm -p 55432:5432 -e POSTGRES_USER=booking \
  -e POSTGRES_PASSWORD=booking -e POSTGRES_DB=booking_test postgres:16-alpine
BOOKING_TEST_DATABASE_URL='postgres://booking:booking@localhost:55432/booking_test?sslmode=disable' \
  go test -race -count=1 -timeout 10m ./...
```

Что покрывают интеграционные тесты:

- жизненный цикл событий и доступность (включая список свободных мест);
- все сценарии ошибок валидации и 404/409;
- идемпотентность создания бронирования (последовательную и конкурентную:
  16 одновременных запросов с одним ключом → одно бронирование);
- конкурентное бронирование одного места 24 параллельными запросами →
  ровно один успех;
- массовое конкурентное бронирование без перепродажи и дублей мест;
- отмену: конкурентную (16 одновременных отмен → места освобождаются
  ровно один раз) и гонку «отмена против повторного бронирования того же
  места» на двух экземплярах;
- сохранность данных после «перезапуска» (закрытие и новое открытие пула
  соединений);
- повторный и конкурентный запуск миграций.

## Структура проекта

```
cmd/server/          — точка входа (конфигурация, запуск, graceful shutdown)
internal/domain/     — доменные типы и ошибки
internal/service/    — бизнес-логика и валидация
internal/store/      — реализация на PostgreSQL + миграции
internal/httpapi/    — HTTP-хендлеры, маппинг ошибок, middleware
integration/         — интеграционные тесты (пропускаются без BOOKING_TEST_DATABASE_URL)
scripts/             — scripts/integration.sh
Dockerfile, compose.yaml
```

## Известные ограничения

- Нет аутентификации/авторизации: любой клиент может отменить любое
  бронирование по id (в задании не требовалось).
- Ключ идемпотентности уникален в рамках события; повтор уже
  отменённого бронирования возвращает его со статусом `cancelled`, а не
  создаёт новое (нужно использовать новый ключ).
- При конфликте хотя бы по одному месту запрос целиком отклоняется
  (`409`); частичное бронирование не выполняется, «подобрать другие
  места» сервис не умеет.
- `GET /events` без пагинации; `available_seat_numbers` в
  `GET /events/{id}` может быть большим массивом при большой
  вместимости.
- Лимиты: вместимость ≤ 100000, ≤ 100 мест на запрос, длина имени ≤ 200
  символов, ключ идемпотентности ≤ 128 символов, тело запроса ≤ 1 МБ.
- Очистки старых отменённых бронирований (retention) нет — строки мест с
  `active=false` остаются как история.
- Метрики (Prometheus) и трейсинг не реализованы; есть только логи и
  `/healthz`.
- Отсутствует rate limiting.
