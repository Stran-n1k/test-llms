# Booking API

Небольшой HTTP JSON-сервис на Go для создания событий и бронирования мест.
Данные хранятся в PostgreSQL. Авторизация намеренно отсутствует.

## Запуск

Требуются Docker с Compose либо Go 1.24+ и доступный PostgreSQL.

```bash
docker compose up --build
```

Сервис будет доступен на `http://localhost:8080`. PostgreSQL слушает порт
`5432`; логин, пароль и имя базы в демонстрационном `compose.yaml` — `booking`.
Данные PostgreSQL находятся в именованном томе `postgres_data` и сохраняются
после перезапуска контейнеров. Остановка без удаления данных:

```bash
docker compose down
```

Для запуска без Docker:

```bash
export DATABASE_URL='postgres://booking:booking@localhost:5432/booking?sslmode=disable'
export HTTP_ADDR=':8080'
go run ./cmd/booking
```

`DATABASE_URL` обязателен. Если `HTTP_ADDR` не задан, используется `:8080`.
При старте приложение автоматически применяет схему. На подключение, проверку
базы и миграцию выделен общий 30-секундный тайм-аут запуска.

## API

Идентификаторы событий и бронирований — UUID, время — RFC 3339 в формате JSON
Go. Успешные ответы и ошибки имеют `Content-Type: application/json`.

### Создать событие

`POST /events`

- `title`: непустая строка до 200 символов, крайние пробелы удаляются;
- `capacity`: целое от 1 до 1 000 000.

```bash
curl -i http://localhost:8080/events \
  -H 'Content-Type: application/json' \
  -d '{"title":"Concert","capacity":100}'
```

Ответ `201 Created`:

```json
{
  "id": "3d6ca37e-bcf0-4f38-8ff1-29e1a617e7f6",
  "title": "Concert",
  "capacity": 100,
  "booked_seats": 0,
  "available_seats": 100,
  "created_at": "2026-01-01T12:00:00Z"
}
```

### Посмотреть событие и доступность

```bash
EVENT_ID='3d6ca37e-bcf0-4f38-8ff1-29e1a617e7f6'
curl -s "http://localhost:8080/events/$EVENT_ID"
curl -s "http://localhost:8080/events/$EVENT_ID/availability"
```

Оба маршрута используют `GET`. Второй возвращает `event_id`, `capacity`,
`booked_seats` и `available_seats`.

### Забронировать несколько мест

`POST /bookings`

- `event_id`: UUID существующего события;
- `seats`: целое от 1 до 1 000 000;
- `idempotency_key`: выбранная клиентом уникальная строка от 1 до 200 байт.

```bash
curl -i http://localhost:8080/bookings \
  -H 'Content-Type: application/json' \
  -d "{\"event_id\":\"$EVENT_ID\",\"seats\":3,\"idempotency_key\":\"order-42\"}"
```

Первый успешный запрос возвращает `201 Created`. Повтор с тем же ключом и теми
же `event_id` и `seats` возвращает `200 OK` и исходную бронь, не резервируя
места повторно. Тот же ключ с другими параметрами даёт `409 Conflict` с кодом
`idempotency_conflict`. Недостаток мест даёт `409 Conflict` с кодом
`insufficient_capacity`.

Клиент должен генерировать новый ключ для каждой новой логической операции и
сохранять его для повторов после тайм-аута или обрыва соединения. Ключи
глобальны для базы, а не только для одного события. Повтор после отмены
возвращает исходную бронь в статусе `cancelled`; для новой брони нужен новый
ключ.

Ответ брони:

```json
{
  "id": "d7c58044-b62f-46b7-a7e6-caa2a6e21c59",
  "event_id": "3d6ca37e-bcf0-4f38-8ff1-29e1a617e7f6",
  "seats": 3,
  "idempotency_key": "order-42",
  "status": "active",
  "created_at": "2026-01-01T12:01:00Z"
}
```

### Посмотреть и отменить бронирование

```bash
BOOKING_ID='d7c58044-b62f-46b7-a7e6-caa2a6e21c59'
curl -s "http://localhost:8080/bookings/$BOOKING_ID"
curl -i -X DELETE "http://localhost:8080/bookings/$BOOKING_ID"
```

Отмена возвращает `200 OK` и бронь со статусом `cancelled` и полем
`cancelled_at`. Повторная и одновременная отмены также возвращают `200 OK`, но
места учитываются как возвращённые только один раз.

### Проверка состояния

```bash
curl -s http://localhost:8080/healthz
```

`GET /healthz` проверяет соединение с PostgreSQL и возвращает `200 OK` либо
`503 Service Unavailable`.

### Ошибки

Формат ошибки:

```json
{"error":{"code":"validation_error","message":"capacity must be between 1 and 1000000"}}
```

Используются коды `400` для JSON, UUID и параметров, `404` для отсутствующих
объектов, `405` для неподдерживаемого метода, `409` для конфликтов вместимости
и идемпотентности, `415` для неверного `Content-Type`. Тело запроса ограничено
1 МиБ; неизвестные JSON-поля и несколько JSON-значений в теле отклоняются.

## Гарантии и устройство хранения

В `events` хранятся вместимость и текущее число активных забронированных мест.
В `bookings` сохраняются активные и отменённые брони; уникальность
`idempotency_key` обеспечивается ограничением PostgreSQL.

Все проверки и изменения одной операции выполняются в транзакции:

1. При создании брони берётся PostgreSQL advisory lock по хешу ключа
   идемпотентности. Поэтому одинаковые запросы сериализуются даже между разными
   экземплярами сервиса. Существующая бронь проверяется до вместимости.
2. Для новой брони строка события блокируется через `SELECT ... FOR UPDATE`.
   Проверка доступности, увеличение `booked_seats` и вставка брони атомарны;
   конкурентные запросы не могут превысить вместимость.
3. Отмена выполняет условный `UPDATE ... WHERE status = 'active'` с
   `RETURNING`. Только один конкурентный запрос меняет статус и уменьшает
   `booked_seats`; остальные читают уже отменённую бронь. Транзакция гарантирует,
   что статус и счётчик меняются вместе.

Advisory lock используется и при первоначальной миграции, чтобы параллельный
запуск нескольких экземпляров на пустой базе был безопасен. Ограничения `CHECK`
дополнительно не допускают отрицательного счётчика или превышения вместимости.

## Тесты

Все пакеты можно проверить без базы; PostgreSQL-тесты при этом будут пропущены:

```bash
go test ./...
go vet ./...
```

Для полного набора нужна отдельная тестовая база. Например, с PostgreSQL из
этого проекта:

```bash
docker compose up -d postgres
export TEST_DATABASE_URL='postgres://booking:booking@localhost:5432/booking?sslmode=disable'
go test -race -count=1 -v ./...
```

Каждый тест создаёт собственную случайную схему и удаляет только её после
завершения. Тесты проверяют повторную миграцию и сохранность данных,
конкурентное бронирование через два пула соединений с одной базой, повторы
идемпотентных запросов, конкурентную отмену, HTTP API и ошибочные запросы.

## Известные ограничения

- Нет авторизации, списков с пагинацией, изменения и удаления событий; событие
  имеет только название и фиксированную вместимость.
- Брони и ключи идемпотентности хранятся бессрочно. Нет автоматической отмены,
  истечения броней и восстановления отменённой брони.
- Миграции создают начальную схему через `CREATE ... IF NOT EXISTS` и безопасно
  повторяются, но это не полноценная система версионированного изменения уже
  существующих таблиц.
- Тайм-аут запуска не является бесконечным ожиданием PostgreSQL: при
  длительной недоступности базы процесс завершается, после чего его должен
  перезапустить оркестратор или оператор.
