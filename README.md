# Сервис бронирования мест

Небольшой backend на Go + PostgreSQL для событий с ограниченной вместимостью:
создание событий, просмотр доступности, бронирование нескольких мест одним
запросом, просмотр и отмена бронирований.

## Стек и устройство

- Go 1.27, стандартный `net/http` (роутинг по шаблонам Go 1.22+).
- PostgreSQL 16, драйвер `github.com/jackc/pgx/v5` (`pgxpool`).
- UUID v4 (`github.com/google/uuid`).
- SQL-миграции встроены в бинарник через `go:embed` и применяются при старте.
- Интеграционные тесты поднимают настоящий PostgreSQL через Testcontainers;
  можно также указать внешнюю базу в `TEST_DATABASE_URL`.

```
cmd/server            точка входа, HTTP-сервер, graceful shutdown
internal/api          маршруты, middleware, валидация, JSON-ошибки
internal/store        транзакции и SQL (ёмкость, идемпотентность, отмена)
internal/migrate      встроенные миграции + advisory lock
internal/db           пул подключений и ожидание готовности БД
internal/config       DATABASE_URL / HTTP_ADDR
internal/model        доменные типы
internal/testutil     PostgreSQL для тестов и изолированные схемы
internal/integration  интеграционные тесты HTTP API
```

## Быстрый старт

```bash
docker compose up --build -d
curl -s http://localhost:8080/healthz
```

Сервис слушает `http://localhost:8080`. PostgreSQL доступен на порту 5432.
Порты можно переопределить:

```bash
APP_PORT=9090 POSTGRES_PORT=55432 docker compose up --build -d
```

Данные PostgreSQL хранятся в именованном томе `booking_postgres_data`:

- `docker compose down` — останавливает сервисы, **данные сохраняются**;
- `docker compose down -v` — удаляет том вместе с данными;
- `docker compose up -d` после перезапуска — данные и схема на месте.

Остановка:

```bash
docker compose down
```

### Запуск без Docker для приложения

```bash
export DATABASE_URL='postgres://booking:booking@localhost:5432/booking?sslmode=disable'
export HTTP_ADDR=':8080'
go run ./cmd/server
```

### Конфигурация

| Переменная     | Обязательна | По умолчанию | Назначение                       |
|----------------|-------------|--------------|----------------------------------|
| `DATABASE_URL` | да          | —            | строка подключения PostgreSQL    |
| `HTTP_ADDR`    | нет         | `:8080`      | адрес HTTP-сервера (`host:port`) |

Секреты в `compose.yaml` — только для локальной разработки.

## API

Все ответы — JSON. Время — RFC 3339 / `timestamptz`. Размер тела запроса
ограничен 1 MiB, для `POST` требуется `Content-Type: application/json`.
Неизвестные поля в JSON отклоняются.

| Метод  | Путь                        | Назначение                              | Успех |
|--------|-----------------------------|-----------------------------------------|-------|
| GET    | `/healthz`                  | liveness                                | 200   |
| GET    | `/readyz`                   | readiness (проверяет БД)                | 200/503 |
| POST   | `/events`                   | создать событие                         | 201   |
| GET    | `/events`                   | список событий                          | 200   |
| GET    | `/events/{id}`              | событие с доступностью                  | 200   |
| GET    | `/events/{id}/availability` | только доступность                      | 200   |
| POST   | `/events/{id}/bookings`     | создать бронирование (нужен ключ)       | 201/200 |
| GET    | `/events/{id}/bookings`     | все бронирования события                | 200   |
| GET    | `/bookings/{id}`            | бронирование                            | 200   |
| DELETE | `/bookings/{id}`            | отменить бронирование (идемпотентно)    | 200   |

### Создать событие

```bash
curl -s -X POST http://localhost:8080/events \
  -H 'Content-Type: application/json' \
  -d '{
    "name": "Go Conference",
    "capacity": 100,
    "starts_at": "2026-12-01T18:00:00Z"
  }'
```

```json
{
  "id": "0c4e5b7a-7a5b-4d2d-bde1-7f8f42a0c111",
  "name": "Go Conference",
  "capacity": 100,
  "reserved_seats": 0,
  "available_seats": 100,
  "starts_at": "2026-12-01T18:00:00Z",
  "created_at": "2026-11-05T12:00:00.123456Z"
}
```

В ответе также есть заголовок `Location: /events/{id}`.
`capacity` — от 1 до 1 000 000. `starts_at` обязателен; события в прошлом не
запрещены (например, для уже идущих мероприятий).

Список: `GET /events` → `{"items": [ ...события... ]}`.

### Доступность

```bash
curl -s http://localhost:8080/events/{id}/availability
```

```json
{
  "event_id": "0c4e5b7a-7a5b-4d2d-bde1-7f8f42a0c111",
  "capacity": 100,
  "reserved_seats": 2,
  "available_seats": 98
}
```

### Забронировать места

`Idempotency-Key` обязателен. Это и есть механизм безопасного повтора: клиент
сам выбирает ключ (например, UUID) и при повторе отправляет тот же ключ и то же
тело запроса.

```bash
curl -s -i -X POST http://localhost:8080/events/{id}/bookings \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: 7b6f2a2c-6f0e-4a8e-9e1e-3a2f4c5d6e7f' \
  -d '{
    "seats": 2,
    "customer_name": "Alice",
    "customer_email": "alice@example.com"
  }'
```

Первый запрос: `201 Created`, `Location: /bookings/{id}`.

```json
{
  "id": "d1f1b3e8-35c1-4d5a-a1e7-7a9d0f2c4b6e",
  "event_id": "0c4e5b7a-7a5b-4d2d-bde1-7f8f42a0c111",
  "seats": 2,
  "status": "confirmed",
  "customer_name": "Alice",
  "customer_email": "alice@example.com",
  "created_at": "2026-11-05T12:01:00.654321Z"
}
```

Повтор с тем же ключом и телом: `200 OK`, тот же `id`, заголовок
`Idempotent-Replayed: true`; места повторно не списываются.

Тот же ключ с другим телом (другие места, имя, email, событие): `409` с кодом
`idempotency_key_conflict`. Ключ уникален в пределах события.

Если мест не хватает: `409` с кодом `not_enough_seats` и деталями:

```json
{
  "error": {
    "code": "not_enough_seats",
    "message": "not enough seats are available for this event",
    "details": {"available_seats": 1, "requested_seats": 2}
  }
}
```

### Отменить бронирование

```bash
curl -s -X DELETE http://localhost:8080/bookings/{id}
```

Возвращает `200 OK` и бронирование со `"status": "cancelled"` и
`cancelled_at`. Повторная и одновременная отмена безопасны: места
возвращаются ровно один раз, повторный вызов — успешный no-op.

### Ошибки

Единый формат:

```json
{
  "error": {
    "code": "validation_error",
    "message": "capacity must be between 1 and 1000000",
    "field": "capacity"
  }
}
```

| Код                          | HTTP | Когда                                      |
|------------------------------|------|--------------------------------------------|
| `invalid_json`               | 400  | битый JSON, лишние поля, несколько объектов |
| `validation_error`           | 400  | неверные значения полей                    |
| `invalid_id`                 | 400  | id в пути не UUID                          |
| `idempotency_key_required`   | 400  | нет заголовка `Idempotency-Key`            |
| `unsupported_media_type`     | 415  | `Content-Type` не `application/json`       |
| `payload_too_large`          | 413  | тело больше 1 MiB                          |
| `event_not_found`            | 404  | события нет                                |
| `booking_not_found`          | 404  | бронирования нет                           |
| `not_enough_seats`           | 409  | не хватает мест                            |
| `idempotency_key_conflict`   | 409  | ключ повторно использован с другим телом    |
| `not_found`                  | 404  | неизвестный маршрут                        |
| `internal_error`             | 500  | внутренняя ошибка (детали не раскрываются) |

## Гарантии и принятые решения

### 1. Ёмкость не превышается никогда

`events.reserved_seats` — единственный источник учёта занятых мест. Резерв
выполняется одной атомарной командой в транзакции:

```sql
UPDATE events
SET reserved_seats = reserved_seats + $2
WHERE id = $1 AND reserved_seats + $2 <= capacity
RETURNING capacity - reserved_seats;
```

PostgreSQL блокирует строку события на время `UPDATE`, поэтому параллельные
бронирования одного события выполняются последовательно на уровне БД. Второй
экземпляр сервиса использует ту же строку и тот же механизм — общего
in-memory состояния нет. Дополнительная страховка —
`CHECK (reserved_seats <= capacity)` и `CHECK (reserved_seats >= 0)`: даже
ошибочный код не сможет сохранить перепроданное состояние.

Бронирование и списание мест происходят в одной транзакции: либо есть и
бронирование, и списанные места, либо нет ничего.

### 2. Идемпотентность создания бронирования

- Клиент передаёт `Idempotency-Key` (1–200 символов).
- Уникальный индекс `(event_id, idempotency_key)` не даёт создать дубликат.
- Вместе с бронированием сохраняется SHA-256 канонического JSON тела запроса.
- Повтор с тем же ключом и телом возвращает существующее бронирование
  (`200`, `Idempotent-Replayed: true`) без повторного списания мест.
- Тот же ключ с другим телом → `409 idempotency_key_conflict`.
- Гонка двух одновременных запросов с одним ключом разрешается уникальным
  индексом: проигравшая транзакция откатывается (вместе со списанием мест),
  затем возвращает бронирование победителя.
- Ключи не истекают и хранятся бессрочно; область действия — событие.
- Бронирование, отменённое после создания, при повторе исходного запроса
  вернётся в статусе `cancelled` и не будет создано заново. Для новой
  брони нужен новый ключ.

Создание событий намеренно не идемпотентно: повтор создаёт новое событие.

### 3. Отмена возвращает места ровно один раз

Отмена выполняется в одной транзакции:

1. `SELECT ... FOR UPDATE` блокирует бронирование;
2. если оно уже `cancelled` — успешный no-op;
3. иначе статус меняется на `cancelled`, затем `reserved_seats`
   уменьшается на число мест.

Блокировка строки исключает двойное уменьшение при одновременных запросах.
Проверка `reserved_seats >= 0` не даёт уйти в минус. Отмена идемпотентна по
идентификатору бронирования, отдельный ключ не нужен.

### 4. Два и более экземпляра

Все гарантии основаны на транзакциях и блокировках PostgreSQL. Несколько
экземпляров с общим `DATABASE_URL` работают корректно: нет локальных счётчиков,
кэшей или фоновых процессов, влияющих на ёмкость. Интеграционные тесты
поднимают два независимых пула подключений и два HTTP-сервера на одной схеме.

Пример второго контейнера (проект compose называется `booking`, сеть —
`booking_default`):

```bash
docker compose up -d --build postgres app
docker run -d --name booking-app-2 \
  --network booking_default \
  -e DATABASE_URL='postgres://booking:booking@postgres:5432/booking?sslmode=disable' \
  -e HTTP_ADDR=':8080' \
  -p 8081:8080 \
  booking-app
```

### 5. Схема и миграции

- SQL-файлы лежат в `internal/migrate/migrations` и встроены в бинарник.
- Учёт применённых версий — таблица `schema_migrations`.
- Каждая миграция применяется в транзакции; ошибка откатывает её целиком.
- Перед применением берётся advisory lock PostgreSQL, поэтому одновременно
  стартующие экземпляры не применяют одну миграцию дважды.
- Повторный запуск пропускает уже применённые версии и не трогает данные.
- Схема создаётся автоматически при старте на пустой базе.

### 6. Валидация

- Строгий JSON: неизвестные поля, мусор после объекта и несколько JSON-значений
  отклоняются.
- Проверяются: имя (1–200 символов), вместимость (1–1 000 000), `starts_at`
  (RFC 3339), число мест (1–1 000 000), email, длина и управляющие символы в
  `Idempotency-Key`.
- Некорректные запросы не создают и не меняют данные.
- Нехватка мест — это конфликт с текущим состоянием (`409`), а не ошибка
  формата (`400`).

## Тесты

```bash
go test ./...          # unit + integration
make test              # то же
make test-unit         # без PostgreSQL
make test-integration  # только интеграционные
```

Интеграционные тесты запускают `postgres:16-alpine` в Docker через
Testcontainers. Нужен доступ к Docker. Вместо контейнера можно указать
существующую базу:

```bash
TEST_DATABASE_URL='postgres://user:pass@localhost:5432/postgres?sslmode=disable' \
  go test ./internal/integration/... -count=1
```

Каждый тест получает отдельную схему PostgreSQL, применяет туда миграции и
удаляет её после завершения, поэтому тесты не мешают друг другу и не требуют
пустой базы.

Что проверяется:

- полный жизненный цикл события, бронирования и отмены;
- коды и форматы ошибок для некорректных запросов;
- повтор запроса с тем же `Idempotency-Key`, конфликт с другим телом;
- 100 конкурентных бронирований на 10 мест через два экземпляра — ровно
  10 успехов, 90 отказов, `reserved_seats` не превышает `capacity`;
- конкурентные многоместные бронирования (по 3 места) без перепродажи;
- 30 одновременных одинаковых запросов — одно бронирование, остальные replay;
- 40 одновременных отмен одного бронирования через два экземпляра — места
  возвращаются один раз;
- устаревшая повторная отмена после нового бронирования не освобождает чужие
  места;
- сохранность данных после закрытия пула и пересоздания экземпляра;
- идемпотентность повторного применения миграций без потери данных;
- health/readiness.

## Известные ограничения и допущения

- Нет авторизации и пользовательских аккаунтов. `customer_name` и
  `customer_email` — необязательные информационные поля; ими может
  воспользоваться любой клиент.
- Нет обновления и удаления событий, изменения вместимости и отмены события.
  Вместимость фиксируется при создании.
- Бронирование удерживает места бессрочно, пока его не отменят. Нет срока
  жизни брони, оплаты и автоматического истечения.
- Нет выбора конкретных мест и схемы зала — только количество.
- Нет списка ожидания; после отмены места просто снова доступны.
- `Idempotency-Key` хранятся бессрочно; политики очистки нет. Ключ действует
  в пределах одного события.
- Списки событий и бронирований не пагинированы — рассчитаны на небольшие
  объёмы.
- Нет rate limiting, TLS и аутентификации на уровне приложения; предполагается
  запуск за обратным прокси.
- Гарантии рассчитаны на один кластер PostgreSQL. При недоступности БД сервис
  отвечает `503` на `/readyz` и `500` на бизнес-запросы; автоматических
  ретраев на стороне сервера нет.
- `405 Method Not Allowed` для известного пути с неверным методом формируется
  стандартным `net/http` как текст, остальные ошибки — JSON.
- `docker compose` содержит dev-пароль и публикует порт PostgreSQL; для
  production нужны другие настройки и сетевые ограничения.
